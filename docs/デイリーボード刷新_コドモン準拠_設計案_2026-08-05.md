# デイリーボード刷新（コドモン準拠）設計案

作成: 2026-08-05 / 出典: 実機確認②の要望群（K5〜K8 + 登降園タイムバー + 出欠編集モーダル + 各種チェック一覧）とコドモン参照画面。

## 方針
デイリーボードを起点に、園児1人の当日の各機能（出欠・登降園・連絡帳・家庭での様子・健康/食事チェック）へ集約導線を張る。UI思想は「園児は一覧・操作は行内・時間軸/一括は上部」。

## DB変更が必要（承認ゲート対象）
- **#2 出欠**: `child_daily_attendance` 拡張（`attendance_kind` enum・`scheduled_start_at`/`scheduled_end_at`/`scheduled_slot`・`attendance_note`）、`is_absent` は kind から生成列/トリガで同期（サマリー163非破壊）。`child_attendance_events.event_type` に `out`/`return` 追加。職員用RPC（出欠保存・実績修正）。
- **#1 登降園予定**: コドモンの登降園管理では予定が**曜日パターン（月火水木金 等）付き**で表示される＝**園児ごとの週次標準保育時間（曜日別）マスタ**が予定の既定値。よって二層構成を推奨: **(a) `child_weekly_schedule`（child × 曜日 × start/end）標準 ＋ (b) 日別override（#2の scheduled_* で当日変更）**。`fetch_daily_board_for_office` を drop+recreate し、登園/降園/外出/戻り時刻・予定(標準or当日)・種別・メモ・中抜け合計を返す（read-only）。
- **#9 登降園管理一覧**: #2/#1 と同一データの一覧編集ビュー（出欠連絡・出欠・予定・打刻・中抜け）。専用の追加スキーマは不要（#2＋週次スケジュールに乗る）。
- **#5 検温複数回**（対応する場合のみ）: `child_daily_contacts.temperature` を複数回対応（`temperature_records jsonb` 追加 等）。

## UI-onlyで先行可能（DB最小 or なし）
- **#3 連絡帳ポップアップ**（既存画面の再利用）
- **#4 家庭での様子 一覧**（read-only fetch RPC 1本追加のみ）
- **#6 排便 / #8 食事 の一覧入力**（既存 `child_daily_contacts` フィールドへの bulk UI ＋ upsert RPC）

## 段階計画案（提案）
- **Phase A（UI先行・DB最小）**: #4 家庭での様子一覧（RPC1本）＋ #3 連絡帳ポップアップ ＋ デイリーボードからの各機能導線集約。→ 早期に「一覧で見る」価値を提供。
- **Phase B（出欠・登降園）**: #2 DB拡張 → 出欠編集モーダル ＋ #1 登降園タイムバー（実績→予定の順）。K5(欠席選択廃止)を内包。
- **Phase C（健康/食事チェック一覧）**: #6 排便・#8 食事の一覧入力、必要なら #5 検温複数回。#7 午睡は実装済のため導線統合のみ。

## 週次標準スケジュールの曜日規約（184で確定）
`child_weekly_schedule.weekday` は **ISO 8601 = 1:月曜 … 7:日曜**（Dart `DateTime.weekday` と一致）。
- 権限: **設定(set/delete)=manages_childcare(主任以上)**、取得(fetch)=has_childcare_office_access(担当施設の職員)。
- 「その曜日は通わない」= `delete_child_weekly_schedule(child, weekday)` で行削除。

| weekday | 曜日 | Dart `DateTime.weekday` | JS `Date.getDay()` |
|---|---|---|---|
| 1 | 月 | 1 (DateTime.monday) | 1 |
| 2 | 火 | 2 | 2 |
| 3 | 水 | 3 | 3 |
| 4 | 木 | 4 | 4 |
| 5 | 金 | 5 | 5 |
| 6 | 土 | 6 | 6 |
| 7 | 日 | 7 (DateTime.sunday) | 0 |

> フロント: Dart はそのまま `DateTime.weekday` を渡す。admin_web(JS)は `getDay()` の 0(日) を 7 に変換して渡すこと（`d.getDay() === 0 ? 7 : d.getDay()`）。

## 決定事項（2026-08-05 俊確定）
1. **着手順**: K5完了 → **Phase A（家庭での様子一覧＋連絡帳ポップアップ）先行**。Phase AはDB変更なしのため本番リリース(145〜183)をブロックしない。DBを伴う第2弾は**本番リリース後**に適用。
2. **予定の二層**: 週次標準＋日別override で確定。入力経路: **週次標準=園児マスタ画面で職員が設定 / 日別override=出欠モーダル(K7)から編集**。「保護者からの連絡（お迎え変更→日別override）」の連動は**将来枠**として記載のみ。
3. **attendance_kind**: `none(-)/late(遅刻)/early_leave(早退)/sick_absence(病欠)/personal_absence(都合欠)`。**遅刻・早退は出席の属性で欠席ではない**。`is_absent` と同期するのは**病欠・都合欠のみ**。サマリー欠席数=病欠+都合欠、遅刻/早退は登園予定・出席側。既存の種別なし欠席は **kind=NULL 許容**・表示は「欠席」フォールバック（バックフィルで種別を捏造しない）。
4. **検温は複数回**で設計。家庭連絡帳の朝検温（保護者記入・既存）は維持し、**園側検温（職員が日中に複数回：記録時刻＋体温）を新設**。K8一覧は「保護者の朝検温列＋園側検温の最新値」を表示。
5. **優先順位**: デイリーボード刷新を先行、Phase 4（クラス活動+Instagram）はその後。

## admin_web 同等実装スコープ（W7 追記 2026-08-07）

### 前提: Phase A は Ohana Kids のみ
- **Phase A（`3d1ba7b`）は Ohana Kids（Flutter/`lib`）専用**であることを確認済み。変更ファイルは全て `lib/` 配下で `admin_web/` は一切含まない。
  - 家庭での様子一覧: `lib/screens/childcare/family_report/family_report_list_screen.dart`＋`childcare_service.fetchFamilyDailyReportsForOffice`（`family_daily_reports` を `children!inner` で office 絞り込み＋`status='submitted'`、**新規RPCなし**・既存RLS `staff_has_guardian_data_access` で保護）。
  - デイリーボードから「家庭での様子」導線＋園児行の「日誌・連絡帳」リンク（既存 `DailyContactDetailScreen` 再利用）。
- したがって **admin_web には Phase A 相当の画面・導線がまだ無い**（実機確認2026-08-06のW7指摘＝admin_webに家庭での様子一覧への導線が無い、はこの通り）。

### admin_web 同等実装（K6/K7/検温/K8/週次）に以下を追加する
既存スコープ（K6 排便一覧・K7 出欠編集モーダル・園側検温・K8 家庭での様子/健康一覧・週次標準スケジュール）に、次の2点を**追記**する:

1. **家庭での様子一覧の画面＋ナビタブ（admin_webにPhase A相当を新設）**
   - Ohana Kids の `family_report_list_screen` と同等の一覧を admin_web に実装（施設×日で全園児の `family_daily_reports`：機嫌/排便/睡眠/食事/検温/迎え/子どもの様子）。
   - `ChildcareNav` に「家庭での様子」タブを追加し、デイリーボードからも導線を張る。
   - **データ取得方針**: Ohana Kids は直接select＋既存RLSで実装したが、admin_web でも同一の `family_daily_reports` を `children!inner`＋`status='submitted'` で取得可能（既存RLS保護）。ただし K8 として「保護者の朝検温列＋園側検温の最新値」を並べる要件（決定事項4）があるため、**園側検温（184〜188系の staff_temperature_records）と結合した read-only fetch RPC を1本用意する方が UI が単純化する**。DB追加の要否は第2弾（184〜189）適用後にRPC設計として確定する。
   - **注意（K8 の read-onlyフェッチ設計）**: RETURNS TABLE のOUTパラメータ名と参照列名の衝突（`notice_id`/`child_id` 等）は実行時 `column reference ... is ambiguous` で必ず失敗する（135/136/**190**の同型バグ）。新規fetch RPCは全参照をテーブル別名で修飾すること。

2. **「欠席選択タブ」の廃止（K5と同じ整理＝欠席登録はデイリーボードに集約）**
   - Ohana Kids の K5 と同じ整理を admin_web にも適用: **欠席の登録・確認はデイリーボード（＋K7 出欠編集モーダルの attendance_kind）に集約**し、独立した「欠席選択タブ」は廃止する。
   - `attendance_kind` の `sick_absence`/`personal_absence` が `is_absent` と同期する設計（決定事項3）に一本化されるため、欠席専用タブは重複導線となる。
