# 1. 目的

Ohana Worksへ次を追加する。

1. OpenRouterを利用した文書リライト・文章作成支援基盤
2. 保育園職員が撮影した写真の保存・公開・販売
3. 保護者への月次請求
4. 保護者アプリからのオンライン決済
5. 施設別・契約プラン別の保育料計算
6. 前月実績に基づく延長保育料、給食費、行事費、教材・備品費等の合算
7. 入金、未収、返金、取消、督促、会計連携の管理
8. 職員マスタからの雇用契約書・労働条件通知書の作成、A4 PDF出力、職員アプリ配信
9. 保護者向け入園契約、必須同意、条件付き提出書類の一元管理
10. 同意内容、同意者、日時、文書版、回答項目を改ざん検知可能な証跡として保存
11. 保護者アプリの園児マスタ内「児童票」入力と、保育業務Webでの確認・承認
12. 感染症による欠席連絡、疾病チェック、登園再開時に必要な意見書・登園届の案内、作成、提出、園側確認
13. 2026年度規程に基づく雇用契約書・労働条件通知書の条件別生成
14. 入社時誓約、自社保育園利用、短時間勤務、自転車通勤、中退共、スポット雇用等の対象者別手続き
15. 職員の写真・動画・音声・氏名をWeb、SNS、採用広報等に利用するための用途別同意
16. 規程配布・既読確認、電子交付希望、電子同意、電子署名、紙署名を文書の性質に応じて使い分ける入社手続き基盤

Ohana Worksを請求内容の正本とし、決済事業者は支払いの受付・決済結果・返金を担当する。料金計算や請求明細を決済事業者だけに依存させない。

# 2. 推奨方針の結論

## 2.1 AI

文章作成・リライトはOpenRouter APIを介して、OpenAIのGPT系モデルとAnthropicのClaude系モデルを切り替えられる設計とする。

ただし、Claude Codeは開発用のコーディングツールであり、アプリから呼び出すAIモデルそのものではない。実行時には、OpenRouter上のClaudeモデルとGPTモデルを使用する。

推奨方針：

- Claude Code：設計・実装・テストに使用
- OpenRouter：本番アプリのAIゲートウェイ
- GPTモデル：構造化、短文化、表現調整等の候補
- Claudeモデル：長文の文脈理解、丁寧な文章化等の候補
- 使用モデルは業務ごとの「AIモデルプロファイル」で設定
- 通常処理で2モデルへ同じ個人情報を同時送信しない
- 比較生成は管理者の品質検証時だけ使用

## 2.2 写真保存

Cloudflareのダッシュボードそのものへ保存するのではなく、Cloudflare R2 Object Storageを使用する。

推奨方針：

- 元写真：非公開R2 bucket
- プレビュー：縮小・透かし・メタデータ除去済み
- 購入後データ：短時間の署名付きURLで配信
- 公開bucketや固定URLを使用しない
- R2 APIキーをアプリへ入れない
- ブラウザ／アプリからのアップロードは、サーバーが発行する短時間の署名付きURLを使用

## 2.3 決済事業者

初期導入の第一候補はStripeとする。

理由：

- 写真購入の都度決済と、毎月の変動請求の両方を扱いやすい
- Checkout、Payment Intents、Invoicing、Billing、Webhook等の選択肢がある
- API・テスト環境・ドキュメントが充実している
- 料金が公開されており、初期の費用試算がしやすい
- 保護者が支払い方法を管理できるCustomer Portalがある
- 3Dセキュア、カード情報の非保持、決済失敗イベント等を利用できる

UnivaPayは次の場合に有力である。

- 口座振替を初期から重要な支払い方法にしたい
- 日本国内の複数決済方法を営業担当と相談して組み合わせたい
- 固定・変動の継続課金やCSV課金を国内サポート込みで導入したい
- 個別見積もりの結果、総費用がStripeより適している

ただし、初期から2社を同時接続すると、返金・入金消込・障害対応・問い合わせ対応が二重になる。まずStripeで開始し、`PaymentGateway`を抽象化してUnivaPayを将来追加できる設計を推奨する。

口座振替を正式運用の必須条件とする場合は、実装確定前にUnivaPayから次の書面見積もりを取得し、Stripe案と再比較すること。

- 初期費用
- 月額費用
- 決済手数料
- トランザクション費
- 振込費用
- 返金・取消費
- 口座振替費用
- コンビニ決済費用
- 入金サイクル
- API利用条件
- 審査期間
- 保育料・写真販売の取扱可否

## 2.4 労務・雇用文書

雇用契約書だけを差し込み生成するのではなく、次を共通文書基盤上で分離して管理する。

- 雇用契約書：労使双方が署名する契約
- 労働条件通知書：使用者が法定事項を明示する通知
- 就業規則・各規程：配布、閲覧、既読確認
- 入社時誓約・任意同意：文書ごとの同意、拒否、撤回
- 条件付き協定：自社保育園利用、短時間勤務等
- 申請・許可：自転車通勤等
- 紙原本：出力、受領、スキャン、保管場所

添付規程には、条文重複、適用範囲の不整合、直近の法改正との未整合候補がある。Claude Codeは原文を自動修正せず、`legal_review_blocked` として専門家承認済みの版だけを本番テンプレートにする。

職員写真・動画は、園児の肖像同意から推測せず、在職者を含む全職員から、Web、SNS、採用広報、印刷物等の用途別に新しい同意を取得する。不同意・未回答を不利益取扱いや公開許可へ変換してはならない。

スポット支援員は設計に含めるが、通常雇用の手続きが安定するまで機能フラグをOFFとする。導入時は、各勤務の開始前に勤務日時、場所、業務、休憩、賃金、交通費、支払条件を通知し、本人の承諾を記録する。

# 4. OpenRouter AI連携

## 4.1 用途

- 連絡帳文章作成
- 文章のリライト
- 個別目標シート
- 個別支援計画
- 架け橋カリキュラム
- 保育要録
- お知らせ文
- 保護者へ送る説明文
- 誤字・重複・不適切表現の確認

AIは事実を作成する機能ではなく、登録済みの事実を目的に合った文章へ整える機能とする。

## 4.2 Provider構造

```text
AIWritingProvider
└─ OpenRouterProvider
    ├─ OpenAI model profile
    └─ Anthropic model profile
```

将来、OpenAIやAnthropicとの直接契約へ変更しても業務画面を作り直さないよう、OpenRouter固有処理をProvider層へ閉じ込める。

## 4.3 AIモデルプロファイル

モデル名をコードへ直接記載しない。

```text
ai_model_profiles
- id
- profile_key
- purpose
- primary_model_id
- fallback_model_ids
- provider_order
- allow_fallbacks
- require_zdr
- deny_data_collection
- temperature
- max_output_tokens
- structured_output_schema
- prompt_template_version
- enabled
- effective_from
- effective_to
```

プロファイル例：

```text
contact_book_rewrite
contact_book_quality_check
goal_sheet_draft
support_plan_draft
bridge_document_draft
guardian_notice_rewrite
```

## 4.4 モデル選択

- モデルは管理者が用途ごとに指定する。
- 職員が毎回モデルを選ぶ方式にはしない。
- 主モデルで障害が発生した場合だけ、許可されたフォールバックモデルを使用する。
- フォールバック実行時はモデル名と理由を履歴へ保存する。
- 自動フォールバックで文章の性質が変わる可能性を考慮し、重要文書は再確認状態へ戻す。
- `latest` aliasを無条件で本番利用せず、検証済みモデルIDを固定期間使用する。
- モデル変更は検証環境で回帰テスト後に有効化する。

## 4.5 個人情報・データポリシー

保育・園児データを扱うリクエストでは次を必須とする。

```text
provider.data_collection = "deny"
provider.zdr = true
```

- OpenRouterのInput & Output Loggingを本番で有効にしない。
- OpenRouterによる入力・出力利用のオプトインを有効にしない。
- ZDRに対応しないモデル・Providerへ機微情報を送信しない。
- Web検索、プラグイン、外部ツールをAI文章作成に自動付与しない。
- 氏名を送る必要がない場合は園児ID等も含めず、匿名化した文脈を送る。
- 健康・発達・家庭情報は、対象機能で本当に必要な項目だけ送る。
- アプリ側では全文ではなく、モデル、トークン、費用、処理時間、対象文書ID、採否等の監査情報を保存する。
- AIへの送信内容をOhana Works側で保存する場合は、業務文書と同等の権限制御を行う。

OpenRouter公式資料では、プロンプト保持はオプトインであり、OpenRouter自身はオプトインしない限りプロンプト・応答を保存しないと説明されている。一方、接続先Providerの保持方針は個別に異なるため、ZDRとProvider制限をリクエスト単位で強制する。

## 4.6 操作フロー

```text
既存記録から根拠候補を取得
→ 職員が使用する記録を確認
→ 箇条書きで補足
→ 用途別プロファイルでAI生成
→ 職員が採用・修正・再生成
→ 主任等が必要に応じて承認
```

補助ボタン：

- 短くする
- やわらかくする
- 具体的にする
- 敬語を整える
- 重複を減らす
- 事実と推測を分ける
- 不適切表現を確認
- この段落だけ再作成

## 4.7 AI監査

保存項目：

- 実行者
- 施設
- 用途
- 文書ID
- モデル
- 実Provider
- プロンプト版
- ZDR適用結果
- フォールバック有無
- 入出力トークン
- 費用
- 実行日時
- 採用・一部採用・不採用
- エラー

APIキーはサーバー側Secretへ保存し、Flutter・ブラウザ・公開リポジトリへ含めない。

## 4.8 AI受入基準

- 用途ごとにGPT系・Claude系を管理者設定で切り替えられる。
- 機微文書はZDR非対応Providerへ送信されない。
- AI障害時に原文や保存済み文章を失わない。
- AI未使用でも手動作成を継続できる。
- AI生成部分と人が確定した文章を追跡できる。
- モデル変更前後の回帰テストができる。
- AIが根拠のない園児情報を追加しない。

# 5. 写真保存・販売

## 5.1 初期範囲

初期実装はデジタル写真の販売を基本とする。

```text
職員撮影
→ 保育業務Webからアップロード
→ 非公開R2へ保存
→ サムネイル・透かし入りプレビュー生成
→ 管理者確認
→ 対象保護者へ販売公開
→ 保護者がカートで選択
→ 決済
→ 購入済み写真のダウンロード権付与
```

プリント写真の配送は初期対象外とし、将来 `delivery_type = physical_print` を追加できる構造にする。

## 5.2 Cloudflare構成

推奨bucket：

```text
ohana-photo-originals-private
ohana-photo-previews-private
ohana-photo-purchased-private
```

または1 bucket内でprefixを分ける。

```text
tenant/{tenant_id}/office/{office_id}/year/{year}/album/{album_id}/original/
tenant/{tenant_id}/office/{office_id}/year/{year}/album/{album_id}/preview/
```

原則：

- bucketを公開しない。
- `r2.dev`で公開しない。
- APIトークンはbucket・操作ごとに最小権限とする。
- アップロードは短時間の署名付きPUT URLを利用する。
- 閲覧・ダウンロードは短時間の署名付きGET URLまたはWorker経由とする。
- CORSはOhana Worksの正式ドメインだけに限定する。
- URLを知っているだけで長期間見られる構造にしない。
- 署名付きURLはBearer tokenとして扱い、有効時間を短くする。

R2は保存データとメタデータを暗号化し、TLS通信を利用できる。販売写真は機微性が高いため、暗号化だけでなくアプリ側の認可が必須である。

## 5.3 アップロード処理

1. 職員の施設・アップロード権限を確認
2. album、撮影日、クラス、行事を選択
3. サーバーがobject keyと署名付きPUT URLを発行
4. 端末からR2へ直接アップロード
5. checksum、容量、MIME、拡張子、画像実体を検証
6. マルウェア・不正ファイル検査
7. EXIF位置情報等を除去
8. サムネイル生成
9. 透かし入りプレビュー生成
10. 職員が園児タグ・公開対象を確認
11. 主任等が公開承認

アップロード途中のファイルは公開対象にしない。

## 5.4 写真の権限

- 保護者は自分の子どもが所属する施設・クラス・対象アルバムだけを閲覧できる。
- 兄弟姉妹がいる世帯は、保護者と各園児の関係を個別に確認する。
- 在籍期間外の写真を自動表示しない。
- 写真掲載・販売同意のない園児が写る写真は販売公開しない。
- 公開同意は園児・用途・期間・範囲ごとに履歴管理する。
- 顔認識による自動識別は初期実装に含めない。
- 園児タグは候補として扱い、職員が確認する。
- 全体行事等で複数園児が写る写真の閲覧範囲は施設方針で設定する。
- 購入前プレビューへ元画像を配信しない。

## 5.5 販売設定

- 1枚価格

- 販売終了後データ
- 購入済みデータ
- 不採用・重複写真

- 返金・紛争中の写真

それぞれの保存期間を設定マスタ化する。R2 Lifecycle Ruleを使用する場合も、購入履歴・紛争・監査上必要なファイルを誤削除しない。

## 5.10 写真販売受入基準

- 未承認写真が保護者へ表示されない。
- 同意のない園児が写る写真を販売公開できない。
- 保護者が他施設・他クラス・他世帯の写真URLを取得できない。
- 購入前に元画像を取得できない。
- Webhook確認前にダウンロード権が付与されない。
- 購入後だけ、短時間のダウンロードURLを発行できる。
- 返金、取消、販売停止、権利取消の履歴が残る。
- R2 APIキーがクライアントへ漏れない。
- EXIF位置情報を購入用・プレビュー用画像から除去できる。

- 請求内容は管理者Webで作成・確認・承認する。

# 7. 決済事業者比較

## 7.1 比較

| 観点 | Stripe | UnivaPay |
|---|---|---|
| 初期導入 | 公開料金で小さく開始しやすい | 審査・契約・個別見積もりを前提に確認が必要 |
| 国内カード | 対応 | 対応 |
| 都度決済 | Checkout/Payment Intents等 | 都度課金、リンク、API等 |
| 定期・継続 | Billing/Subscription、自動回収 | 定期課金、再課金、CSV課金等 |
| 変動月額 | Invoice item等で対応可能 | スポット課金・API・CSV等を契約条件と合わせて確認 |
| 口座振替 | 銀行振込とは別。日本の口座振替要件は要確認 | 紙の振替依頼書等による口座振替を案内 |
| コンビニ | 公開料金・対応情報あり | 対応。条件は見積もり・審査確認 |
| API資料 | 非常に充実 | API、Webhook、冪等リクエスト等の資料あり |
| 保護者用管理 | Customer Portal等 | 提供範囲を契約前に確認 |
| 料金透明性 | 標準料金公開 | 商材・決済方法ごとの個別見積もりが多い |
| Ohana Works初期適合 | 高い | 口座振替重視なら有力 |

## 7.2 Stripe料金の参考

2026-07-30に確認したStripe公式標準料金では、国内カード成功取引は3.6%、コンビニ決済は3.6%（最低120円）、銀行振込等は1.5%と掲載されている。Stripe Billingは取引額の0.7%、Invoicing Starterは支払済み請求書の0.4%と掲載されている。

実装方式により追加料金が変わるため、Ohana Worksで請求計算・請求書管理を行い、Stripeは決済だけに使用する案と、Stripe Billing/Invoicingを利用する案の月額試算を比較する。

# 10. 移行・安全上の注意

- 既存Supabase Storageの写真を一括削除・上書きしない。
- R2移行はchecksumを照合し、DB参照先切替前に復元試験を行う。
- 既存の園児写真と販売写真を同じ公開権限にしない。
- Cloudflare dashboardの個人アカウントだけに依存せず、法人管理、MFA、最小権限、API tokenローテーションを設定する。
- Stripe test modeとlive modeのIDを混在させない。
- Webhook Secretを環境ごとに分離する。
- 既存保護者へ自動決済を無断で適用しない。
- 料金表移行時は、元ExcelとDBマスタを全行照合する。
- 過去請求は当時の料金スナップショットを保持する。
- 写真販売と保育料の売上区分を会計上分ける。
- 決済手数料を保護者へ転嫁するかは、規約・法令・決済事業者条件を確認し、勝手に加算しない。
- 返金済みでも会計・監査用の注文履歴を物理削除しない。
- OpenRouterのモデル・Providerを価格だけで自動選択しない。
- AI入力・出力ログを外部サービスへ重ねて送信しない。

- Webhookを署名検証せず処理しない。
- カード情報をDBやログへ保存しない。
- 料金をソースコードへ固定しない。
- 発行済み請求書を上書きしない。
- AIで請求金額を計算・決定しない。

# 14. 共通文書基盤の追加方針

## 14.1 結論

雇用契約書、労働条件通知書、職員向け規程・同意・申請、入園利用契約書、各種同意書、申込書、児童票を、画面ごとに個別実装してはならない。

次の共通基盤を先に設ける。

```text
文書テンプレート
  ├─ 適用施設・対象者・有効期間
  ├─ 入力項目定義
  ├─ 自動入力元
  ├─ 必須・条件付きルール
  ├─ 承認・同意方法
  ├─ PDFレイアウト
  ├─ 文書版・条文版
  └─ 保存・再同意ルール
          ↓
文書案件
  ├─ 対象職員／園児／保護者
  ├─ 回答・契約条件
  ├─ 作成・確認・承認
  ├─ 署名／同意証跡
  ├─ 確定PDF
  └─ 変更・再発行履歴
```

共通文書基盤は、雇用・入園・同意・児童票に加え、将来の誓約書、休職・復職通知、料金改定同意、健康情報更新、行政提出書類にも再利用できる構造とする。

## 14.2 文書の実行方式

テンプレートごとに、次のいずれかを設定する。

| 方式 | 用途 |
|---|---|
| `information_only` | 閲覧のみ |
| `policy_read_receipt` | 規程・方針の周知と既読確認。契約同意とは区別する |
| `electronic_acknowledgement` | 内容確認と同意回答を記録 |
| `electronic_signature` | 電子署名サービス等を用いる契約 |
| `paper_signature_required` | A4印刷、署名・押印、受領確認 |
| `electronic_or_paper` | 施設判断で電子または紙を選択 |
| `data_submission` | 児童票、申込書、届出書等の情報提出 |
| `application_approval` | 申請、証憑、会社承認、有効期限を管理 |

画面上のチェックボックスだけを、すべての契約書について一律に「電子署名」と呼んではならない。規程を読んだ記録、任意同意、申請・許可、法定通知、契約締結は、それぞれ別の証跡と状態を持たせる。契約の性質、本人確認方法、法的リスクに応じて方式を分ける。

## 14.3 共通原則

- PDFはA4を基本とし、画面表示・ダウンロード・印刷のすべてに対応する。
- 確定時点の入力値、条文、料金、文書版をスナップショットとして保存する。
- 確定済み文書を上書きしない。訂正・更新は新しい版として作成する。
- 文書本文と回答項目を別管理し、本文改定後も当時の同意内容を再現できるようにする。
- 日時はサーバー時刻で保存する。
- 本人・対象・施設・文書版・PDFハッシュ・同意回答を監査ログへ記録する。
- 添付・PDFは非公開Storageへ保存し、短時間の署名付きURLで取得させる。
- 原文テンプレートは管理者が承認した版だけを本番利用する。
- AIが契約条件、料金、法定項目、同意の意味を勝手に変更してはならない。

# 15. 労務・雇用文書・職員同意管理

## 15.1 結論

雇用契約書だけを職員マスタから差し込み生成する機能にはしない。次の4つを分離した「職員入社・契約手続き基盤」として再設計する。

```text
労働条件データ
  ├─ 雇用契約書
  └─ 労働条件通知書

規程・方針
  └─ 配布、閲覧、既読確認

契約・同意・申請
  └─ 対象者判定、電子同意／署名、紙提出

法令・労使協定・会社承認
  └─ 条件検証、本番利用可否
```

重要な区分：

| 文書の性質 | 推奨方式 | 例 |
|---|---|---|
| 労使双方の契約 | 電子署名または紙署名 | 雇用契約書 |
| 使用者からの法定通知 | 職員の希望に基づく電子交付または紙交付 | 労働条件通知書 |
| 社内規程の周知 | 閲覧・既読確認 | 就業規則、賃金規程等 |
| 任意の同意 | 項目別の明示同意 | 職員写真・SNS利用 |
| 条件付き契約・確認 | 対象者判定後に電子署名または紙署名 | 自社保育園利用、短時間勤務 |
| 申請・許可 | 申請、証憑、承認、有効期限 | 自転車通勤 |
| 制度加入同意 | 制度説明、明示同意 | 中退共 |
| 高機密法定手続き | 専用権限・専用フロー | こども性暴力防止法に基づく犯罪事実確認 |

「同意する」ボタンを全書類へ共通使用し、すべてを電子契約扱いにしてはならない。

## 15.2 添付規程の適用関係

規程は、文書名だけでなく雇用区分、適用開始日、終了日、対象施設、事業場、承認状態を持つ。

添付規程のうち2026年8月1日施行のものは、施行日前には `scheduled` とし、2026年7月31日以前の雇用条件へ遡って自動適用しない。施行日前に締結・更新する契約を作成する場合は、その時点で有効な旧規程版も登録し、適用日から正しい版を選択する。

初期整理：

| 規程 | 主な対象 | 契約生成での利用 |
|---|---|---|
| 就業規則（2026.8.1改訂） | 無期雇用の正職員 | 労働時間、配置、休日、服務、定年等 |
| パートタイマー就業規則（2026.8.1） | 有期かつ短時間のパート職員 | 契約期間、更新、勤務、服務等 |
| 賃金規程 | 規程本文上は正職員 | 賃金項目、締日・支払日、手当、賞与等 |
| 育児・介護休業規程 | 全職員 | 育児・介護制度の案内 |
| ハラスメント防止規程 | 正職員、パート、有期、派遣等 | 禁止事項、相談窓口の周知 |
| 再雇用規程 | 定年退職後の再雇用者 | 有期再雇用契約 |
| 退職金規程 | 正職員 | 中退共加入条件、掛金等 |
| 文書管理規程 | 役員・全職員 | 文書、電磁的記録、持出し、廃棄等 |

同一人物に適用される規程セットを `employment_rule_set` として確定し、そのIDと各規程版を雇用文書へ記録する。

初期ルールセット例：

```text
regular_employee
fixed_term_full_time
part_time_fixed_term
part_time_indefinite
reemployed_employee
spot_support_worker
temporary_agency_worker
```

現在の規程だけでは `有期フルタイム`、`無期パート`、`スポット支援員` の適用規程が明確でない可能性がある。Claude Codeは名称から推測せず、専門家と法人管理者の確認が終わるまで該当テンプレートを本番利用不可にする。

## 15.3 規程・現行書式の要確認事項

次は、契約自動生成前に解消する。システムが条文を自動修正してはならない。

### 15.3.1 育児・介護休業規程

- 第8条が重複している。
- 第13条が重複している。
- 子の看護等休暇の対象が「小学校就学前」となっているが、2025年4月以降の制度では小学3年生修了までへ拡大されている。
- 2025年10月施行の柔軟な働き方を実現するための措置、個別周知・意向確認等との整合確認が必要である。
- 取得日数、時間単位、対象除外、申出方法等を最新モデル規程と照合する必要がある。

対応：

```text
legal_review_status = blocked
production_use = false
```

修正版が専門家承認されるまで、この規程本文を職員へ「法令対応済み最新版」と表示してはならない。

### 15.3.2 賃金規程とパートタイマー就業規則

- 賃金規程第2条は正職員へ適用するとしている。
- 一方で、賃金規程第10条第3項はパートタイマー職員の調整手当を定めている。
- パートタイマー就業規則第12条は、賃金規程を参照している。
- 自転車通勤時の100円／200円支給は、公共交通機関の実費を定める賃金規程第12条だけでは説明しきれない。

対応案：

1. 賃金規程の適用範囲を全職員へ整理し、雇用区分別条項を設ける。
2. または正職員賃金規程とパートタイマー賃金規程を分離する。

どちらかを専門家と決定するまで、パート向け契約へ賃金規程の条文を自動引用しない。

### 15.3.3 1年単位の変形労働時間制

就業規則への記載だけで適用済みと判定してはならない。事業場ごとに、労使協定、労働基準監督署への届出、対象期間、対象者、年間勤務カレンダー、有効期間を確認する。

雇用文書へ「1年単位の変形労働時間制」と表示できる条件：

```text
active_labor_management_agreement == true
AND agreement_type == annual_variable_working_hours
AND employee_is_in_scope == true
AND employment_start_date is within agreement_effective_period
```

### 15.3.4 退職金規程

- 中退共への追加加入では、対象従業員の同意取得が案内されている。
- 原則全員加入と、規程上の正職員限定との関係を確認する。
- 産前産後休業、育児休業、介護休業等を理由とする掛金停止条項が、中退共の取扱いと不利益取扱い禁止に整合するか、専門家・中退共へ確認する。
- 中退共制度による退職金の減額・不支給申出の条件を、システムが自動判定してはならない。

### 15.3.5 入社時誓約書

- 守秘義務、提出書類の真実性、反社会的勢力排除、情報セキュリティ等は入社時確認に適する。
- 「健康状態の申告」は、必要な配慮・安全確保に必要な最小限へ限定し、病歴の包括申告や差別的取扱いにつながらない設計にする。
- 性犯罪前科の自己申告欄は、2026年12月25日施行のこども性暴力防止法に基づく正式な犯罪事実確認とは別であり、自己申告だけで法定確認を完了扱いにしてはならない。
- 犯罪事実確認情報は通常の職員マスタ、誓約書PDF、一般監査ログへ保存せず、専用の情報管理規程・専用権限・保存制御へ分離する。
- 私的LINE等を例外許可する現行条項は、Ohana Worksの個別連絡・グループ連絡の正式運用開始時に見直す。

### 15.3.6 自転車通勤同意書

- 神奈川県では自転車損害賠償責任保険等への加入が義務付けられているため、保険の種類、証券番号等、保険期間、証憑、更新期限を管理する。
- 「事故やトラブルは自己責任」とする文言を、通勤災害や会社の法的責任まで一律に排除する免責として扱ってはならない。
- 労災保険上の通勤災害該当性は、同意書で放棄させられるものとして設計しない。
- 通勤手当100円／200円の適用根拠、時間判定、会社駐輪場利用時の不支給を賃金規程または通勤手当規程と一致させる。

### 15.3.7 自社保育園利用・短時間勤務

- 自社保育園の利用契約と雇用契約を、一つの包括同意に混在させない。
- 保育料、実費、休業中利用、ダブルワーク時の費用等は、有効期間付きの料金ルールとして管理する。
- 園間転園、退職時退園等の条項は、保護者向け利用契約、児童の利益、自治体・助成制度上の要件と整合確認する。
- お子さまの卒園を契機に雇用条件を協議することと、雇用契約が当然に終了することは別である。
- 卒園だけを理由に自動退職・自動雇止めにしてはならない。
- 有期契約とする場合は、契約期間、更新基準、更新上限、雇止めルールを雇用契約書・労働条件通知書へ明示する。
- 無期契約の場合、将来の労働条件変更は一方的に確定せず、協議・合意・合理的な就業規則変更等の法的手続を前提とする。

### 15.3.8 スポット支援員契約

- 勤務日、勤務時間、賃金額を勤務後に決める運用にしてはならない。
- 各勤務の開始前に、日時、場所、業務、休憩、賃金、交通費、支払日等を明示し、本人が承諾した記録を持つ。
- 求人・依頼への応募時点で契約が成立する場合があるため、取消し、休業手当、条件変更の取扱いを事前に確定する。
- 学生等が18歳未満の場合は、年齢証明、深夜業、時間外・休日労働等の制限を検証する。
- 日払いは例外機能とし、現金受領記録だけで給与台帳・源泉・労災・雇用管理を省略してはならない。

推奨：初期リリースでは機能フラグをOFFにし、通常雇用文書が安定した後に実装する。

```text
spot_employment_enabled = false
```

## 15.4 雇用契約書と労働条件通知書

### 15.4.1 共通条件から別文書を生成

一つの承認済み `employment_condition_version` から、次を別々に生成する。

#### 雇用契約書

- 労使双方が合意する契約文書
- 会社側署名と職員側署名を持つ
- 電子署名または紙署名
- 双方が同一内容を保有できる

#### 労働条件通知書

- 使用者から職員への法定明示文書
- 通知日、使用者、職員、法定明示事項を持つ
- 職員が電子交付を希望した場合は、職員アプリでPDFを閲覧・保存・印刷できる
- 電子交付を希望しない場合は紙で交付する

文書名だけを置換して同一PDFを使い回さない。労働条件の値は一致させるが、署名、説明、通知欄は文書種別ごとに持つ。

### 15.4.2 雇用区分別テンプレート

少なくとも次を分ける。

```text
regular_indefinite
fixed_term_full_time
part_time_fixed_term
part_time_indefinite
reemployment_fixed_term
spot_day_or_assignment
```

派遣職員はOhanaが雇用主ではない場合があるため、Ohanaの雇用契約生成対象へ含めず、派遣元との契約・就業条件明示・受入書類を別モジュールで管理する。

### 15.4.3 必須データ

職員マスタ等から自動入力する。

| 区分 | 項目 |
|---|---|
| 本人 | 職員ID、氏名、ふりがな、住所、生年月日、入社日 |
| 雇用 | 雇用区分、無期／有期、契約開始・終了、試用期間、更新の有無・基準・上限 |
| 配属 | 雇入れ直後の就業場所、変更の範囲、主所属、兼務先 |
| 職務 | 雇入れ直後の業務、変更の範囲、職種、役職 |
| 時間 | 始業・終業、シフト、所定日数、週所定時間、休憩、時間外の有無 |
| 休日休暇 | 休日、法定休日、年休、特別休暇、変形労働時間制 |
| 賃金 | 月給／時給／日給、基本給、各手当、割増率、締日、支払日、支払方法 |
| 待遇 | 昇給、賞与、退職手当の有無 |
| 保険 | 社会保険、雇用保険の適用予定 |
| 相談 | パート・有期雇用管理の相談窓口、ハラスメント窓口 |
| 規程 | 適用規程セット、規程版、閲覧方法 |
| 法令 | 無期転換申込機会、無期転換後条件、説明対象 |

マイナンバー、扶養家族のマイナンバー、銀行口座番号、犯罪事実確認内容を契約書へ自動掲載しない。

### 15.4.4 2026年10月1日対応

短時間・有期雇用労働者について、2026年10月1日以降に使用する通知書版では、通常の労働者との待遇差について説明を求められる旨を含む、施行時点の最新モデル様式と照合する。

テンプレートは次のように有効期間を分ける。

```text
part_time_notice_2024
  effective_to = 2026-09-30

part_time_notice_2026_10
  effective_from = 2026-10-01
```

契約日・更新日が境界をまたぐ場合、作成日時ではなく、法令上の明示タイミングと適用日を基準にテンプレート版を決定する。

### 15.4.5 不整合検査

確定前に少なくとも次を検査する。

- 雇用区分と適用就業規則。
- 賃金区分と賃金規程。
- 最低賃金。
- 法定時間外、法定休日、深夜、月60時間超の割増率。
- 週所定時間と社会保険・雇用保険設定。
- 契約期間と更新上限。
- 無期転換申込機会。
- 変形労働時間制の有効な労使協定。
- 契約書と通知書の条件一致。
- 通勤手当と通勤申請。
- 退職手当の有無と中退共対象。

自動検査合格は法的承認を意味しない。

## 15.6 電子交付・電子署名・紙の使い分け

### 労働条件通知書

職員が電子交付を希望した記録を取得し、PDFを端末へ保存・印刷できるようにする。

記録：

- 希望する交付方法
- 希望取得日時
- 取得画面・文言の版
- 本人アカウント
- 公開日時
- 初回閲覧日時
- ダウンロード日時
- 紙交付日
- 交付担当者
- PDFハッシュ

電子交付を希望しない人へアプリ公開だけで完了扱いにしてはならない。

### 雇用契約書・協定書

高い証拠力が必要な文書は、認証済みアカウントのチェックボックスだけでなく、採用する電子署名サービスまたは紙署名を使用する。

電子署名サービス未導入時：

```text
paper_signature_required
```

とし、A4 PDF出力、署名済み原本受領、スキャン、原本保管場所を記録する。

### 規程・方針

就業規則等は原則として「同意」ではなく「周知・閲覧・既読確認」とする。職員の同意によって法令や規程の有効性を作り出す設計にしない。

### 出力形式

| 形式 | 用途 |
|---|---|
| A4 PDF | 職員交付、署名対象、確定版、印刷 |
| DOCX | 労務担当・専門家が承認前テンプレートを編集する場合に限定 |
| XLSX | 対象者、進捗、不足、期限等の一覧出力 |
| 紙 | 紙署名が必要または本人が紙交付を希望する場合 |
| スキャンPDF | 署名済み紙原本の参照用控え |

確定済み文書の正本をExcelで管理しない。DOCXを確定版として職員へ配信せず、承認済みテンプレートと条件スナップショットから生成したPDFを交付版とする。紙原本が正本となる手続きでは、スキャンPDFだけで原本を廃棄しない。

## 15.8 入社時誓約書

既存誓約書を一枚の包括同意にせず、次を分離して記録する。

### 誓約本文

- 就業規則・合理的な業務指示の遵守
- 提出書類の正確性
- 守秘義務
- 個人情報・業務データの適正利用
- 反社会的勢力との関係不存在

- 会社指定の業務連絡手段

## 15.10 託児利用を伴う短時間勤務の条件確認


対象条件：

```text
uses_company_nursery == true
AND short_time_work_arrangement == true
AND special_employment_condition_confirmation_required == true
```

記載内容：

- 自社託児を利用しながら短時間勤務すること
- 現在の勤務日数・時間
- 子どもの在園予定期間
- 卒園・転園等の前に勤務条件を協議する時期
- 協議候補となる勤務日数・時間

次を実装してはならない。

- 卒園日に自動退職処理する。
- 条件変更を自動適用する。
- この確認書だけで将来の解雇・雇止めに同意済みとする。

入力：

- 距離・所要時間
- 利用自転車情報
- 利用駐輪場
- 会社駐輪場の利用希望
- 自転車保険の加入有無
- 保険会社・保険種類
- 証券番号等

## 15.14 職員写真・動画・SNS利用同意

職員本人を識別できる写真は個人情報に該当し得る。不特定多数が閲覧するWebサイト、SNS、広告、採用広報等では、利用目的を明示し、職員本人の用途別同意を取得する。

既存職員を含む全職員を対象に、新規同意を取り直す。

### 用途別回答

少なくとも次を分ける。

| 用途 | 回答 |
|---|---|
| 社内職員プロフィール | 許可／顔を隠せば許可／不許可 |
| 職員・保護者限定アプリ | 許可／顔を隠せば許可／不許可 |
| 園内掲示・保護者限定配布物 | 許可／顔を隠せば許可／不許可 |
| 法人・園Webサイト | 許可／顔を隠せば許可／不許可 |
| 法人・園の公式SNS | 許可／顔を隠せば許可／不許可 |
| 採用サイト・求人広告 | 許可／顔を隠せば許可／不許可 |
| パンフレット・印刷物 | 許可／顔を隠せば許可／不許可 |
| 研修・講演・外部発表 | 許可／顔を隠せば許可／不許可 |
| 動画・音声 | 許可／限定条件付き許可／不許可 |
| 氏名・役職の併記 | 許可／役職のみ／不許可 |

媒体、利用目的、公開範囲、利用期間、加工、第三者提供、委託先、撤回方法を表示する。

### 原則

- 同意しないことを採用・配置・評価・賃金上の不利益へつなげない。
- 未回答を許可扱いにしない。
- 新しい用途へ流用しない。
- SNSごとに一括同意ではなく、少なくとも公開SNS群と採用広報を分ける。
- 撤回後は将来の新規公開を停止する。
- 印刷済み配布物、既に第三者が保存・共有したSNS等から完全回収できない場合があることを事前説明する。
- 退職時に公開継続・削除・差替えを確認する。
- 写真管理機能と連携し、不許可または未回答の職員が写る写真を公開候補から除外する。
- 顔認識だけで人物・同意を確定せず、公開前に人が確認する。

### 職員アプリ表示文案

次を法務確認用の初期文案とし、承認前に本番表示しない。

```text
職員の写真・動画・音声・氏名等の利用について

株式会社Ohanaは、園内での情報共有、保護者への活動報告、法人・園の広報、
採用活動、研修等のため、職員が写っている写真・動画、職員の音声、氏名、
役職等を利用する場合があります。

利用を希望する範囲を、用途ごとに選択してください。
同意は任意であり、同意しないことによって、採用、配置、評価、賃金その他の
労働条件について不利益な取扱いを受けることはありません。

同意した内容は、職員アプリから将来に向かって撤回できます。
撤回後は新しい掲載・公開を停止し、会社が管理できる媒体について削除または
差替えを検討します。ただし、既に配布した印刷物、第三者が保存・共有した
SNS投稿等については、完全に回収・削除できない場合があります。

新しい媒体・目的で利用する場合は、現在の同意範囲に含まれるかを確認し、
含まれない場合は改めて同意を求めます。
```

同意画面には、対象となる公式Webサイト・SNSアカウント・採用媒体、利用期間、問合せ・撤回窓口を具体的に表示する。

### 同意証跡

- 同意者
- 本人アカウント
- 同意項目
- 同意日時
- 文書版
- 有効開始日・終了日
- 撤回日
- 撤回後の対応
- 公開済みコンテンツとの関連

# 16. 入園利用契約・同意・提出書類管理

## 16.1 推奨する保護者向け構成

ファイル単位で毎回署名・同意させる方式ではなく、「入園手続きパッケージ」として案内する。

ただし、法的性質が異なる文書を1つの同意に混ぜない。次の3群に分ける。

### A. 契約

- BABY MAHALO利用契約書
- 月極保育契約利用時間個別契約書

契約内容、料金プラン、利用時間を個別に確認し、契約単位の実行記録を持つ。

### B. 全員提出・全員確認

- 入園の同意
- 園児専用バス利用に関する同意
- 肖像権・写真・動画利用に関する回答
- 教材申込
- 児童票

各章を順番に確認し、必要な個別回答を完了した後、最後に一括提出する。すべてを1個の包括同意チェックだけで済ませてはならない。

### C. 条件付き

- 自動車利用届
- 地域枠かつ弾力運用入園者の必要書類
- 将来追加される個別対象書類

最初に「該当する／該当しない／分からない」を必須回答とする。「分からない」は未提出扱いにせず、園側確認タスクを生成する。

## 16.2 適用ルール

```text
all
conditional
compound_conditional
staff_assigned
```

添付資料の初期設定：

| 文書 | 適用 | 完了条件 |
|---|---|---|
| BABY MAHALO利用契約書 | 全員 | 契約確認・実行 |
| 月極保育契約利用時間個別契約書 | 月極利用者 | プラン・利用時間・料金確認・実行 |
| 入園の同意 | 全員 | 個別項目確認と最終同意 |
| 園児専用バス同意 | 全員 | 全項目確認と回答 |
| 肖像権承諾 | 全員 | 用途別の許可・不許可を全項目回答 |
| 教材申込 | 全員 | 各品目の数量確認、0個を含む明示回答 |
| 児童票 | 全員 | 必須項目入力、保護者提出、園確認 |
| 自動車利用届 | 該当者 | 該当有無を必須回答。該当時は車両情報提出 |
| 地域枠・弾力運用必要書類 | 地域枠かつ弾力運用 | 条件判定、同意、必要書類提出、園確認 |

`地域枠・弾力運用` は、次のAND条件とする。

```text
admission_slot_type == "regional"
AND
flexible_operation_admission == true
```

保護者回答だけで適用を確定せず、園児の入園区分マスタと園職員の確認を組み合わせる。

## 16.3 保護者アプリの操作

```text
入園手続き
  ├─ 進捗
  ├─ 契約
  ├─ 同意・確認
  ├─ 条件付き書類
  ├─ 教材申込
  ├─ 児童票
  └─ 提出内容・確定PDF
```

要件：

- 未完了件数を表示する。
- 途中保存・再開に対応する。
- 園児マスタの氏名、生年月日、施設、クラス、保護者情報を自動入力する。
- 同じ情報を複数文書で再入力させない。
- 契約本文は見出しと要点を先に表示し、全文PDFも閲覧できるようにする。
- 重要な独立項目は個別チェックまたは選択回答を必須とする。
- 未回答、該当判定未確定、必須添付不足のまま最終提出できない。
- 提出前に回答一覧を確認できる。
- 提出後は保護者が確定PDFと回答内容を保存できる。

## 16.4 肖像権・写真販売同意

現行書式の一括承諾方式を分解し、少なくとも次を用途別に回答させる。

- 園内掲示
- 園のWebサイト
- 園のSNS
- 行事・発表会等の配布資料
- 保護者限定のクラス写真共有
- 保護者向け写真販売
- 動画利用
- 広告・採用広報

各項目は `許可する／許可しない` を必須回答とする。1項目の不許可を他用途の許可と解釈してはならない。

添付の現行書式には、全体を「承諾しない」とした場合でも保護者限定販売システムへ掲載すると読める箇所がある。新システムでは、この矛盾を解消し、`photo_sales_consent == granted` の園児だけを写真販売の公開対象判定に使用する。

複数園児が写る写真は、写っている全園児の該当用途の同意が有効な場合だけ公開候補とする。顔認識だけで自動確定せず、職員の目視確認を必須とする。

## 16.5 バス同意

少なくとも次を独立した確認項目として記録する。

- 園児専用バスの利用
- 園外活動時の利用
- 状況により事前予告なく利用する可能性
- 体調不良時の参加見合わせ・迎え依頼
- 緊急時の職員車両利用に関する説明
- 車両、安全管理、保険内容の説明確認

添付文書の「保険補償以外を請求しない」趣旨の条項は、システムが有効性を判断してはならない。弁護士・保険会社による確認前は、旧文面を自動的に本番テンプレートへ採用しない。

## 16.6 入園同意

添付書式をもとに、少なくとも次を章単位で確認する。

- 重要事項説明、利用料、実費負担
- 小学校その他関係機関との必要最小限の情報共有
- 防犯カメラ
- 緊急連絡・医療受診
- 災害時対応
- 園内での勧誘・販売・威圧的行為等の禁止
- 職員への暴言、脅迫、威圧行為等への対応
- 規則違反時の継続利用判断

同意が任意である項目と、施設利用契約上の確認事項を画面上で区別する。すべてを同じ「同意する」ラベルにしない。

## 16.7 月極個別契約と請求機能の連携

個別契約で選択した次を、請求システムの契約プランマスタと同一IDで管理する。

- 契約プラン
- 利用可能時間
- 基本料金
- 延長料金
- 適用開始月
- 適用終了月
- 月途中変更の可否
- 上限額ルール

契約PDFへ料金表を直接固定値で埋め込むのではなく、承認済み料金プラン版のスナップショットを使用する。

添付の2022年改定利用契約書には「毎月5日頃請求、15日までに支払う」とする記載がある一方、最新の請求構想では「請求日から1週間以内」とされている。契約テンプレートを本番化する前に、正式な支払期限を確定し、契約・請求書・督促ロジックを一致させる。

- 入所保留通知書
- 毎月の提出状況
- 毎年4月の必須提出
- 未提出時の案内

月次提出が必要な書類は、1回の入園時同意だけで完了扱いにしない。対象月ごとのタスクを生成する。

園職員は、次を確認・訂正できる。

- 地域枠判定
- 弾力運用判定
- 適用開始日・終了日
- 書類の有効期間
- 提出済み・不足・差戻し
- 例外理由

## 16.11 同意証跡

最終提出時に次を保存する。

- 同意案件ID
- 園児ID
- 保護者ID
- 保護者氏名
- 園児との続柄
- 認証済みアカウントID
- 文書テンプレートID・版
- 表示した本文のハッシュ
- 各チェック・各回答
- 同意・提出日時
- 端末・OS・アプリ版
- IPアドレス等の技術情報
- 確定PDFの保存先とハッシュ
- 取消、更新、再同意履歴

タップ画像や署名画像だけを本人性の唯一の根拠にしない。アカウント認証、操作記録、確定本文、回答内容を組み合わせる。

## 16.12 管理者・保育業務Web

# 17. 園児マスタ「児童票」機能

## 17.1 目的・基本方針

保護者アプリの園児マスタ内に「児童票」タブを追加し、添付の4ページ構成の児童票を入力・提出できるようにする。提出内容は保育業務Webで確認、差戻し、受理、PDF出力できるものとする。

紙の4ページをそのまま縦長画面へ置き換えてはならない。次を基本方針とする。

- 園児・保護者マスタにある情報は再入力させない。
- 排他的な回答にはラジオボタンを使用する。
- 複数該当する回答にはチェックボックスを使用する。
- `あり／なし／分からない` を先に選び、必要なときだけ詳細欄を表示する。
- 自由記述は、選択式で表現できない内容に限定する。
- 年齢に応じて質問を出し分ける。
- すべての画面で途中保存できる。
- 保護者欄と園職員欄を画面・API・DBで分離する。
- 保護者が確定版を直接上書きしない。変更は履歴を残す。

入力画面の設計目標は、特記事項が少ない家庭であれば、マスタ情報の確認を含めて短時間で提出できることとする。ただし、入力時間短縮のために健康・安全上必要な情報を省略してはならない。

## 17.2 画面配置

```text
保護者アプリ
  └─ 園児
      ├─ 基本情報
      ├─ 児童票
      │   ├─ 入力を始める／続きから
      │   ├─ 進捗
      │   ├─ 未回答一覧
      │   ├─ 提出内容確認
      │   └─ 提出済み・過去版
      └─ 提出書類

保育業務Web
  └─ 園児管理
      └─ 児童票
          ├─ 未提出
          ├─ 入力中
          ├─ 確認待ち
          ├─ 差戻し
          ├─ 受理済み
          ├─ 変更申請
          └─ 年次確認待ち
```

保護者アプリの児童票トップには、次を表示する。

- 対象園児
- 提出期限
- 現在の状態
- 完了したセクション数
- 残りの必須項目数
- 最終保存日時
- `入力を続ける` ボタン
- 園からの差戻しメッセージ

## 17.3 入力ステップ

スマートフォンでは次の7ステップに再編する。

```text
1. 基本情報の確認
2. 家族・送迎・通園
3. 出生・発達
4. 健康・医療
5. 食事・睡眠・生活
6. お子さまの様子・園への希望
7. 内容確認・提出
```

各ステップはカード単位で表示し、現在位置と完了状況を常に確認できるようにする。

## 17.4 自動入力と確認方式

次は既存マスタから自動表示し、保護者は原則として `この内容で正しい` を確認するだけとする。

| 自動入力項目 | 入力元 |
|---|---|
| 園児氏名・ふりがな・愛称 | 園児マスタ |
| 生年月日・性別 | 園児マスタ |
| 入園施設・クラス | 在籍・クラス履歴 |
| 保護者氏名・続柄 | 保護者／園児関係マスタ |
| 住所・郵便番号・電話番号 | 世帯・保護者マスタ |
| 通常送迎者・代理送迎者 | 送迎許可者マスタ |
| 同居家族 | 世帯構成マスタ |
| 通園方法 | 登園設定 |
| かかりつけ医 | 医療・緊急情報マスタ |
| 健康保険情報 | 登録済み健康情報 |

自動入力欄には、`園児マスタから表示` 等の出典を表示する。

誤りがある場合は、児童票内だけを変更させず、`基本情報の変更を申請` へ誘導する。変更申請中は、児童票には申請値を候補表示し、園確認後に正式マスタへ反映する。

兄弟姉妹が在籍している場合は、次を保護者が確認したうえでコピーできる。

- 住所
- 同居家族
- 保護者連絡先
- かかりつけ医
- 通園方法

健康・発達・アレルギー・予防接種・性格等、園児固有の情報は兄弟姉妹から自動コピーしない。

## 17.5 ステップ1：基本情報の確認

表示項目：

- 氏名
- ふりがな
- 愛称
- 生年月日
- 性別
- 血液型
- 保護者
- 住所
- 連絡先
- 健康保険

入力方法：

| 項目 | UI |
|---|---|
| 血液型 | `A／B／O／AB／不明` のラジオボタン |
| 健康保険種別 | `社保／国保／共済／その他／分からない` |
| 記号・番号 | 必要な場合のみ文字入力。通常表示ではマスクする |
| 保険者名 | 登録済み候補＋その他 |

FAXは添付原票にあるが、現在の運用上必要かを確認し、初期実装では任意項目とする。

## 17.6 ステップ2：家族・送迎・通園

### 送迎

- 通常の送り担当
- 通常の迎え担当
- 代理送迎者
- 園児との続柄
- 連絡先

通常・代理送迎者は保護者マスタまたは送迎許可者マスタから選択する。新規人物だけ追加フォームを表示する。

### 通園

通園方法は複数選択可能とする。

```text
□ 徒歩
□ 自転車
□ 自動車
□ バス
□ 電車
□ その他
```

所要時間は、時間と分を別欄にせず、`約○分` の数値入力を基本とする。

自動車を選択した場合は、入園書類の「自動車利用届」の該当判定と連動する。

### かかりつけ医

- 病院名
- 診療科
- 電話番号

### 家族・同居人

繰り返し入力形式とする。

- 氏名・ふりがな
- 続柄
- 生年月日
- 職業・学校
- 同居・別居

## 17.7 ステップ3：出生・発達

### 出生時

| 項目 | UI |
|---|---|
| 妊娠期間 | 週数の数値入力。分からないを選択可能 |
| 出生順位 | 第○子 |
| 出生時身長 | cm |
| 出生時体重 | gを基本とする |
| 特別な所見 | `なし／あり／分からない` |
| 所見詳細 | `あり` の場合だけ表示 |

添付原票には出生時体重の単位が `cm` と読める箇所があるため、システムでは `g` とし、最終帳票テンプレートも修正する。

保護者の年齢は、業務上の必要性を再確認する。保持する場合も任意項目とし、未入力を理由に提出を妨げない。

### 発達

次を月齢または年齢で入力する。

- 卒乳
- 離乳食開始・完了
- 首すわり
- おすわり
- はいはい
- 歯の生え始め
- 発語
- 歩き始め

各項目には次の選択肢を持たせる。

```text
○歳○か月
まだ
覚えていない／分からない
該当しない
```

発達時期の入力値だけを理由に、システムが診断・異常判定を行ってはならない。

## 17.8 ステップ4：健康・医療

### 健診

添付原票の健診項目をチェック式で表示する。

- 4か月
- 8か月
- 1歳6か月一般
- 1歳6か月歯科
- 3歳6か月
- その他

各項目は `受診済み／未受診／対象前／分からない` とする。

### 既往歴

最初に次を回答する。

```text
これまでに大きな病気・繰り返す病気がある
  ○ ない
  ○ ある
  ○ 分からない
```

`ある` の場合だけ、病名を複数選択し、必要に応じて発症日・最終発症日・現在の配慮を入力する。

添付原票の病名一覧をコードへ固定しない。既往歴マスタとして管理し、医学用語・誤記・旧称を運用責任者が確認できるようにする。

### けいれん・脱臼・アレルギー

| 項目 | 最初の回答 | 条件付き詳細 |
|---|---|---|
| けいれん | なし／あり／分からない | 時期、熱性か、対応方法 |
| 脱臼 | なし／あり／分からない | 部位、最終時期、配慮 |
| アレルギー | なし／あり／検査中／分からない | 原因、症状、診断、緊急対応 |

アレルギーが `あり` または `検査中` の場合は、園側へ重要確認アラートを生成する。ただし、児童票だけで給食提供可否を自動決定しない。医師の指示書等の別書類と連携する。

### 予防接種

予防接種は、ワクチンマスタから表示し、次を管理する。

- 未接種
- 接種済み
- 回数
- 最終接種日
- 分からない

添付原票のワクチン名を固定せず、年度・制度変更に対応できるマスタ方式とする。

### 平熱・現在の状態

- 平熱：小数1桁の摂氏入力
- 現在治療中の病気
- 服薬
- 日常生活上の配慮

入力値の単位を明示し、不自然な値は保存を禁止せず確認メッセージを表示する。

## 17.9 ステップ5：食事・睡眠・生活

園児の年齢と回答に応じて、乳児向け・幼児向けを出し分ける。

### 乳児向け食事

- 授乳回数
- 1日の目安量
- 夜間授乳の有無
- 粉ミルク名
- 離乳食の段階
- 食べたことがある食品群

食品群は次のチェック式を基本とし、詳細だけ任意入力とする。

```text
□ 穀類
□ 野菜・果物
□ 魚
□ 肉
□ 卵
□ 豆・豆製品
□ 乳製品
□ その他
```

### 幼児向け食事

| 項目 | UI |
|---|---|
| 食べ方 | 自分で／手伝ってもらう／両方 |
| 使用するもの | スプーン、フォーク、箸、手づかみのチェック |
| 食事中の様子 | 集中する／遊び食べがある／その他 |
| 食事量 | 多い／普通／少ない／日による |
| 好きな食べ物 | 任意入力 |
| 苦手な食べ物 | 任意入力 |
| おやつ | 時間を決める／要求に応じる／ほとんど与えない／その他 |

### 睡眠

- 起床・就寝時刻：時刻選択
- 昼寝：する／時々する／しない
- 寝方：仰向け／横向き／うつ伏せ／一人寝／添い寝／その他

複数該当しうる寝方はチェックボックスとする。

### 排泄・清潔・着脱

次はラジオボタンまたはチェックボックスで回答する。

- おむつの使用状況
- 大便を自分でできるか
- 後始末
- 排泄の知らせ方
- 手洗い、洗顔、うがい、歯みがき、鼻をかむ
- 自分で着られる衣類
- 自分で脱げる衣類

能力を単純な `できる／できない` だけにせず、必要な項目には `一部手伝いが必要／練習中` を追加する。

### 言語・社会性・遊び

- 話し方：明瞭／不明瞭／単語中心／どもりがある／その他
- 人見知り：する／時々する／しない
- 遊び方：友達／一人／大人／いずれも
- 好きな遊び
- 好きなおもちゃ

## 17.10 ステップ6：お子さまの様子・園への希望

自由記述は次の5項目に整理する。

1. これまで主に養育した方・生育環境
2. お子さまの良いところ・得意なこと
3. 困っていること・気になる癖
4. どのように育ってほしいか、家庭で大切にしていること
5. 園への希望・伝えておきたいこと

入力欄には短い記入例を表示するが、回答を誘導しない。

音声入力はOS標準機能を利用できるよう、通常の複数行テキスト欄として実装する。録音データをサーバーへ保存する必要はない。

## 17.11 ステップ7：確認・提出

提出前に、次の3区分で確認する。

```text
基本情報
健康・安全に関する重要情報
家庭生活・保護者記述
```

重要項目には次を含める。

- アレルギー
- けいれん
- 服薬
- 現在治療中の病気
- 緊急時の配慮
- かかりつけ医
- 送迎者

保護者は、確認画面で各項目を編集画面へ戻って修正できる。

提出ボタンの直前に、次を表示する。

```text
入力内容を確認し、園へ提出します。
健康状態や送迎者等に変更があった場合は、提出後も速やかに園へ連絡してください。
```

同意文書と児童票の情報提出を混同しない。児童票の提出は、登録情報の提出・確認記録として管理する。

## 17.12 必須・任意・条件付き

項目定義に次を持たせる。

```text
required
optional
required_if
hidden_if
staff_only
```

原則：

- 安全・連絡に直結する項目は必須。
- 本人が知り得ない項目には `分からない` を用意する。
- 自由記述は原則任意。ただし `あり` を選択した重要事項の詳細は必須にできる。
- 未回答と `なし` を同一に扱わない。
- 初期値として `なし` や `同意` を自動選択しない。

## 17.13 園職員のみ入力する項目

次は保護者画面へ入力欄として表示しない。

- 入所時の年齢
- 入所時の健康状態
- 健康面・身体面での園側留意点
- 面接所感
- 面接者
- 園による健康状態確認日
- 園の確認者、確認日時
- 園内の非公開メモ

保護者へ共有する項目と園内限定項目は、表示制御だけでなくAPI・DB・RLSでも分離する。

園職員は、保護者入力値を無断で上書きしない。誤りがある場合は次のいずれかとする。

- 保護者へ差戻す
- 園側確認値を別欄へ記録する
- マスタ変更申請を作成する

## 17.14 保育業務Webの確認画面

施設・クラス・状態で絞り込める一覧を作る。

| 表示項目 | 内容 |
|---|---|
| 園児 | 氏名、クラス |
| 状態 | 未着手、入力中、確認待ち、差戻し、受理済み |
| 提出日 | 保護者提出日時 |
| 重要確認 | アレルギー、けいれん、服薬等 |
| 不足 | 未回答数 |
| 更新 | 前回版からの変更有無 |
| 操作 | 確認、差戻し、受理、PDF |

確認画面は、紙面順ではなく次のタブで表示する。

```text
概要
健康・安全
送迎・家族
出生・発達
家庭生活
保護者記述
園内記録
変更履歴
```

アレルギー、けいれん、服薬等がある場合は、`重要確認` として上部にまとめる。赤色だけに依存せず、アイコンと文言で示す。

園職員の操作：

- 内容確認
- セクション単位の差戻し
- 差戻し理由
- 受理
- 園側留意事項の入力
- 前回版との差分表示
- A4 PDF出力
- 確認者・確認日時の記録

## 17.15 保存・変更・年次確認

状態：

```text
not_started
draft
submitted
under_review
needs_correction
accepted
change_requested
superseded
```

提出後、保護者は確定版を自由に上書きできない。変更時は `児童票変更申請` を作成し、変更前後を記録する。

次の情報変更は、年次確認を待たずに園へ通知する導線を設ける。

- アレルギー
- 服薬
- 既往歴
- けいれん
- かかりつけ医
- 住所・電話番号
- 送迎者
- 家族構成

園が設定した時期に、保護者へ次を依頼できるようにする。

```text
○ 変更なし
○ 変更あり（編集する）
```

## 17.16 PDF出力

- A4縦を基本とする。
- 添付原票に対応する4ページ構成を標準帳票として再現する。
- マスタ自動入力値、保護者回答、園職員欄を明確に区別する。
- 未回答を空欄にせず、必要に応じ `未確認` と表示する。
- 作成日、提出日、受理日、版番号を表示する。
- 確定PDFを非公開Storageへ保存する。
- PDF生成時の入力スナップショットとハッシュを保存する。

画面の質問順とPDFの紙面順は一致させる必要はない。PDF出力時に原票の項目位置へ再配置する。

## 17.17 データ設計

児童票を1つの巨大なJSONだけで保存してはならない。検索・アラート・権限制御が必要な項目は構造化する。

主要データ：

```text
child_profile_forms
child_profile_form_versions
child_profile_household_members
child_profile_transport_records
child_profile_birth_histories
child_profile_development_milestones
child_profile_health_records
child_profile_health_checkups
child_profile_medical_histories
child_profile_allergies
child_profile_vaccinations
child_profile_home_life_records
child_profile_guardian_notes
child_profile_staff_reviews
child_profile_change_requests
```

各値に次を持たせる。

- 入力元：マスタ／保護者／園職員
- 入力者
- 入力日時
- 確認者
- 確認日時
- 有効開始日
- 変更前の値
- 変更理由
- 児童票版

マスタから自動表示した項目も、提出時点の値をスナップショット保存する。

## 17.18 健康情報の保護

既往歴、アレルギー、健診、予防接種、健康上の留意点等は、アクセスを特に制限する。

- 保護者は自分の園児だけ閲覧・編集可能
- 職員は所属施設・担当クラス等の業務上必要な範囲だけ閲覧
- 園長、主任、指定職員は健康詳細を閲覧
- 健康情報の閲覧、変更、出力、ダウンロードをログに残す
- 一覧画面へ健康保険番号等を表示しない
- 児童票をOpenRouterへ送信しない
- AI文章作成の入力へ児童票全体を自動添付しない
- 連絡帳等で必要な場合も、承認された最小限の構造化項目だけを参照する

## 17.19 Claude Codeへの禁止事項

- 4ページのExcelを1画面の長大なフォームとして再現してはならない。
- 既存マスタ情報を保護者に再入力させてはならない。
- `未回答` を `なし` として保存してはならない。
- ラジオボタンで表現すべき排他的回答を複数選択にしてはならない。
- 複数選択可能な送迎方法・生活行動を単一選択にしてはならない。
- 健康・発達情報を自動診断してはならない。
- アレルギー情報だけで食事提供可否を自動確定してはならない。
- 園職員が保護者回答を履歴なく上書きできるようにしてはならない。
- 園職員限定欄を保護者向けAPIへ返してはならない。
- 児童票全体をOpenRouter等の外部AIへ送信してはならない。
- ワクチン名・健診名・病名を画面コードへ固定してはならない。
- 出生時体重の単位を添付原票の誤記どおり `cm` としてはならない。

## 17.20 受入基準

- 園児・保護者マスタに存在する情報が自動表示される。
- 自動入力値の出典と変更申請導線が表示される。
- 各ステップを途中保存し、別端末で再開できる。
- `あり` の場合だけ詳細欄が表示される。
- `なし`、`分からない`、`未回答`を区別できる。
- 年齢により乳児・幼児向け質問が適切に出し分けられる。
- 兄弟姉妹からコピーできるのは共通生活情報だけである。
- 健康・発達情報が兄弟姉妹間でコピーされない。
- 保護者提出後に保育業務Webへ確認タスクが生成される。
- セクション単位で差戻しできる。
- 園職員欄は保護者アプリから閲覧・編集できない。
- アレルギー、けいれん、服薬等が重要確認として表示される。
- 前回版との差分を確認できる。
- A4 4ページ相当のPDFを生成・保存できる。
- 確定済みデータを上書きせず、変更履歴を再現できる。
- 児童票データがOpenRouterへ送信されない。

# 18. 感染症欠席連絡・登園再開書類

## 18.1 目的と位置付け

保護者アプリの欠席連絡に、感染症専用の入力、書類案内、提出管理を追加する。

目的：

- 保護者が感染症による欠席を簡単に園へ連絡できる。
- 感染症名を選ぶと、次回登園時に必要となる書類をその場で確認できる。
- 医師記入の意見書を、園児情報が入力済みのA4 PDFとしてダウンロードできる。
- 保護者記入の登園届をアプリ上で作成・提出できる。
- 園側が感染状況、必要書類、提出状況、確認状況を一元管理できる。
- 感染症対策ガイドラインや自治体運用の変更に、マスタ更新で対応できる。

本機能は医療診断、登園許可の自動判定、治癒証明を行うものではない。診断は医師が行い、最終的な受入確認は園の運用規程と指定権限者の確認に基づく。

## 18.2 ガイドライン上の重要事項

添付資料は、厚生労働省作成の「保育所における感染症対策ガイドライン（2018年改訂版、2023年5月一部改訂）」である。こども家庭庁が掲載する現行ページでは、2023年10月10日現在の全体版が案内されている。

ガイドラインは、意見書と登園届について次を明記している。

- 意見書・登園届は、一律に作成・提出する必要があるものではない。
- 罹患後の登園再開時の取扱いは、市区町村の支援の下、地域の医療機関等と協議して各保育所で決定する。
- 園が提出を求める場合は、事前に保護者へ十分周知する。
- 意見書は必ずしも治癒確認を目的とせず、症状の改善が認められた段階で記入可能とされている。

したがって、疾病と提出書類の関係をアプリコードへ固定してはならない。次の二層で管理する。

```text
ガイドライン上の参考区分
  ＋
施設・自治体で承認した提出ルール
  ↓
保護者へ表示する最終案内
```

初期導入時はガイドラインの参考区分を候補値として登録し、Ohana Worksで実際に「必須」と表示する前に、法人管理者が各施設の運用、自治体の指示、嘱託医・地域医療機関との協議結果を確認して承認する。

## 18.3 欠席連絡画面の表示条件

通常の欠席連絡では感染症一覧を表示しない。

欠席理由に、少なくとも次を用意する。

```text
体調不良
感染症（医療機関で診断済み）
感染症の疑い・診断前
家庭の都合
その他
```

### 診断済み

`感染症（医療機関で診断済み）` を選択したときだけ、感染症チェックリストを必須表示する。

### 疑い・診断前

`感染症の疑い・診断前` では、保護者に病名を自己診断させない。

- 病名選択は任意とする。
- `病名未確定` を選択できるようにする。
- 園には「感染症疑い」として通知する。
- 診断後に保護者が同じ欠席案件を更新できるようにする。
- 病名確定後に必要書類を再判定し、保護者へ改めて通知する。

### 入力項目

マスタから取得できる項目は自動入力し、保護者へ再入力させない。

自動入力：

- 園児氏名
- 生年月日
- 所属施設
- クラス
- 保護者氏名
- 保護者と園児の関係
- 連絡日時

保護者入力：

- 欠席日または欠席期間
- 欠席理由
- 診断状況
- 感染症名
- 診断日
- 受診医療機関名
- 発症日
- 解熱日等、該当疾病の登園目安確認に必要な最小限の情報
- 次回登園予定日
- 園への連絡事項

病名は複数選択可能なチェックボックスとする。複数感染が実際に診断された場合へ対応するためである。

`その他の感染症` と `病名未確定` を必ず用意する。自由入力だけで既定の病名を登録させず、該当候補がある場合はマスタ候補を優先する。

| 水痘 | 全ての発しんが痂皮化していること |

| 侵襲性髄膜炎菌感染症 | 医師により感染のおそれがないと認められていること |
| 溶連菌感染症 | 適切な抗菌薬治療開始後24～48時間を経過していること |
| マイコプラズマ肺炎 | 発熱や激しい咳が治まっていること |
| 手足口病 | 発熱や口腔内の水疱・潰瘍の影響がなく、普段の食事がとれること |
| 伝染性紅斑 | 全身状態が良いこと |
| ウイルス性胃腸炎 | 嘔吐、下痢等の症状が治まり、普段の食事がとれること |

表示時には、次を併記する。

感染症欠席連絡の送信完了画面に、選択した疾病ごとに次を表示する。

```text

書類の作成者
登園のめやす
必要な操作

```

表示例：

```text

大和オハナ保育園の現在の運用では、
次回登園時に医師記入の「意見書」が必要です。

[ 意見書をダウンロード ]

```

または：

```text

```

複数疾病を選択した場合は、最も厳しい一種類へ勝手に統合せず、疾病ごとの必要書類を表示する。施設が「一案件一書類」で運用する場合のみ、施設ルールに従って一つの書類へ複数疾病を記載する。

送信後は次の両方へ保存する。

- 保護者アプリのお知らせ・手続き一覧
- 保育業務Web／管理者Webの感染症連絡一覧

プッシュ通知のロック画面には、初期設定では具体的な病名を表示しない。

## 18.7 医師記入の意見書

### 18.7.1 PDF生成

ガイドラインの参考様式に対応するA4 PDFを生成する。

園児・施設マスタから自動入力：

- 宛先となる保育所施設長
- 入所児童氏名
- 生年月日
- 選択済みの感染症
- 施設名
- 感染症欠席案件ID

医師記入欄：

- 症状が回復し、集団生活に支障がない状態である旨
- 登園可能と判断した日
- 記入日
- 医療機関名
- 医師名

PDFには、参考様式であること、一律に提出が必要な書類ではないこと、必ずしも治癒確認を目的としないことを、現行ガイドラインに合わせて表示する。

### 18.7.2 保護者操作

- 保護者は案件画面からPDFをダウンロードできる。
- A4で印刷できる。
- 園児氏名等が入力済みのため、保護者の転記負担を減らす。
- 保護者が医師欄をアプリ上で編集できないようにする。
- 必要に応じ、医師記入済み書類を写真またはPDFで事前提出できる。
- 原本提出が必要かどうかは施設ルールとして表示する。

### 18.7.3 園側確認

園側は次を記録できる。

- 事前画像・PDF受領
- 原本受領
- 受領日
- 確認者
- 不備
- 再提出依頼
- 返却有無
- 原本保管場所

画像だけで正式受領扱いにするかは施設設定とし、Claude Codeが推測して固定しない。

## 18.8 保護者記入の登園届

登園届は保護者アプリ上で作成・提出できる。

自動入力：

- 宛先となる保育所施設長
- 入所児童氏名
- 生年月日
- 選択済みの感染症
- 保護者氏名候補

保護者入力：

- 受診した医療機関名
- 受診日
- 病状が回復し、集団生活に支障がない状態と判断されたことの確認
- 登園再開予定日
- 提出日
- 提出者氏名
- 園児との関係

確認チェック：

```text
医療機関の診断を受けました。
表示された登園のめやすを確認しました。
現在の症状と登園予定について、園へ正確に申告します。
内容に変更が生じた場合は園へ連絡します。
```

疾病に応じて不要な項目は表示しない。登園届の提出時には、入力内容、文書テンプレート版、感染症マスタ版、施設ルール版、提出者、提出日時をスナップショット保存し、A4 PDFを生成する。

提出後に内容を変更する場合は、元の提出記録を上書きせず、新版を作成する。

登園届を提出しただけで自動的に `登園承認済み` にしない。園側の確認後に状態を更新する。

## 18.9 園側の管理画面

保育業務Webと、必要権限を持つ管理者Webに「感染症連絡」画面を追加する。

一覧項目：

- 施設
- クラス
- 園児
- 欠席日・期間
- 診断状況
- 感染症
- 発症日
- 受診日
- 登園予定日
- 必要書類
- 書類提出状況
- 園確認状況
- 最終更新日時

絞り込み：

- 施設
- クラス
- 日付
- 感染症
- 診断済み／疑い
- 意見書／登園届／書類なし／要相談
- 未提出／提出済み／不備／確認済み
- 登園予定日

園側操作：

- 欠席連絡確認
- 診断状況の更新依頼
- 書類案内の再送
- 意見書の受領記録
- 登園届の確認
- 不備・再提出依頼
- 登園予定日の確認
- 案件の終了
- 誤登録の取消
- 施設ルールの例外適用

疾病別件数を施設・クラス・日別に集計できるようにする。ただし、一般職員へ必要以上の健康情報を表示しない。

## 18.10 状態管理

感染症欠席案件の状態は、単一の真偽値にしない。

```text
draft
reported_suspected
reported_diagnosed
waiting_for_document
document_submitted
document_needs_correction
document_verified
return_scheduled
return_confirmed
closed
cancelled
```

書類状態は別に管理する。

```text
not_required
pending_rule_confirmation
required_not_created
downloaded
submitted_digitally
original_received
needs_correction
verified
waived_by_authorized_staff
```

`return_confirmed` は園側の指定権限者だけが設定できる。保護者の欠席連絡送信や登園届提出だけでは設定しない。

## 18.11 通知

## 18.15 権限・個人情報保護

感染症名、受診情報、書類は要配慮性の高い健康情報として扱う。

- 保護者は、自分と有効な関係がある園児の案件だけ閲覧・更新できる。
- 園職員は、所属・担当・施設権限の範囲だけ閲覧できる。
- 健康情報の詳細閲覧、書類ダウンロード、原本確認は指定ロールへ限定する。
- 法人全体集計は権限者だけ利用可能とする。
- RLSとサーバー側認可を必須とする。
- 添付書類を公開URLで保存しない。
- 短時間の署名付きURLを使用する。
- 閲覧、ダウンロード、印刷、変更、承認、取消を監査ログへ記録する。
- OpenRouterその他の生成AIへ、感染症案件、意見書、登園届、医療機関情報を送信しない。
- 通知本文へ病名や医療情報を表示するかは保護者設定と施設ポリシーに従い、初期値は非表示とする。

## 18.19 受入基準

- 登園届提出時の文書版、疾病マスタ版、施設ルール版が保存される。
- 園側が提出、不備、原本受領、確認を管理できる。
- 保護者の提出だけで登園承認済みにならない。
- 保護者は自分の園児だけを閲覧できる。
- 園職員は権限のある施設・クラスだけを閲覧できる。
- 通知の初期表示に病名が含まれない。
- ルール改訂後も過去案件を当時の内容で再現できる。

- 添付書類が公開URLで配信されない。

- 雇用契約書と労働条件通知書は別文書であり、同じ承認済み条件版を参照する。
- 2024年4月施行事項と、2026年10月1日以降の短時間・有期雇用通知書版を適用日に応じて切り替えられる。
- 有効な労使協定が確認できない対象者へ、1年単位の変形労働時間制を自動表示しない。
- 法定時間外、法定休日、深夜、月60時間超の割増率等が最低基準未満の場合、確定できない。
- 就業規則・規程版が未承認の場合、本番公開できない。
- 電子交付希望の有無と取得時点を記録でき、希望しない職員の紙交付を管理できる。
- 規程の既読確認、任意同意、申請・許可、契約署名を別状態で管理できる。
- 自社保育園利用、短時間勤務、自転車通勤、中退共を条件付きで正しく判定できる。
- 子どもの卒園により職員を自動退職・自動雇止めしない。
- 自転車通勤手当は、承認済み規程と一致する場合だけ給与へ連携する。
- スポット勤務は勤務開始前に日時、場所、業務、休憩、賃金、交通費、支払条件を本人へ明示できる。
- 職員写真・動画・SNS同意を用途別に許可・条件付き・不許可で管理し、未回答を許可扱いにしない。
- 同意撤回後は新規公開を停止し、過去の公開物との対応履歴を残せる。
- A4 PDFで文字切れ、重なり、空白ページがない。
- 職員本人だけが自分の契約・通知・同意を閲覧・保存できる。
- 労務権限のない園管理者が雇用条件や機微情報を閲覧できない。
- 改定後も当時の規程版、条件版、回答、署名、PDFハッシュを再現できる。
- マイナンバー、健康情報、犯罪事実確認情報をOpenRouterへ送信しない。

## 21.4 入園契約・同意の受入基準

- 「全員」文書は対象園児全員に必須表示される。
- 「該当者」文書は該当・非該当・分からないの回答が必須である。
- 地域枠かつ弾力運用のAND条件が正しく判定される。
- 未回答・不足書類がある状態で最終提出できない。
- 同意項目ごとの回答を後から再現できる。
- 文書改定後も、旧版で同意した内容を表示できる。
- 写真販売不許可の園児を写真販売対象にできない。
- 紙受領と電子同意を区別できる。
- 保護者は自分の園児だけを操作できる。
- 園職員は管理施設の園児だけを確認できる。

## 21.5 児童票の受入基準

- 園児マスタの既存情報が自動表示される。
- 同じ情報を複数回入力させない。
- 年齢・回答に応じて不要項目を非表示にできる。
- 下書きを保存し、別端末で再開できる。
- 保護者欄と園職員欄が分離されている。
- 健康情報は指定権限だけが閲覧できる。
- 提出後の変更が履歴に残る。
- A4 4ページ相当で出力できる。
- 原則として児童票データをOpenRouterへ送信しない。

## 21.6 感染症欠席連絡の受入基準

- 感染症を理由とするときだけ疾病チェックリストが表示される。
- 診断前は病名未確定で送信できる。
- 送信直後に施設ルールに基づく必要書類が表示される。
- 意見書をA4 PDFでダウンロードできる。
- 登園届を保護者アプリで作成・提出できる。
- 園側の確認前に登園承認済みにならない。
- ガイドライン版と施設ルール版を保存できる。
- 健康情報のRLS、非公開Storage、監査ログが有効である。
- 過去案件が後日のマスタ変更で書き換わらない。

# 22. 移行上の注意と未確定事項

## 22.1 移行上の注意

- 既存紙書類を、本人の電子同意があったものとして移行してはならない。
- 既存紙は `legacy_paper` として、受領日、文書名、対象者、原本保管場所、スキャン有無を登録する。
- 既存職員が過去に受領した規程を、全員一括で既読・同意済みにしてはならない。新しい規程版は周知と既読確認を行う。
- 現在の雇用条件と旧契約書が異なる場合、旧文書を上書きせず、適用開始日付きの新しい条件版・通知書を作成する。
- 既存の包括的な誓約・同意から、写真・SNS・採用広報への同意を推測してはならない。
- 職員写真・動画の新しい用途別同意は、在職者を含めて取得する。未回答は不許可として扱う。
- 過去に公開済みの職員写真は、媒体、URL、掲載日、写っている職員、既存同意の有無を棚卸しする。
- 既存の自転車通勤者は、保険証憑・有効期限・経路・手当根拠を再確認する。
- 自社保育園利用者と託児利用を伴う短時間勤務者は、職員と園児の関係および適用期間を再登録する。
- 中退共加入状況を、加入済み、対象外、確認中に分け、同意未確認を加入拒否と推測しない。
- スポット支援員機能は `spot_employment_enabled = false` で導入し、専門家確認と受入テスト後に有効化する。
- 犯罪事実確認情報を、既存誓約書や汎用職員マスタから専用領域へ自動コピーしてはならない。
- 現行書式の文言上の矛盾・誤記をそのままデジタル化しない。
- 料金・支払期限・契約プランは、有効開始日付きの版として移行する。
- 旧同意から写真販売同意を推測しない。必要に応じ、新しい用途別同意を取り直す。
- 確定済み文書を移行スクリプトで上書きしない。
- 児童票の健康情報を汎用園児テーブルのJSON一列へまとめない。
- 園児の退園、職員の退職後も、法令・契約・運用で必要な期間は記録を保管し、通常画面からはアクセスを制限する。
- 新機能は施設単位・機能単位のフラグで段階導入する。
- 本番移行前に、匿名化したテストデータでPDF、権限、同意証跡、差戻し、再発行を検証する。
- 既存の欠席連絡を、新しい感染症案件と重複登録しない。
- 過去の欠席理由から感染症名や提出書類を推測して自動移行しない。
- 現行ガイドラインの参考区分を、施設確認なしに必須ルールへ移行しない。
- 施設ルールは有効開始日付きで導入し、導入前の案件へ遡及させない。
