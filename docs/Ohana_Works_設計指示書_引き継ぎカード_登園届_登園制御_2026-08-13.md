## §2 確定した業務フロー(2起点)

### 起点A: 園内発症(引き継ぎカード起点)

```text
園児が登園 → 園内で体調悪化
  → 職員が検温・排便を記録(既存機能: 188/194)
  → 早退・引き取りを決定(電話連絡は従来どおり)
  → 一般職員が引き取り・引き継ぎカードを作成(Ohana Kids/admin_web)
      ├ 当日の全検温履歴を時系列で自動取得(最新値だけに省略しない)
      ├ 当日の排便履歴を自動取得
      ├ 発疹・蕁麻疹等を追加入力
      └ 園内で報告されている感染症を参考表示(§3.2)
  → プレビュー確認後、保護者アプリへ送信(引き取り決定時点。従来の「紙をお迎え時に手渡し」の電子化+前倒し)
  → 保護者が受診時にカードを提示・参照
  → 保護者が受診結果を入力
      ├ 感染症(マスター選択)→ 感染症確定 → 起点共通フローへ
      ├ 感染症ではない/診断未確定 → ブロックなし・案件は受診結果として記録し終了/継続
      └ 未入力のまま翌日登園 → 案件自動消滅(§3.6)
```

### 起点B: 自宅発症(欠席連絡起点)

```text
登園前に自宅で発症 → 保護者が受診 → 医師から感染症の診断
  → 保護者が欠席連絡を送信: 病欠を選択+「感染症」チェック → 感染症一覧から選択(§3.3)
  → 選択した時点で感染症確定 → 起点共通フローへ
(引き継ぎカードは存在しない。案件はカード無しで成立する)
```

### 起点共通フロー(感染症確定後)

```text
感染症マスターの有効版と照合し必要書類を判定
  ├ 登園届(保護者記入) → アプリ内で完結(§3.5)
  ├ 登園許可書(医師記入) → 紙ベース: アプリからPDF DL→医師記入→紙で園へ提出(§3.7)
  └ (マスター未登録等の例外) → 職員確認
  → 必要書類が未提出の間、登園処理をブロック(§3.8)
  → 電子提出 or 職員の紙受領記録でブロック解除 → 登園処理続行
```

**確定原則(俊 2026-08-13)**:
- 対象は**書類提出が必要な感染症のみ**。通常の風邪等の欠席は本フローに入らず、表示も出さない。
- **ブロック発動は「感染症確定後・必要書類未提出の間」のみ。** カード送信のみ・受診結果未入力の状態ではブロックしない(未受診の保護者も実在し、受入れ拒否はできない。本機能は受診を促す仕組みとして機能させる)。

## §3 確定仕様

### 3.1 引き取り・引き継ぎカード

- 対象園児・対象日・作成職員を必須。作成者は**一般職員**(施設アクセス権で可)。作成端末はOhana Kids(iPad)を主とし、admin_webにも同等画面。
- 状態: 下書き→送信済み(取消は送信前のみ。送信後の訂正は再送信=新版スナップショットとし、保護者には最新版を表示・旧版は履歴保持)。
- **自動取得(スナップショット固定)**:
  - 検温: 当日の`child_temperature_records`全件を時系列(時刻・体温・可能なら記録職員)。家庭連絡帳の朝検温があれば併記。
  - 排便: 当日の`toileting_records`(時刻・性状)+家庭連絡帳の排便情報(存在すれば)。
  - 送信時点のスナップショットをJSONで保存。以後デイリーボード側が修正されてもカードは変わらない(AC-03)。
- **職員追加入力**: 蕁麻疹(あり/なし/未確認+補足)、発疹(あり/なし/未確認)、発疹部位(複数選択: 顔・首・胸・腹部・背中・腕・手・脚・足・臀部・全身・その他+自由記述)、自由記述(園で確認した様子・症状開始時刻・医療機関への補足)。※咳・鼻水等の標準項目追加は未確定(§12)のためv1では自由記述で扱う。
- **保護者向け文面**: 施設別テンプレート管理(コード固定禁止)。既定文=集団生活のため必要に応じた受診への協力依頼+受診後の結果入力依頼。医療判断を断定する文章は生成しない。園児名は保護者アプリの表示規則(honorific_suffix_resolved)に従う。
- 送信時: 送信日時・送信職員・送信先(対象園児に紐づく保護者)を記録し、notifications outbox経由でプッシュ通知。

### 3.2 園内感染症の参考表示(カード内)

- ソース: **欠席連絡の感染症選択**(§3.3)。
- 集計初期値(俊確定): **同一施設・過去7日間・1件から**「○○の報告 n件」を表示。園児名・クラス等の個人特定情報は一切表示しない。
- 「流行している」とは表現せず「報告がある」事実のみ。「診断ではなく受診時の参考情報」である旨を明示。
- 期間・集計単位・最低件数は設定値として後から調整可能な実装にする(DB設定 or 定数、Fit & Gapで判断)。

### 3.3 欠席連絡の改修(parent_requests拡張)

- 病欠(sick_absence)選択時に「感染症」チェックを表示→ONで感染症一覧(マスターの有効版)から選択して送信。
- 選択は必須ではない(感染症でない病欠は従来どおり)。感染症を選択した場合、**その時点で感染症確定**として案件を自動作成し、必要書類判定→保護者アプリに次の手続きを表示する。
- 誤選択・診断変更への対応: **主任以上(manages_childcare)が理由付きで案件を取消できる**(監査ログ必須)。取消でブロックも解除される。元の欠席連絡値は履歴として保持。

### 3.4 受診結果入力(起点Aの後続)

- 保護者は引き継ぎカードから受診結果入力へ遷移。
- 項目: 受診した/していない、受診日時、医療機関名(任意)、感染症(マスター選択・該当なし選択可)、医師からの説明、園への補足。
- 感染症を選択→確定→必要書類判定へ。「感染症ではない」→書類不要・案件終了。「受診していない/診断未確定」→ブロックなしのまま継続(§3.6の自動消滅対象)。
- 提出時に園側へ通知(既存の施設管理者宛通知パターン踏襲)。

### 3.5 電子登園届(保護者記入・アプリ完結)

- 対象: マスターで`登園届`区分の感染症(初期9種、§4)。
- 入力・表示: 園児情報・提出者(保護者)情報はログイン情報から自動表示。感染症名・受診日等に加え、**マスターのルールから動的に生成される確認項目**を表示。
- **登園基準の扱い(重要・設計簡素化)**: 初期マスターの登園届9種の基準はほぼ**症状ベース**(「発熱や咳が治まっている」「普段の食事がとれる」等)であり、これらは**保護者の確認チェック**で扱う。日付計算が必要なのは溶連菌(抗菌薬内服後24〜48時間経過)のみ。ルール表現は日付条件・症状条件の両方を宣言的に表現できる構造にするが(§4.3)、複雑な日数エンジンは初期実装では最小限でよい。
- 全条件充足時のみ提出可能。未達時は提出ボタン無効+未達理由を具体的に表示。
- 本人確認: 登録済み保護者名の自動表示+「上記内容を確認し、この内容で登園届を提出します」確認チェック必須。署名・捺印不要。提出者guardian_id・提出日時を監査保存。
- 提出成立: 保護者の提出時点で成立。**園側の追加承認は不要**。提出時にサーバー側で条件を再検証。園側へ「提出済み」即時反映+通知。
- 提出前編集は変更履歴を記録(項目・前後の値・日時・保護者ID・使用マスター版)。**提出後は保護者による修正不可**。提出時の入力・判定・マスター版を不変スナップショットで保存(AC-09/16)。
- 提出済みなら登園可(登園予定日欄はv1では設けない。書類充足=ゲート解除)。

### 3.6 受診結果待ちの自動消滅(俊確定)

- 起点Aでカード送信後、受診結果が未入力のまま園児が登園した場合(=感染症未確定)、**登園処理の時点で案件の「受診結果待ち」状態を自動で消滅させる**(closed・理由=登園により自然終了)。職員の操作は不要。受診は強制ではない。
- カード自体は履歴として保護者・職員とも参照可能なまま残す(消えるのは案件の待ち状態のみ)。

### 3.7 登園許可書(医師記入・紙ベース)

- 対象: マスターで`登園許可書`区分の感染症(初期13種、§4)。
- 保護者アプリで「登園許可書(医師記入)が必要」と明示し、**有効版の様式PDFを表示・ダウンロード**できる(137 document_templatesの版管理。旧版を新規案件へ配布しない)。
- 医師記入→紙で園へ提出→**一般職員が実物確認のうえ「受領」記録**(受領日時・受領職員・対象感染症・様式版)。受領でブロック解除。
- 紙原本はアプリへの画像保存はせず(v1)、既存方法で保管。受領記録のみ必須。
- 例外の紙登園届(スマホ故障等): 同様に一般職員が受領記録。submission_method=paperで電子提出と明確に区別(偽装禁止)。

### 3.8 登園制御(ゲート)

- 判定: 対象園児に**「感染症確定済み・必要書類未充足」の有効案件が1件でもあれば登園処理不可**(複数案件並行時はすべて充足するまで不可)。
- 適用経路: ①キオスクQR(resolve-guardian-qr。家庭連絡帳必須拒否と同じ機構に判定追加、拒否理由=必要書類名) ②職員による出欠編集・代理登園(K7経由の登園登録)にも同判定を適用し、理由と必要書類を表示して停止。
- **朝の紙持参の一続き処理**: ブロック表示画面から一般職員が「対象書類の選択→内容確認→紙で受領→受領記録保存→ブロック解除→登園処理続行」を1画面・1フローで完結できる。受領記録の保存成功時のみ解除(トランザクション一貫性)。
- 「警告を無視して登園」の汎用バイパスは設けない。例外は§3.3の案件取消(主任以上・理由必須・監査)で対応。
- 電子登園届の提出は即時にゲートへ反映(提出→翌朝の登園が通る)。

### 3.9 機能フラグ(2段構成)

- `infection_control_enabled`(既定OFF・施設別ON): カード・欠席連絡の感染症選択・受診結果・登園届/許可書の全機能。
- `infection_gate_enabled`(既定OFF・施設別ON): 登園ブロックのみ。**controlを先行ONにして案件・書類のデータが揃ってからgateをONにする**段階リリースを必須とする(既存園児の誤ブロック防止。草案§16の原則)。gateがOFFの間はブロックせず警告表示のみ。

## §4 感染症マスター

### 4.1 初期データ(俊提供の一覧「30. 保育所における感染症の登園基準一覧」を正とする)

**登園許可書(医師記入)が必要な感染症(13種)**

| 感染症名 | 登園基準 |
|---|---|
| 麻しん(はしか) | 解熱後3日を経過してから |
| 風疹(三日はしか) | 発しんが消失していること |
| インフルエンザ | 発症した後5日を経過し、かつ解熱した後2日を経過していること(乳児にあっては、3日経過していること) |
| 水痘(水ぼうそう) | すべての発しんがかさぶた化していること |
| 流行性耳下腺炎(おたふくかぜ) | 耳下腺、顎下腺、舌下腺の腫脹が発現してから5日を経過し、かつ全身状態が良好になっていること |
| 結核 | 医師により感染の恐れがないと認められていること |
| 咽頭結膜熱(プール熱) | 発熱・充血等の主な症状が消失した後、2日経過していること |
| 百日咳 | 特有の咳が消失していること又は適切な抗菌性物質製剤による5日間の治療が終了していること |
| 流行性角結膜炎 | 結膜炎の症状が完全に消失していること |
| 腸管出血性大腸菌感染症(O157、O26、O111等) | 医師により感染のおそれがないと認められていること |
| 急性出血性結膜炎 | 医師により感染の恐れがないと認められていること |
| 髄膜炎菌性髄膜炎 | 医師により感染の恐れがないと認められていること |
| 新型コロナウイルス感染症 | 発症したあと5日経過し、かつ症状が軽快した後1日を経過すること(無症状の感染者の場合は、検体採取日を0日目として、5日を経過すること) |

**登園届(保護者記入)が必要な感染症(9種)**

| 感染症名 | 登園基準 |
|---|---|
| 溶連菌感染症 | 抗菌薬内服後24〜48時間経過していること |
| マイコプラズマ肺炎 | 発熱や激しい咳が治まっていること |
| 手足口病 | 発熱や口腔内の水疱、潰瘍の影響がなく、普段の食事がとれること |
| 伝染性紅斑(リンゴ病) | 全身症状が良いこと |
| ウイルス性胃腸炎(ノロ、ロタ、アデノウイルス) | 嘔吐、下痢等の症状が治まり、普段の食事がとれること |
| ヘルパンギーナ | 発熱や口腔内の水疱、潰瘍の影響がなく、普段の食事がとれること |
| RSウイルス感染症 | 呼吸器症状が消失し、全身状態が良いこと |
| 帯状疱疹 | すべての発しんがかさぶたになってから |
| 突発性発しん | 解熱し機嫌がよく全身状態が良いこと |

※「感染しやすい期間」も参考情報としてマスターに保持してよい(保護者・職員向け表示用)。システム判定には使わない。

### 4.2 CCの照合タスク

初期データ登録前に、こども家庭庁「保育所における感染症対策ガイドライン」の**現行最新版**(§13のURLを起点に現行ページを確認)と上記一覧を照合し、**不足・差分があれば俊へ報告する。勝手に変更しない。** 俊が承認した内容のみを初期データとする。

### 4.3 マスター構造の要件

- 版管理必須: effective_from/effective_to・version・出典(source_title/url/revision)。ハードコード禁止。過去の提出済み記録は当時の版で再現できること(AC-16)。
- ルール定義は宣言的な形式(任意コード実行禁止)。表現できる条件: 症状確認チェック(文言リスト)・日付条件(基準日+経過時間/日数)・両者のAND。初期データでは登園届9種=症状チェック中心+溶連菌のみ日付条件。
- 適用スコープ: **グループ共通1系統**で開始(様式は自治体指定なし・園独自と確定済みのため、自治体別上書き構造はv1不要。施設別上書きの器だけ将来枠として残してよい)。
- **承認方式=(b)運用承認**: マスターの登録・改訂・有効化は俊(admin_web、権限はexecutive_director/system_admin)。大原統括園長の確認は運用(会議・口頭)で担保し、システムには確認記録(確認者名・日付)を入力して残す。アプリ内承認フロー((a)方式)は将来拡張とし、v1では実装しない。

## §5 データモデル方針

草案§5の論理モデルをベースに、以下をOhana Works規約へ写像してCCが物理設計する(Fit & Gap後にmigration全文提示)。

- `tenant_id/facility_id` → `office_id`(施設)。テナント概念は導入しない。
- 中心エンティティ=**感染症・体調不良案件**(仮: `infection_cases`): child_id・office_id・起点(handover/absence)・status・確定感染症(rule_id+version)・必要書類区分・書類状態・作成/確定/終了の各タイムスタンプ。**引き継ぎカードは案件の任意の子**(起点Bでは存在しない)。
- カードスナップショット(仮: `handover_card_snapshots`): case_id・version・検温/排便/症状/参考表示のJSON・送信情報。
- 受診結果(仮: `medical_visit_reports`)、電子登園届(仮: `return_notices`: 入力スナップショット・確認チェック・提出情報・マスター版・提出後不変)、届の編集履歴、紙受領記録(仮: `paper_document_receipts`)、状態遷移イベント(監査用)。
- マスター(仮: `infection_rule_masters`)+様式PDFは**137 document_templatesの拡張**で管理。
- ステータスは草案§4を簡素化: 案件=awaiting_medical_result/infection_confirmed/closed(+closed_reason: auto_attended(§3.6)/no_infection/returned/cancelled)、書類=not_required/required_not_submitted/submitted_electronically/received_on_paper。ゲート判定は案件+書類状態からの導出関数とし、状態の二重管理をしない。
- 命名は既存規約(小文字snake_case・日本語コメント)に合わせCCが最終確定。既存テーブルの拡張を優先し重複エンティティを作らない。

## §8 UI要件

### 職員側(Ohana Kids主+admin_web同等)

## §9 受入条件(AC)

- **AC-01** 当日3件の検温記録がカードに3件すべて時系列表示される。
- **AC-02** 当日の排便記録が時刻・性状とともにカードへ反映される。
- **AC-03** 送信後にデイリーボードを修正しても送信済みカードは変わらない。
- **AC-04** 欠席連絡で感染症を選択すると案件が自動作成され、有効マスター版から書類区分(届/許可書)が判定される。
- **AC-05** 受診結果で感染症を確定した場合も同様に判定される。
- **AC-06** 登園届: 感染症に応じた確認項目が動的に切り替わり、条件未達では提出ボタンが無効+未達理由表示(溶連菌は抗菌薬開始からの時間判定を含む)。
- **AC-07** 提出前編集の履歴(前後の値・変更者・日時・マスター版)が記録される。
- **AC-08** 条件充足+確認チェックで提出すると園の追加承認なしで提出済みとなり、ゲートへ即時反映される。
- **AC-09** 提出済み登園届は保護者が修正できず、提出時の内容とマスター版を再現できる。
- **AC-10** 許可書対象では有効版PDFのみが表示・DLでき、旧版は新規案件に配布されない。
- **AC-11** gate ON施設で書類未充足の園児はキオスクQR・職員の登園登録の両方でブロックされ、理由と必要書類が表示される。
- **AC-12** 一般職員が紙を受領記録すると受領者・時刻・方法が保存され、同一フローでブロック解除→登園処理が続行できる。受領記録の保存失敗時は解除されない。
- **AC-13** カード送信のみ・受診結果未入力の園児はブロックされず、登園処理の時点で「受診結果待ち」が自動消滅する(カードは履歴に残る)。
- **AC-14** 複数案件が並行する園児は、すべての案件の書類が充足するまで登園不可。
- **AC-15** 別施設・別世帯の園児のカード・受診結果・書類は閲覧・操作できない(拒否側E2E)。
- **AC-16** マスター新版を有効化しても過去の提出済み登園届は旧版のまま再現できる。
- **AC-17** 主任以上の案件取消でブロックが解除され、監査ログに理由が残る。一般職員の取消は拒否される。
- **AC-18** infection_gate_enabled=OFFの施設ではブロックされず警告表示のみになる。

## §10 Fit & Gap調査項目(CCが正式設計前に実施)

1. 検温(188)・排便(194)・家庭連絡帳の実スキーマとカード取得RPCの設計。
2. 早退の既存表現(attendance_kind=early_leave)と案件の関連付け方法。
3. parent_requestsへの感染症選択追加の物理設計(197のend_date/absence_kindとの整合、旧バージョンparent_appからのRLS直接insert互換)。
4. resolve-guardian-qrの拒否機構への判定追加方法と、職員側登園登録(K7/185/187経路)へのゲート適用点の洗い出し。
5. 137 document_templatesの現構造と様式PDF(2種)の格納・署名URL・版管理の設計(M1基盤の先行最小実装として)。
6. 様式PDFの生成方法(静的PDF配布か、園児情報差し込み生成か。差し込みは保育園名・クラス・氏名・病名。生成する場合の技術選定)。
7. 通知outboxへのイベント追加(type定義・宛先解決)。
8. 監査対象操作の一覧化(作成・送信・提出・受領・取消・ゲート判定変更)とtrg_audit適用。
9. 保護者と園児の関係(複数保護者・共同親権)での閲覧/提出権の扱い(guardian_has_child_access準拠)。
10. 健康情報の保持期間・退園後の扱い(既存方針との整合、不足があれば指摘)。
11. 機能フラグ2本の追加(feature_flags既存機構)。
12. 案件・カード・届のRLS設計(3ドメイン分離)。

調査結果は「既存利用/既存拡張/新規実装/要業務確認/対象外」に分類し、根拠となるコード・テーブル・画面を示すこと。

## §11 実装フェーズ案

1. **Phase 0**: Fit & Gap調査+マスター照合(§4.2)→報告で停止(俊確認)。
2. **Phase 1**: 感染症マスター+初期データ+様式PDF(137拡張)+admin_web管理画面(俊が登録・改訂できる最小UI)。
3. **Phase 2**: 欠席連絡の感染症選択(parent_app+admin_web承認画面表示)+案件自動作成+必要書類判定+保護者への手続き表示。
4. **Phase 3**: 引き継ぎカード(作成・スナップショット・送信・保護者閲覧)+受診結果入力+自動消滅。
5. **Phase 4**: 電子登園届(条件判定・編集履歴・提出固定)+許可書PDF配布+紙受領記録。
6. **Phase 5**: 登園ゲート(キオスク+職員経路)+朝の一続き処理+E2E一式。
7. 段階リリース: `infection_control_enabled`を試験施設でON→運用確認→`infection_gate_enabled`ON。全フェーズでDB変更はmigration全文提示→俊承認→俊適用の規約に従う。

各Phaseの粒度・並行可否はCCが現行キューとの兼ね合いで最適化してよい(着手タイミングはCC判断に一任済み)。

## §14 設計上の最終原則

1. 事実を引き継ぐ。診断しない。
2. 既存データ(188/194/家庭連絡帳)を再利用し、二重入力・二重実装をしない。
3. 基準と様式は版管理し、ハードコードしない。
4. ブロックは「感染症確定後・書類未充足」のみ。未受診を理由に受入れを拒否しない。
5. 紙持参の現場対応は一般職員が一続きで安全に完結できる。
6. 提出済み記録は当時の内容とマスター版を固定する。
7. 全経緯(作成・送信・提出・受領・取消・ゲート判定)を追跡できる。
8. 保護者には理由と次の行動を分かりやすく示す。
9. ゲートは2段フラグで段階有効化し、既存園児を誤ブロックしない。
