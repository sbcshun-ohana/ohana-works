# Ohana Works 保育業務・共通基盤 実装指示書 v0.2

作成日：2026-07-16
元資料：`Ohana_Works_追加機能_設計指示書_v0.1`（レビュー済み・改善反映版）

---

## 0. この指示書の位置づけ

- 設計指示書v0.1をレビューし、矛盾・実運用上の問題を修正した実装用の指示書です
- **今回実装する機能は、すぐに利用開始するものではありません。あらかじめ実装しておき、将来利用を開始します**
- したがって以下を厳守してください：
  - 新機能はすべて**機能フラグでデフォルトOFF**とし、有効化するまで既存画面・既存機能に一切影響を与えないこと
  - 既存の職員業務（勤怠・給与・申請・お知らせ）の動作・スキーマ・RPCを壊さないこと
  - マイグレーションは既存の連番規約に従い、`supabase/migrations/` に作成すること（`admin_web/supabase/migrations/` に作らない）
  - 既存の実装パターン（履歴管理テーブル、payroll系と同様のRPC権限パターン、監査履歴）を踏襲すること

## 1. 実装スコープ（今回）

設計指示書v0.1の §36「初期実装範囲」を対象とするが、順序として先に共通基盤（Phase 0）を作り、その上に連絡帳ワークフロー（Phase 1）を載せる。

### Phase 0：共通基盤

1. **機能フラグ基盤**
   - 施設ごと × 機能ごとのON/OFF（feature_flags的なテーブル）
   - 役職・権限ごとの利用可否
   - 試験運用対象施設・対象職員のみ先行公開できる仕組み
   - クラス単位のON/OFF・利用開始日・料金プラン制御は**実装しない**が、テーブル設計上は将来追加できる余地（拡張列やスコープ概念）を残す
   - 注意：「機能のON/OFF」と「機能内の運用設定（例：家庭連絡帳の必須/任意）」は**別レイヤー**として設計する。後者は各機能のテーブル側に持たせる

2. **クラス管理**
   - 施設に紐づくクラス（年度・クラス名・年齢区分）
   - 年度ごとのクラス編成、クラス変更履歴の保持

3. **園児マスタ（最小限）**
   - 基本項目：園児氏名、呼び方、呼称サフィックス、性別、生年月日（年齢自動計算）、所属施設、所属クラス、入園日、退園日、きょうだい情報、備考
   - **呼称サフィックス**：デフォルトは性別ルール（女児=ちゃん、男児=くん）だが、園児ごとに上書き可能な列を持たせる
   - 在籍ステータス：入園予定 / 在籍中 / 退園予定 / 退園済み
   - 退園済みは当日の作成対象・未作成件数から除外、過去記録は削除しない
   - クラス在籍履歴テーブル（進級・クラス変更後も同一園児として記録継続）
   - 身体測定・発達記録・保育料プラン・曜日別登降園設定・園児台帳詳細は**今回はテーブルを作らない**（将来フェーズ。ただし園児IDを軸に追加できる構造にする）

4. **権限・RLS**
   - 既存の職員・権限の仕組みを再利用し、保育業務向けに「一般職員 / 管理者 / システム管理者」の3階層をマッピングする（既存ロールと二重管理にしないこと。既存ロール体系をまず調査し、対応表を提示してから実装する）
   - 職員ごとに利用可能施設・クラスを設定できるようにする
   - **RLS分離の必須要件**：保育士（一般職員）は担当施設の園児情報にアクセスできるが、給与・他職員の勤怠等の職員業務データthere へのアクセス権は一切広げないこと。逆に、園児情報は職員業務の権限では見えないこと。既存RLSへの影響をレビューし、変更点を報告する
   - 園児ごとの固定担当保育士は登録しない（当日の担当割当のみ）

5. **監査履歴**
   - 入力・修正・承認・差し戻し・公開・閲覧の履歴を残す共通の仕組み（既存の操作履歴の仕組みがあれば再利用、なければ汎用audit_logsを新設）

### Phase 1：連絡帳ワークフロー（初期実装範囲）

6. **保育業務メニュー**
   - Flutterアプリに職員業務⇔保育業務の画面切替を追加（機能フラグOFF時は保育業務メニュー自体を非表示）

7. **当日の欠席選択**
   - 在籍園児一覧から欠席チェック、複数端末へ即時反映（Supabase Realtime）
   - 欠席児童は当日の連絡帳作成対象外・未作成件数から除外
   - 変更者・変更日時を履歴保存、出席へ戻すと対象へ復帰

8. **クラス活動入力・申請・承認**
   - クラスごとに1日1回、入力項目：今日の活動 / 活動内容 / クラス全体の様子 / クラス全体へのお知らせ / その他
   - 担当者は「職員が自分を設定」「管理者が指定」の両方可能
   - 入力担当者以外は原則編集不可。ただし**担当者不在時は管理者が担当者を変更でき、変更履歴を残す**（連絡帳の§11と同じ考え方をクラス活動にも適用）
   - 入力 → 申請 → 管理者確認 → 承認 / 差し戻し
   - 園ごとに入力・申請締切時刻を設定（デフォルト15:00）、状態別の通知

9. **園児別担当者割当**
   - 各園児の連絡帳は担当職員1名が作成する（**1人の職員が複数園児を担当できる**、という意味であることに注意。原文の「職員1人が園児1人分」は誤解を招く表現なのでこの解釈で実装する）
   - 園児ごとに担当者選択、複数園児の一括割当、途中変更可能（入力内容は保持）
   - 入力者・入力時刻を記録し、他職員の入力を上書きしない。補足メモは別レコードとして追加

10. **園児個別メモ・個別お知らせチェック**
    - 毎日の入力：保護者からの連絡内容 / 今日の園児の様子（短い箇条書き）/ 個別のお知らせ（複数チェック）/ その他自由記載
    - 個別お知らせ候補（着替え補充・おむつ補充・鼻水・咳など設計書§10.3の項目）は**マスタテーブル化**し、園ごとに項目を編集できるようにする（正式一覧は別途決定のため、初期データとして§10.3の項目を投入）
    - 備品利用の記録欄（品目・数量）は設けるが、**請求への自動連携は今回実装しない**（請求管理は後続フェーズ。単価マスタと計算ロジックは請求フェーズで追加）

11. **AI連絡帳作成（共通AI基盤の最小版）**
    - クラス活動＋園児個別メモから、保護者向け連絡帳文章を生成
    - 文章ルール：保護者の内容に理解を示す / 質問・相談へ返答 / 必要事項を明確に / 気遣い / 明るく丁寧 / 攻撃的・否定的表現を避ける
    - AI安全ルール（設計書§7.3）をシステムプロンプトに組み込む：入力されていない出来事を追加しない、過去を当日として書かない、他児比較禁止、病気・発達の断定禁止、数値・日時・症状等の改変禁止
    - **外部送信の最小化（必須）**：AIへ送るデータはallowlist方式とする。送ってよいもの＝呼び方（＋呼称サフィックス）、クラス名、年齢区分、当日の入力内容、直近7日分の連絡帳本文。送ってはいけないもの＝正式氏名、住所、保護者情報、既往歴・アレルギー・医療情報、児童票の詳細。児童票参照（§7.4）は将来フェーズでセキュリティ方針確定後に対応
    - AIプロフィール（園・クラス・職員ごとの文体設定）はテーブルだけ用意し、生成時に園プロフィールのみ反映する最小実装でよい（クラス・職員別の反映と学習は後続）
    - 職員操作：AI生成 / 直接編集 / 短く / 詳しく / やわらかく / 気遣い追加 / 重要事項明確化 / 作り直し
    - AI呼び出しは既存プロジェクトで使っているAPIキー管理・Edge Functions等の構成に合わせること（実装前に構成案を提示して確認を取る）

12. **職員編集・申請 → 管理者承認・差し戻し**
    - 管理者操作：そのまま承認 / 直接編集 / AI全文修正 / AI部分修正 / 自由指示によるAI修正 / 上書き承認 / 職員向けコメント / 差し戻し（理由コメント必須）
    - 差し戻し前後の文章、管理者修正前後の文章をすべて履歴保存
    - 管理者コメントは保護者向け本文に含めない
    - 承認期限：デフォルト17:00、園ごとに変更可能。期限前・超過時に通知
    - 管理者はMacのadmin_webに加え、iPad・iPhone（Flutterアプリ）からも承認・差し戻し・コメント・AI修正・直接編集ができること

13. **承認済み文章のコピー（コドモン運用）**
    - 承認済み文章のみコピー可能（コピー画面は最終文章を表示）
    - 基本は申請者がコピー、不在時は他職員・管理者が対応可能
    - コピー操作の履歴（誰がいつ）を記録

14. **通知**
    - 既存の通知・お知らせの仕組みを調査し、可能な限り再利用する
    - プッシュ通知（iPad・iPhone、アプリを閉じていても受信）：APNs構成が未整備なら、まず構成に必要な作業を洗い出して報告し、承認後に進める
    - 管理者向け：クラス活動申請 / 連絡帳申請 / 再申請 / 承認期限前 / 超過
    - 職員向け：クラス活動期限前 / 未入力 / 未申請 / 承認 / 管理者修正承認 / 差し戻し / 担当割当

15. **リアルタイム保存・同期**
    - 入力中の内容をリアルタイム保存（下書き自動保存）
    - 欠席情報・クラス活動・承認/差し戻し/コメントを複数端末へ即時反映
    - 通信断時は端末内へ一時保存し復旧後に同期（Flutterローカル保存→再送。競合時は「他職員の入力を上書きしない」原則に従う）

16. **個人日誌の同時生成・追記**
    - 連絡帳と同じ入力から、職員向けの個人日誌を同時生成（保護者向けと文章を分ける）
    - 記録観点：事実 / 援助 / 反応 / 経過 / 配慮 / 引継ぎ
    - AI生成後も自由追記可能、追記者・時刻を記録
    - 保護者へは自動公開しない
    - **初期デフォルト（設定で変更可能にする）**：管理者承認は不要 / 閲覧範囲は同一施設の職員＋管理者。※設計書上は未確定項目のため、デフォルト値をこの通り置き、設定画面から後で変更できるようにする

## 2. 設計書v0.1からの変更点（レビューによる修正）

実装時は以下を設計書の記載より優先すること。

1. **未登園アラート（§8.3）**：9:00固定ではなく「園児の登園予定時刻＋猶予分数」を基準にする。猶予分数は園ごと設定（デフォルト30分）。登園予定時刻データ（曜日別設定）が未実装の初期段階では、園ごとの固定時刻（デフォルト9:00）をフォールバックとして使う。※このアラート自体は登降園管理フェーズで実装（今回はスコープ外、設計余地のみ）
2. **家庭連絡帳未作成時の打刻ブロック（§21.1）**：打刻を止めない。登降園の打刻は安全管理の根幹のため必ず記録し、「未作成の警告表示＋職員側での確認フロー」に変更する。※家庭連絡帳・登降園QRは後続フェーズだが、この方針を前提に設計すること
3. **体温プルダウン（§21.2）**：35.0〜40.0℃に拡大。37.5℃以上選択時は登園基準の注意表示＋欠席申請への導線を出す。※後続フェーズ向けの方針
4. **午睡チェック間隔（§31）**：5分固定にせず、施設×年齢区分ごとの間隔マスタとする（例：0歳児5分・1〜2歳児10分）。※後続フェーズ向けの方針
5. **個人日誌の承認・閲覧範囲（§17・§34）**：上記1-16の初期デフォルトを採用し、設定で変更可能にする
6. **園児別担当（§11）**：「各園児の連絡帳は担当職員1名が作成、1職員は複数園児を担当可」と解釈を確定
7. **呼称（§5.3）**：性別デフォルト＋園児ごとの上書き可能
8. **AIへのデータ送信（§7.4×§35）**：allowlist方式を必須とし、児童票参照は将来フェーズへ
9. **備品利用→請求連携（§10.4）**：今回は記録のみ、請求連携は請求フェーズで実装
10. **保護者アプリ（§19以降）**：後続フェーズだが、保護者はAndroid端末利用者が必ずいるため、保護者アプリフェーズではFlutterのAndroidビルド対応が前提になる。共通基盤の設計でiOS/macOS固有機能に依存しすぎないこと

## 3. 進め方（必須）

1. まず既存コード・スキーマを調査し、以下を提示して**承認を得てから**実装に入ること：
   - 新規テーブル一覧とER概要（園児・クラス・在籍履歴・機能フラグ・連絡帳ワークフロー・監査履歴）
   - 既存ロール体系と保育業務3階層の対応表
   - RLS方針（職員業務と保育業務の分離）
   - AI呼び出しの構成案（どこでAPIを呼ぶか、キー管理）
   - Phase 0 → Phase 1 のマイグレーション分割案
2. マイグレーションは小さく分割し、各段階でbegin/rollbackの動作確認を行うこと（これまでの給与エンジン実装と同じ流儀）
3. 機能フラグOFFの状態で既存機能（勤怠・給与・申請・お知らせ・admin_web全画面）に影響がないことを確認してから、フラグONでの動作確認に進むこと
4. 実データ（実在園児の個人情報）はまだ投入しない。テスト用のダミー園児データで検証すること
5. output/配下に個人情報を含むファイルを生成する場合は.gitignore対象であることを確認すること

## 4. 今回実装しないもの（明示）

- 保護者アカウント・保護者アプリ全般（§19〜§29）
- 登降園QR・登降園管理（§20、§8.2デイリーボード、§8.3アラート本体）
- 請求管理（§30）・備品利用の請求連携
- 午睡チェック（§31）
- クラス写真（§32）
- カメラ・センサー連携（§33）
- 身体測定・発達記録・保育料プラン・曜日別登降園設定・園児台帳詳細項目（§5.5〜§5.9）
- ヒヤリハット・週案・月案・個人記録・要録・年間指導計画・保育安全計画

ただし、これらが園児ID・クラスID・保護者IDを軸に後付けできるよう、共通基盤の設計時に拡張ポイントとして考慮すること。
