## 0. 本書の位置づけと前提

### 0.1 対象アプリ

| アプリ | 本書での役割 |
|---|---|
| Ohana Kids(iPad保育業務、APP_MODE=childcare) | 主対象。ホーム画面・デイリーボード拡張・午睡チェック・クラス活動の実装先 |
| admin_web | 監査用の午睡チェック閲覧/編集、Instagram投稿の承認、タブ名変更、保育業務ナビの再編 |
| Ohana Family(parent_app) | クラス写真項目の削除、保護者からの連絡の承認済み表示 |
| Ohana Staff(職員スマホ) | 管理者・統括園長へのプッシュ通知の受信先 |

### 0.2 既存規約の遵守(最優先)

1. RLSは職員業務/保育業務職員側/保護者の3ドメイン完全分離を維持する。
2. 新機能はすべて機能フラグでデフォルトOFF。既存機能に影響を与えない形で段階実装し、試験施設(BABY MAHALOまたはMahalo Station)から有効化する。
3. 通知は既存のnotifications outbox + dispatch-pending-notifications(pg_cron毎分)に統一する。新しい通知経路を作らない。
4. マイグレーション番号は「着手時点の最新+1」で採番する(本書内の連番指定はしない)。staging適用→検証→俊の確認→本番の現行フローに従う。
5. 役職名の写像: 本書では「主任以上」「統括園長以上」と表記する。実装時は既存rolesテーブルの実ロール名に写像し、写像表を実装報告に含めること(v3.1統制版と同じ方針)。
   - 主任以上 = 主任(chief)・管理者(office_manager)・統括管理者・統括園長、およびそれより上位の役職
   - 統括園長以上 = 統括園長、およびそれより上位の役職
6. `docs/Ohana_Works_統合追加機能_実装統制設計書_v3_1_2026-07-30.md`(v3.1統制版)と整合させる。特に写真原本のR2保存(M4)・AIゲートウェイ=OpenRouter(M2)・ai_runsへの実行記録は本書のクラス活動/Instagram機能でも同じ基盤を使う。矛盾を発見した場合は実装前に俊へ報告する。

### 0.3 前提(俊に確認済み・仮置き含む)

- 【仮置き・要最終確認】Instagram投稿の単位は「施設ごとに1日1投稿」。OhanaGroupのInstagramアカウントは1つ(全施設共通)で、そこへ各施設の投稿が流れる。画像最大6クラス分=最大クラス数の大和オハナ保育園(6クラス)に対応。
- 【仮置き・要最終確認】投稿画像はクラスごとにアップロード写真の中から投稿用1枚を選択する(施設投稿=最大6枚のカルーセル。Instagramのカルーセル上限10枚に収まる)。
- 上記2点が異なる場合は俊の回答を受けて本書を改訂する。それ以外の仕様は確認済み。

## 1. ホーム画面(Ohana Kids)

### 1.1 要件

- Ohana Kids起動後の最初の画面としてホーム画面を新設する。
- 背景は白ベース。各機能区分をポップなアイコン付きの大きなタイルで表示し、タップで各機能へ遷移する。iPadの保育現場で直感的に使えるデザインとする。
- 全画面の左上にオハナワークスのロゴを配置し、これをホームボタンとする(どの画面からでもワンタップでホームへ戻れる)。

### 1.2 機能区分(確定・7区分)

| # | 区分 | 内容 |
|---|---|---|
| 1 | デイリーボード | 在籍状況サマリー・園児一覧・天気入力(§2) |
| 2 | 連絡帳 | 園連絡帳の作成・17時公開予約・公開(§2.4) |
| 3 | クラス活動 | 活動記録・写真アップロード・Instagram投稿(§4)。旧「クラス写真」を統合 |
| 4 | 午睡チェック | §3の新機能 |
| 5 | 保護者からの連絡 | 旧「保護者申請」。欠席・遅刻等の連絡の確認・承認 |
| 6 | 園内記録 | 既存機能 |
| 7 | 支援保育 | 既存機能 |

- 「保護者管理」「緊急連絡先」はホーム画面に置かない(admin_web側に残す。機能自体は削除しない)。
- 名称変更: 「保護者申請」→「保護者からの連絡」。Ohana Kids・admin_webのタブ名・画面タイトル・通知文言を全箇所置換する。DB上の識別子(テーブル名parent_requests等)は変更しない(表示名のみ)。

### 1.3 実装手順

1. Ohana KidsのルーティングにHomeScreenを追加し、childcareモードの初期画面をホームに変更する。
2. 共通AppBar(ロゴ=ホームボタン)をウィジェット化し、全画面に適用する。
3. アイコンは絵文字ではなくアイコンフォント/アセットで統一する。区分ごとに色分けしたポップなトーンで、ラベルは日本語。
4. 機能フラグ `childcare_home_enabled`(仮称、既存命名規約に合わせて可)でホーム画面自体を切替可能にし、OFF時は現行の画面遷移を維持する。

## 2. デイリーボード拡張(Ohana Kids / admin_web)

### 2.1 クラス絞り込み

- クラスのプルダウン(既定: 全クラス)で園児一覧を絞り込む。並び順はクラス(年齢区分順)→園児名。
- 注意: 同内容の「クラスプルダウン追加」は別指示(Phase Cクローズ直後の小タスク)で admin_web側に着手済み/実装済みの可能性がある。実装前に現状を確認し、済んでいる場合は同じUI部品・挙動をOhana Kidsへ展開する形にして二重実装を避けること。

### 2.2 在籍登園状況のリアルタイムサマリー

デイリーボード上部に当日のサマリーを常時表示する。定義は以下で確定。

| 項目 | 定義 |
|---|---|
| 在籍 | その日時点の在籍人数(child_class_enrollmentsの当日有効行) |
| 登園予定 | 在籍のうち欠席連絡が入っていない人数 |
| 出席 | その日一度でも登園した人数(降園済みを含む) |
| 欠席 | 欠席連絡が入っている人数 |
| 登園中 | いま園内にいる人数(登園済みかつ未降園) |

- クラスで絞り込むと、サマリーの人数もそのクラス単位に自動で切り替わる。
- 集計は既存のfetch_daily_board_for_office系RPCの拡張で返す(クライアント集計でも可だが、admin_webとOhana Kidsで数字が一致するようRPC側集計を推奨)。
- リアルタイム性: Supabase Realtimeの購読または30秒程度のポーリングで最新化する。実装コストの低い方を選び、選択理由を報告すること。

### 2.3 打刻漏れの登降園登録(代理登録)

- デイリーボードの園児行に「登園を登録」「降園を登録」ボタンを設置する(状態に応じて表示)。
- 時刻は職員が手入力する(例: 実際は8:30に登園していた)。
- 実行できるのは主任以上。変更と同時に承認扱いとする(別途の承認フローは設けない)。
- 記録はQR打刻と区別できる形で保存する: child_attendance_eventsに登録方法(kiosk_qr / staff_manual等)と実行職員IDを記録し、監査ログに残す。既存のWeb代理打刻(Phase D)の仕組みがあれば流用・整合させる。
- daily_child_statusの更新・保護者への「登園しました」通知は通常打刻と同じ経路に乗せるが、代理登録時に保護者通知を送るか否かはフラグで制御できるようにする(初期値: 送る)。

### 2.4 連絡帳の編集状況表示と17時公開予約

- 対象は園連絡帳(職員→保護者)。デイリーボードの園児行/クラス行に編集状況バッジを表示する: 下書き / 公開予約済 / 公開済。
- 公開予約: ワンプッシュで「当日17:00公開」の予約になるボタンを設置する。押下後に公開時刻を変更できるUI(時刻ピッカー)も用意する。
- 公開の単位: ①園児個別 ②クラス単位一括 ③施設一括、の3操作を提供する。
- 権限: 公開・公開予約・予約取消は主任以上のみ。一般職員は下書き作成・編集まで。
- 実装: published_at(実公開日時)とscheduled_publish_at(予約日時)を持たせ、pg_cronの毎分ジョブ(既存dispatcherと同居可)が到来した予約を公開処理する。公開時の保護者プッシュ通知は既存outbox経由。
- 予約済みの連絡帳を編集した場合は予約を維持したまま内容が更新される(再予約不要)。公開済みの再編集可否は現行仕様を踏襲する。

### 2.5 天気・気温・湿度の記録

- 施設ごとに1日1回、手入力で記録する。入力場所はデイリーボード上部(サマリーの近く)。
- 項目: 天気(晴れ/曇り/雨/雪/その他の選択式)、気温(数値、℃)、湿度(数値、%)。
- テーブル案: `daily_weather_records`(office_id, record_date, weather, temperature, humidity, recorded_by, recorded_at)。office_id×record_dateでユニーク。
- 当日中は誰でも上書き修正可。過去日の修正は管理者以上(admin_web)。
- 未入力の日はデイリーボード上に「未入力」を軽く表示する(強いアラートは不要)。

## 3. 午睡チェック(Ohana Kids + admin_web)

### 3.1 対象園児とセッション

- 0〜2歳児クラスの園児は必須対象(自動)。3歳以上は職員が当日任意で追加できる(体調がすぐれない園児を想定)。
- セッションの開始・終了:
  - 入眠の記録でチェック開始。園児個別の開始と、クラス一括開始の両方を用意する。
  - 起床の記録で終了(こちらも個別/一括)。
- 記録単位は園児個別。チェック間隔は5分。

### 3.2 記録項目

| 項目 | 記録方式 | 値 |
|---|---|---|
| 身体の向き | 値を記録する | 右 / 左 / 仰向け / うつ伏せ直し |
| 呼吸 | 確認ボタン(押した事実を記録) | ✓ |
| 顔色 | 確認ボタン | ✓ |
| 寝具の状態 | 確認ボタン | ✓ |

- 「5分前と変化なし」ボタン: 1タップで5分前の記録と同内容を当該スロットに登録する(園児個別)。さらに、変化のない園児をまとめて登録できるクラス一括版も用意する。
- 文言は短く(iPad画面幅の制約)。「うつ伏せ直し」の表記はこのまま使う。

### 3.3 UIレイアウト方針

- 縦軸=園児、横軸=5分刻みの時間スロットのグリッドを基本とする。各セルをタップで4項目の入力シートを開く。
- 未チェックのスロット(現在時刻を過ぎたもの)は色で警告表示する。
- 1画面に収まらない場合は横スクロール+現在時刻へ自動スクロール。
- タイマー通知(5分ごとのアラート)は実装しない。

### 3.4 15時のチェック漏れアラート(確定仕様)

- 毎日15:00 JSTのpg_cronジョブで、当日の午睡セッション中に未チェックのスロットがある園児を検出する。
- 漏れがある場合:
  1. デイリーボードおよび午睡チェック画面に警告バナーを表示する(施設・クラス・園児・漏れスロットが分かる形)。
  2. 当該施設の管理者(および統括園長)へ既存notifications outbox経由でプッシュ通知を送る。
- 15時以前に起床済みのセッションは、入眠〜起床の間のスロットのみを判定対象とする。

### 3.5 編集権限(確定仕様)

| 操作 | 一般職員 | 主任以上 | 管理者以上 |
|---|---|---|---|
| 当日のリアルタイム記録 | ○ | ○ | ○ |
| 当日の漏れスロットの事後記入(漏れ発生から30分以内) | ○ | ○ | ○ |
| 当日の漏れスロットの事後記入(30分超) | × | × | ○ |
| 過去日の追記・修正(admin_web) | × | × | ○ |

- 事後記入・修正はすべて「誰が・いつ・何を」の監査ログを残す(記録実時刻と対象スロット時刻を区別して保存)。
- admin_webに午睡チェックの閲覧・編集画面を新設する(監査対応: 日付・施設・クラスで絞り込み、漏れの有無が一目で分かる一覧+セル編集)。

> 既知の挙動(2026-08-04): admin_webの区間編集(set_nap_interval)の権限判定は起床優先(coalesce(新起床,新入眠))のため、起床をnow付近で書きつつ古い入眠を同時修正すると入眠側の時刻は権限判定に使われない。当日内限定・監査ログありのため許容する。

### 3.6 テーブル案

- `nap_sessions`: id, child_id, office_id, class_id, session_date, sleep_start_at, wake_up_at, is_required(必須対象か任意追加か), added_by, created_at
- `nap_checks`: id, session_id, slot_at(5分刻みの正時刻), body_position(right/left/supine/prone_corrected), breathing_checked, complexion_checked, bedding_checked, checked_by, checked_at(実記録時刻), source(realtime/late_entry/admin_edit)
- チェック漏れ判定・30分ルールはslot_atとchecked_atの比較で行う。RLSは保育業務ドメインの既存パターンに合わせる。

## 4. クラス活動とInstagram投稿

### 4.1 クラス活動記録(旧クラス写真の統合)

- 新カテゴリ「クラス活動」を新設する。クラス別に当日の活動内容(テキスト)を記載し、その延長で写真をアップロードする。
- 旧「クラス写真」は単独区分として廃止し、クラス活動内の写真機能に統合する。既存のclass_daily_photos/バケットは移行または流用し、二重管理にしないこと。
- 写真の保存はv3.1のM4方針に従う: 原本をR2へ非公開保存(今後の撮影分)。この原本が写真販売(M4)とInstagram投稿の両方の供給元になる。
- 投稿用写真の選択: クラスごとに、アップロードした写真の中から「Instagram投稿用」を1枚選択できる(§0.3の仮置き前提)。

### 4.2 保護者アプリのクラス写真削除(確定仕様)

- Ohana Family上の「クラス写真」項目・画面・導線を削除する(機能フラグOFF化+UIからの導線除去)。
- 保存済みの写真データは削除せず保持する(閲覧経路のみ閉じる)。
- 保護者への写真提供は、実装中の写真販売機能(ダウンロード販売のみ)に一本化する。本書ではその前提の整合のみ取り、写真販売自体はv3.1 M4のスコープとする。

### 4.3 投稿パイプライン(確定フロー)

1. 各クラスが「クラス活動の作成完了+写真アップロード」を行う。
2. 施設内のすべてのクラスが完了した時点で、統括園長以上へ承認依頼の通知を送る(notifications outbox経由。全クラス完了までは通知しない)。
3. AIが投稿文面を生成する(§4.4)。参照元は写真アップロードがあったクラスの活動コメント。
4. 統括園長以上が承認画面で「写真(最大6クラス分)+生成文面」を確認する。文面は手直し可能。写真の差し替え・除外も可能。
5. 承認するとInstagramへ投稿される(施設ごとに1日1投稿・カルーセル最大6枚+文面。§0.3の仮置き前提)。
6. 却下時はクラスへ差し戻し通知を送る。
- 承認操作はadmin_web(PC)とスマホの両方から行えること(通知タップ→承認画面で完結)。
- 状態遷移: draft(クラス作成中)→ ready(全クラス完了)→ ai_generated → approved → posted / rejected。各遷移の実行者・日時を記録する。

### 4.4 AI文面生成

- 実行基盤はv3.1 M2のOpenRouterゲートウェイを使用し、実行履歴をai_runsに記録する(M2未完成の場合は、後でM2に載せ替え可能なProvider抽象を挟んだ最小実装とし、直書きしない)。
- 生成要件:
  - 入力: 当日の各クラスの活動コメント(写真アップロードがあったクラスのみ)、施設名、日付。
  - 出力: 保育園の公式Instagram投稿として適切なトーンの文面。園児の個人名は出力しない。
  - ハッシュタグはちょうど5つ含める。
  - リーチ最大化の構成をプロンプトに組み込む: 冒頭1〜2行で内容が伝わるフック(フィードでは冒頭のみ表示されるため)、本文は改行を活かした読みやすい段落、絵文字を適度に使用、ハッシュタグは「地域系(例: 神奈川/大和市)+保育系(例: 保育園/保育士)+内容系(その日の活動)」を混ぜ、超ビッグタグのみに偏らせない。文末に園の紹介・採用や見学への軽い導線を1行。
  - プロンプトはコード直書きではなく編集可能な形(document_templates拡張またはDB上のプロンプト管理)で保持し、俊が文面の方向性を調整できるようにする。
- 生成失敗時は空文面のまま承認画面へ進め、手入力で投稿できるフォールバックを用意する。

### 4.5 SNS掲載可否(肖像権)— 第1段を実装

- 園児マスタ(children)に「SNS掲載可否」フラグを追加する(既定: 掲載不可。保護者の同意を確認した園児のみadmin_webで可に変更)。admin_webの園児マスタ画面に設定UIを追加する。
- 承認画面に、当該施設の「SNS掲載NG園児」の一覧を常時表示し、統括園長が目視確認のうえ承認する運用とする。
- 顔検出による自動チェック(第2段)は本書のスコープ外の将来拡張とする。設計上は写真テーブルに検査結果を持てる拡張余地(nullable列またはサブテーブル)だけ確保しておく。

### 4.6 Instagram連携の技術方針と事前準備

- 連携はMeta公式のInstagram Graph API(Content Publishing)を使用する。カルーセル投稿(最大10枚)に対応すること。
- 実装はEdge Function経由とし、アクセストークンはVaultに保存する(長期トークンの更新運用も設計に含める)。
- API制限(投稿数/24hのクォータ、画像はJPEG推奨・アスペクト比制限)をバリデーションに組み込む(アップロード時に自動リサイズ/変換)。
- 事前準備(俊の作業。Claude Codeは手順書を提示する):
  1. OhanaGroupのInstagramをプロアカウント(ビジネス)へ切替
  2. Facebookページを作成しInstagramと連携
  3. Meta開発者アプリの作成・審査・アクセストークン発行
- 上記が完了するまでは、投稿処理の直前までを実装し「Instagram連携未設定」の状態で承認→投稿予約まで動く形にしておく(モック投稿でE2E確認可能にする)。

### 4.7 テーブル案

- `class_activities`: id, office_id, class_id, activity_date, content(活動コメント), status(draft/completed), completed_by/at

## 7. 実装フェーズと受入基準

依存関係の少ない順に4フェーズへ分割する。各フェーズ完了ごとにstaging検証→俊の確認を挟む。

### Phase 1: ホーム画面+名称変更
- 受入: ホーム7区分から各機能へ遷移できる。全画面のロゴからホームへ戻れる。「保護者からの連絡」への名称変更が全画面に反映。フラグOFFで従来動作。

### Phase 2: デイリーボード拡張(§2全部)
- 受入: サマリー5項目がクラス絞り込みに連動して正しい数字を出す(欠席連絡・登園・降園の各操作後に検証)。代理登録がstaff_manualとして監査ログに残る。ワンプッシュで17時公開予約→17時に自動公開→保護者に通知が届く。時刻変更・クラス一括公開・個別公開が動作。天気の1日1回入力と上書き。

### Phase 3: 午睡チェック(§3全部)
- 受入: クラス一括入眠→5分グリッドに記録→「変化なし」1タップ複製→起床終了の一連が動作。30分ルールが境界値(29分/31分)で正しく効く。15:00のcronで漏れ検出→デイリーボード警告+管理者プッシュの両方が届く。admin_webで過去日を管理者のみ編集でき、監査ログが残る。

### Phase 4: クラス活動+Instagram(§4)+保護者アプリのクラス写真削除+§5
- 受入: 全クラス完了時のみ統括園長へ通知される(1クラスでも未完了なら通知されない)。AI文面がハッシュタグ5つ付きで生成され、承認画面で編集できる。NG園児一覧が承認画面に表示される。モック投稿でE2Eが通る(実投稿はビジネスアカウント準備完了後)。parent_appからクラス写真の導線が消えている。保護者からの連絡の承認が保護者アプリで確認済み表示になる。

各フェーズで、dart analyze / tsc / eslint / next build をクリーンにしてからコミットする。ルーチンの検証・フェーズ内の進行は俊の確認を待たずに進めてよいが、フェーズ完了時のstaging検証結果は必ず報告する。
