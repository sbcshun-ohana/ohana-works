# Ohana Works 設計指示書 — ヒヤリハット・事故報告書と週次AI集計(会議資料生成)

作成日: 2026-08-07 / 作成: 俊 + Claude(Fable) / 実装: Claude Code

---

## 0. 目的と前提

- コドモンで運用中の「ヒヤリハット・事故報告書」をOhana Worksに再現し、さらに週次でAIが全施設の事案を集計・分析して金曜の職員会議資料を自動生成する。コドモンにない付加価値は後半の週次集計にある。
- 既存規約(RLS3ドメイン分離、機能フラグでデフォルトOFF、notifications outbox、マイグレーション採番=着手時点の最新+1、staging→本番、実ロールへの権限写像表の提示)は既存設計指示書§0と同一。AI生成はM2のOpenRouterゲートウェイを使用しai_runsに記録する(M2未完成時はProvider抽象を挟む)。
- 入力様式はコドモンの現行フォーマット(俊提供のスクリーンショット8枚)を忠実に踏襲する。職員が慣れている項目構成を変えないことが移行成功の条件。
- 対象アプリ: 入力・閲覧はOhana Kids(iPad)とadmin_webの両対応。承認はadmin_web+スマホ(通知から承認画面へ)。**Ohana Kidsのホーム画面に8区分目「ヒヤリハット・事故報告」を追加する**(Phase 1実装済みのホーム画面への区分追加)。

## 1. 報告書の様式

### 1.1 種別(単一フォーム+3区分切替)

コドモンと同じく1つのフォームで種別をタブ切替する: **ヒヤリハット / 園内対応(軽傷) / 病院搬送(重大事故)**。
- ヒヤリハット=事故が起こらなかった際に何が危険だったかの記録
- 事故報告書=軽症でも実際に事故となった内容の記録(処置をしない転倒でも事故報告書)
- この定義を新規作成画面の種別選択部に短いヘルプテキストとして表示する(入力者の迷い防止)。

### 1.2 共通項目(全種別)

| 区画 | 項目 |
|---|---|
| ヘッダ | 記入者(自動)/主任(承認者・自動記録)/園長(承認者・自動記録)/状態 |
| 対象者(必須) | 園児(複数選択可)・クラス・年齢・性別(園児マスタから自動)。職員が対象の場合は職員選択 |
| 基本 | 表題(既定値「ヒヤリハット・事故報告書」)/発生時間(日時) |
| 発生場所 | チェックボックス21種(保育室・ホール・廊下・階段・玄関・トイレ・ベランダ・テラス・総合遊具・滑り台・ジャングルジム・ブランコ・鉄棒・砂場・園庭・門・自転車・プール・手洗い場・道路・公園)+その他自由記述。複数選択可 |
| 経緯 | どういう作業・動作をしている時(カテゴリ選択+自由記述)/どのような状態となり(カテゴリ選択+自由記述)/どうなった(自由記述) |
| 現場写真・図 | 画像アップロード(複数可、R2非公開保存) |
| 現場の人員 | 保育士◯名/担当保育士◯名/園児◯名/目撃者◯名(数値) |
| 原因問題点 | 9行(システム・ルール/建物・設備/道具・もの/食べ物/周辺状況/子どもの関心/子ども同士の関わり/保育士の配慮/その他)×2列(何が/どう問題だったか)。空欄可 |
| 今後の改善策 | 自由記述 |
| 保護者連絡 | 複数行: 時刻/連絡した職員(選択)/連絡相手/連絡内容・相手の反応 |
| 経過と観察記録 | 複数行: 時刻/対応した職員(選択)/経過・連絡・報告 |
| 備考 | 自由記述 |

- 「どういう作業・動作をしている時」「どのような状態となり」のカテゴリ選択肢はコドモンの実選択肢を確認できないため、初期値として保育現場の標準的な区分(作業・動作: 食事/睡眠/遊び/移動/排泄・着脱/水遊び・プール/散歩・戸外/行事/その他。状態: 転倒・転落/衝突/挟み込み/誤飲・誤嚥/咬傷・引っかき/やけど/溺水/アレルギー/その他)をルックアップテーブルでシードし、admin_webから管理者以上が追加・編集できるようにする。発生場所・診察科等の選択肢も同様にルックアップ管理とする(コード直書きにしない)。

### 1.3 病院搬送(重大事故)のみの追加セクション

種別で「病院搬送(重大事故)」を選んだ場合のみ以下を表示する:

| 区画 | 項目 |
|---|---|
| 医師の診断(複数追加可) | 診療有無(あり/なし)/受診同意(あり/なし)/診察引率者(職員選択)/医療機関名/医師名/診察科(外・整形・脳神経・形成・皮膚・歯・耳鼻咽喉・眼・泌尿器+その他)/受診内容(診察のみ・レントゲン検査・血液検査・CT検査+その他)/処置内容(処置なし・消毒・縫合・テーピング・包帯固定・ギブス固定・シーネ固定・湿布・点眼・歯の固定・肘内障の整復+その他)/医師の指示(今後の登園可/登園不可)/処方薬(なし・内服薬・外用薬+その他)/治療期間 |
| 保護者連絡(受診後) | 複数行: 時刻/連絡した職員/連絡相手/連絡内容・相手の反応 |
| 保育課連絡(受診後) | 複数行: 時刻/連絡した職員/連絡相手 |

- 自治体への提出様式(重大事故の行政報告)は**今回スコープ外**(俊が様式を調査してから決定)。ただし保育課連絡の記録がその一次情報になるため、将来の様式出力を想定してデータは構造化して保持する。

## 2. 承認フローと権限

### 2.1 状態遷移(2段階承認)

```
下書き(draft) → 申請中(submitted・主任承認待ち) → 主任承認済(chief_approved・園長承認待ち) → 承認済(approved)
```

- 承認者: 1段階目=施設の主任以上(主任・管理者。小規模施設は管理者が担う)、2段階目=統括園長(大原園長)以上。
- 各承認時に承認者と承認日時を記録し、ヘッダの主任欄・園長欄に自動表示する。**approved_at(園長承認日時)が週次集計の「承認日」になる**。
- 差し戻し: 各承認者は理由を付けて差し戻せる(→draft、記入者へ通知)。承認済みの取消は統括園長以上のみ(コドモンの「承認の取消し」相当)。
- 通知(すべて既存outbox経由): 申請時→当該施設の主任以上へ / 主任承認時→統括園長へ / 承認完了・差し戻し時→記入者へ。
- 編集可否: draftは記入者と主任以上、submitted以降の編集は差し戻しを経由する(承認後の無断改変を防ぐ)。

### 2.2 権限まとめ

| 操作 | 一般職員 | 主任以上(施設) | 統括園長以上 |
|---|---|---|---|
| 作成・下書き編集・申請 | ○ | ○ | ○ |
| 1段階目承認・差し戻し | × | ○(自施設分) | ○ |
| 2段階目承認・差し戻し・承認取消 | × | × | ○ |
| 閲覧(全施設・全状態) | ○ | ○ | ○ |
| 週次会議資料の閲覧 | ○ | ○ | ○ |
| 週次会議資料の編集・再出力 | × | ○ | ○ |
| ルックアップ選択肢の管理 | × | 管理者以上 | ○ |

- 閲覧は全職員・施設横断でOK(俊確認済み)。保護者からは一切見えない(RLSで保育業務ドメインに閉じる)。

## 3. 週次AI集計(会議資料の自動生成)

### 3.1 集計ルール(確定)

- 週の定義: **木曜〜水曜**。毎週**木曜の朝(6:00 JST提案、pg_cron)**に前週分を自動生成し、金曜の職員会議で使用する。
- 対象: **全施設横断で1つの資料**。**承認済み(approved)のみ**を、**承認日(approved_at)ベース**で「前週木曜0:00〜水曜23:59に承認されたもの」として抽出する(発生日ベースではない点に注意。承認遅れの事案は承認された週の資料に載る=漏れが出ない設計)。
- 種別: ヒヤリハット・園内対応・病院搬送の**すべての事案**を対象とする。
- 0件の週も資料は生成する(「今週の事案は0件」+前週までの累計傾向を記載)。

### 3.2 資料の構成

数値・件数はSQLで確定集計し、AIには**文章化・分析・提案のみ**を担わせる(AIに計算をさせない。幻覚対策として、AIプロンプトには集計済みの数表と各事案の本文を渡す)。構成:

1. 今週のサマリー: 総件数、施設別・種別・クラス/年齢別・発生場所別・時間帯別・原因分類別の件数表
2. 事案一覧: 全件を施設/クラス/種別/発生日/概要1行で列挙
3. 主要事案の詳細: 特に共有すべき事案(病院搬送は必須、他はAIが重要度判断)の経緯・対応・対処方法
4. 傾向分析: 今週の特徴、繰り返し発生しているパターン、前週比・累計での傾向(過去の週次データを参照)
5. 再発防止に向けた取り組みの提案: 原因問題点マトリクスの記載を横断して、具体的で実行可能な取り組みを提案(誰が・何を・いつまでに、のレベルまで踏み込む)
6. 会議での確認事項: 議論すべき論点の箇条書き

- できるだけ多くの情報を含める方針(俊確認済み)。ただし会議で使える分量(A4で数ページ程度)に収める。
- 園児名の扱い: 資料内は園児名を記載してよい(職員限りの内部資料のため)。ただしAIプロンプトの設計上、出力に不要な個人情報(生年月日等)は渡さない。

### 3.3 画面・編集・出力(確定)

- admin_webに「週次会議資料」画面を新設: 週の一覧→資料の表示。**生成後の本文を主任以上が直接編集できるエディタ**を備える(そのまま会議で使うため、誤りの修正・追記が必須要件)。編集履歴(最終編集者・日時)を保持する。
- 出力: **画面表示+Word(docx)+PDF**の3形態。docx/PDFは編集後の最新本文から生成する。既存の帳票生成基盤(v3.1 M5雇用文書等)があれば流用し、なければライブラリを選定して報告。
- 「再生成」ボタン: AIで再生成できるが、手編集済みの場合は上書き確認を出し、編集済み本文は別版として保持する(編集の消失防止)。
- 生成完了時に主任以上・統括園長へ通知(outbox経由)。資料の閲覧は全職員可。

### 3.4 テーブル案

- `incident_reports`: id, office_id, report_type(hiyari/minor/hospital), status(§2.1), title, occurred_at, activity_category_id+activity_text, condition_category_id+condition_text, outcome_text, staff_counts(jsonb: 保育士/担当/園児/目撃者), cause_matrix(jsonb: 9行×2列), improvement_text, note, created_by, submitted_at, chief_approved_by/at, approved_by/at(=園長承認・週次集計キー), rejected_reason
- 子テーブル: `incident_report_children`(対象園児・複数), `incident_report_staff`(対象職員), `incident_report_places`(発生場所・複数+その他), `incident_report_photos`, `incident_report_guardian_contacts`(区分: 通常/受診後), `incident_report_progress_logs`, `incident_report_diagnoses`(病院搬送のみ・複数), `incident_report_childcare_dept_contacts`
- ルックアップ: `incident_lookup_options`(kind: place/activity/condition/med_department/med_exam/med_treatment/prescription, label, sort_order, is_active)
- 週次: `weekly_incident_digests`(id, period_start, period_end, generated_at, ai_run_id, content_md(編集可能な本文), edited_by/at, docx_key, pdf_key)
- approved_atへのインデックス(週次抽出用)。

## 4. 実装フェーズと受入基準

### Phase A: 報告書様式+承認フロー
- 受入: 3種別の作成→申請→主任承認→園長承認→承認済の一連が動作し、各段階で通知が届く。病院搬送でのみ医師の診断等が表示・保存される。差し戻しで理由つきの通知が届き再申請できる。承認済みの取消は統括園長のみ。全職員が全施設の報告書を閲覧でき、保護者アカウントからは一切見えない。ルックアップ選択肢の追加が管理画面からでき、既存データを壊さない。ホーム画面に区分が追加されている。

### Phase B: 週次集計+AI生成+出力
- 受入: 木曜朝のcronで前週(木〜水・承認日ベース)の全施設分が抽出され、資料が生成される。数表の件数がSQL集計と一致する(AIの本文中の数字も含めて検証)。0件の週も資料が生成される。生成完了通知が届く。主任以上が本文を編集でき、編集後にdocx/PDFを出力すると編集内容が反映されている。再生成時に手編集が失われない。一般職員は閲覧のみで編集ボタンが出ない。

各フェーズでstaging検証→俊へ報告。dart analyze / tsc / eslint / next build クリーンでコミット。
