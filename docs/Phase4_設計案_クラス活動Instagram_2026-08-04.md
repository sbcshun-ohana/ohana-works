# Phase 4 設計案: クラス活動 + Instagram投稿(グループ全体1日1投稿)

作成: 2026-08-04 / **設計のみ・実装なし**。俊の判断後に実装フローへ。
設計の正: `docs/Ohana_Works_設計指示書_ホーム画面_..._2026-08-03.md` §4 を、下記の**確定変更**で上書き。

## 0. 確定した前提(2026-08-04 俊)
- **投稿単位 = グループ全体で1日1投稿**(施設ごとではない ← §4.3/§0.3 の「施設ごと1投稿」を上書き)。
- **投稿画像 = AIに選ばせる**(職員が選ぶのではない ← §4.1 の「クラスごと1枚を職員が選択」を上書き)。
- 投稿前に**統括園長以上の承認が必須**。AI文章生成(**ハッシュタグちょうど5つ**)。
- 承認依頼通知は**全クラスがクラス活動作成+写真アップロード済みのときのみ**。
- 保護者アプリでは**クラス写真を配信しない**(Ohana Family の導線削除・データは保持)。

---

## 1. 詰めた論点と設計方針

### 1.1 グループ全体1投稿での写真選定(複数施設・最大6クラス/施設)
- **母集団**: その日に「クラス活動作成+写真アップロード」があった**全施設・全クラス**の写真(施設4×最大6クラス=最大24クラス分、各クラス複数枚あり得る)。
- **投稿枚数**: Instagram カルーセルは**最大10枚**。→ **グループ全体1投稿=最大10枚**を母集団から選定。
- **AI選定(投稿画像=AIに選ばせる)の基準案**:
  1. **多様性**: 施設・クラスが偏らないよう分散(1クラス最大1〜2枚を目安)。
  2. **画質**: ブレ・露出・被写体の明瞭さ(要**画像認識AI=vision**)。
  3. **NG児回避**: SNS掲載NG児(§1.2)が写る写真は候補から除外(第1段は**フラグ+目視**、vision顔検出は将来)。
  4. **活動の代表性**: クラス活動コメントと整合する写真を優先。
  - **重要**: 「画像そのものを見て選ぶ」には**vision対応AIが必須**=M2契約後(§1.4)。**契約前は代替セレクタ**(例: 各クラスの先頭1枚を順に、施設分散で10枚まで)を置き、後でAI選定に差し替える。
- **差し替え・除外の可否**: **承認画面で統括園長以上が差し替え・除外・並べ替え可**(AIの選定は「提案」、最終決定は承認者)。これで「AIに選ばせる」+人手の最終責任を両立。母集団の全写真を承認画面に一覧し、選定済み10枚をハイライト+差し替え候補を表示。

### 1.2 肖像権NG児の除外の担保
- **DB**: `children.sns_publish_allowed boolean not null default false`(**既定=掲載不可**)。admin_web 園児マスタに設定UI(保護者同意を確認した児のみ true・**設定権限=管理者以上=主任以上/または統括園長。要確認**)。
- **運用(第1段=確定スコープ)**:
  1. 写真アップロード時: NG児が写らないよう職員が配慮(運用ルール)。
  2. 承認画面に**当該投稿の対象施設の「SNS掲載NG児一覧」を常時表示** → 統括園長が**目視確認**のうえ承認。
  3. AI選定は、NG児が「タグ付け/紐付け」された写真を候補から除外(※写真と児の紐付けが無い現状は、目視が主担保)。
- **顔認証(自動チェック)は現実的でない**(顔検出AI+園児ごとの顔登録+同意の法的整理が必要で、初期スコープ過大)。→ **第1段はフラグ+目視**。写真テーブルに**検査結果を持てる拡張余地(nullable列 or サブテーブル)だけ確保**(将来の顔検出用)。
- **代替運用の明記**: 「NG児が写り込んだ場合は承認者が除外」「判断に迷う写真は使わない」を運用手順書に含める。

### 1.3 Instagram Graph API の前提
- **ビジネスアカウント必須**(プロアカウント+Facebookページ連携)。→ 別紙 `docs/Instagram_ビジネスアカウント切替手順_2026-08-04.md`。
- **Content Publishing API**: カルーセル最大10枚。画像は公開URL(JPEG推奨)を Meta 側が取得 → **原本はR2(M4)or Storageで一時公開URL**が要る。
- **アクセストークン**: 長期トークン(約60日)。**Vaultに保存**し、失効前に**リフレッシュ運用**(cron or 手動)。トークン失効時は投稿失敗→エラー記録+再認証導線。
- **クォータ/制約**: 1アカウント **25投稿/24h**(グループ1投稿/日なら余裕)。アスペクト比 4:5〜1.91:1、画像サイズ上限 → **アップロード時に自動リサイズ/変換**(要画像処理)。
- **実装は Edge Function 経由**(トークンをクライアントに出さない)。

### 1.4 AI呼び出しの前提(M2未締結)
- 現状 `generate-contact-note` は **ANTHROPIC_API_KEY 未設定でモック**。M2(OpenRouterゲートウェイ)も未完成。
- **契約前に作れる範囲**:
  - Provider抽象(`callAI()`)を挟んだ**文面生成のスタブ**(mock文面 or 手入力フォールバック)。
  - **画像選定のヒューリスティック版**(vision無し・メタデータ/枚数配分で10枚選定)。
  - 実行履歴 `ai_runs` への記録枠。
- **契約後に結線する範囲**:
  - 文面生成を M2(OpenRouter)実呼び出しへ差し替え(プロンプトは `document_templates` 拡張 or DB管理で俊が調整可能に)。
  - **画像選定を vision AI へ**(画質・被写体・NG回避の判定)。
- **切り分けの原則**: AI呼び出し箇所は**すべて Provider抽象の内側**に隔離。契約前でもパイプライン全体(承認・投稿予約・モック投稿E2E)が動くこと。

## 2. データ設計案(実装時に確定)
- `children.sns_publish_allowed boolean not null default false`(掲載可否・既定不可)。
- `class_activities`: id, office_id, class_id, activity_date, content(活動コメント), status(draft/completed), completed_by/at。
- 写真: 既存 `class_daily_photos` を拡張(`activity_id` FK, `is_selected_for_post`, `r2_key` 等)**または**後継テーブルへ移行。**M4写真販売の設計と衝突しないよう着手時にv3.1 M4節を確認**。顔検査結果の nullable 拡張余地を確保。
- `instagram_group_posts`(グループ全体1投稿): id, post_date(**ユニーク=1日1投稿**), status(draft/ready/ai_generated/approved/posted/rejected), caption_ai, caption_final, ai_run_id, selected_photo_ids(jsonb・最大10), approved_by/at, posted_at, instagram_media_id, error_detail。
  - ※「グループ全体」なので office_id は持たず、複数施設の写真を横断参照。
- `ai_runs`: 既存/新設のAI実行履歴(M2載せ替え可能な形)。

## 3. 状態遷移(§4.3を単位=グループへ調整)
`draft`(各クラス作成中)→ `ready`(**対象日の全クラスがクラス活動+写真アップ完了**)→ `ai_generated`(文面+画像選定生成)→ `approved`(統括園長以上)→ `posted`(Instagram投稿)/ `rejected`(差し戻し)。各遷移の実行者・日時を記録。
- **通知**: `ready` 到達時に統括園長以上へ承認依頼(全クラス完了まで通知しない)。却下時はクラスへ差し戻し通知。承認は admin_web(PC)+スマホ両対応(通知タップ→承認画面)。

## 4. フェーズ分割案
- **Phase 4a(M2契約前・実装可能)**:
  - DB(class_activities / instagram_group_posts / sns_publish_allowed / class_daily_photos拡張 / ai_runs)。
  - パイプライン状態遷移+全クラス完了判定+承認依頼通知。
  - admin_web: クラス活動作成、写真アップロード(既存 class_daily_photos 流用)、SNS掲載可否UI(園児マスタ)、**承認画面**(写真プール+選定ハイライト+差し替え/除外、NG児一覧、文面編集)。
  - AI = Provider抽象で**mock文面+ヒューリスティック画像選定**。
  - **モック投稿でE2E**(Instagram未設定でも承認→投稿予約まで動く)。
  - parent_app: クラス写真導線の削除(フラグOFF+UI除去)。
- **Phase 4b(M2契約後)**: 文面生成を実AI(OpenRouter)へ、画像選定を vision AIへ差し替え(Provider内側のみ改修)。
- **Phase 4c(Instagramビジネスアカウント準備後)**: Edge Function で実 Graph API 投稿(Vaultトークン・カルーセル・自動リサイズ・クォータ検証・トークンリフレッシュ)。
