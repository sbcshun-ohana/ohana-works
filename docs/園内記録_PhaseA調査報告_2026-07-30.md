## 2. 名称衝突の確認(区分名「個人日誌」と既存テーブル`child_personal_journals`)

**設計書§7.3の表示名確定を受けての追加確認事項。**

- `child_personal_journals` を閲覧・一覧表示する**画面・メニュー項目はadmin_web・Ohana Kids・parent_appのいずれにも存在しない**。
- `admin_web/src/app/childcare/contacts/page.tsx`(268〜297行目)と`lib/services/childcare_service.dart`(365〜410行目)から書き込み(insert/update)のみ行われており、これは連絡帳(`child_daily_contacts`)のAI生成時に「連絡帳本文+個人日誌」を同時生成して保存する副次的な書き込みである。
- 既存のRPC `fetch_personal_journal`(migration 20260714000067)はDBに存在するが、**どのUIからも呼び出されていない**(未使用)。
- `childcare_office_settings.personal_journal_visibility_scope`(`same_office_staff_and_admin` / `admin_only`)という閲覧範囲設定も存在するが、対応する閲覧画面がない状態で設定項目だけが用意されている。

**結論**: 現時点でユーザーが画面上で「個人日誌」という表示名の衝突を目にすることはない(表示画面が存在しないため)。ただし将来`child_personal_journals`の閲覧画面が追加された場合は、園内記録の区分表示名「個人日誌」との混同に注意が必要。対処方針(表示名を変える/据え置く)は俊さんの判断に委ねる。

## 3. child_personal_journals の現状確認

- 実データ件数: ステージング0件、本番0件(上表と同じ)。

## 4. 再利用する既存機構の確認(Phase Bでそのまま従う流儀)

### 4.1 職員権限判定関数(Phase 2/3で使用)

| 関数 | 用途 |
|---|---|
| `my_employee_id()` | 現在ログイン中の職員IDを解決 |
| `has_childcare_office_access(office_id)` | 「自施設」判定の基礎(保育業務ドメインの施設アクセス権) |
| `manages_childcare(office_id)` | chief/office_manager/director/system_adminの役職チェック(has_childcare_office_access内部で使用) |
| `is_support_childcare_chief(office_id)` | Phase3で新設した「主任以上」判定の実例。**園内記録では同じロジックで独自関数`is_child_internal_notes_chief`を新設する**(D3方針: ドメインごとに権限関数を分離し、承認ロジックを機能間で共有しない。Phase3がPhase2の関数を再利用せず独自に持ったのと同じ理由) |
| `is_support_childcare_office_approver(office_id)` | 施設ごとの直接指定型の承認者判定(園内記録では不要、参考として記載) |
| `is_system_admin()` | 全施設アクセスの最終バイパス |

### 4.2 機能フラグ機構(137番)

- グローバル登録: `insert into feature_flags (feature_key, name, description, default_enabled) values (...)`(137番98〜101行目の書式をそのまま踏襲)
- 施設単位の有効化: `feature_flag_office_overrides`への`exists()`ガード付きinsert(seed_staging.tsで確立した環境非依存パターンをPhase Bのシードでも使う)
- 判定関数: `is_childcare_enabled_for_office`/`is_support_childcare_enabled_for_office`と同型の`is_child_internal_notes_enabled_for_office(office_id)`をPhase Bで新設する(3段階のcoalesce: employee override → office override → default_enabled)

### 4.3 支援保育RPC群(140番)のエラー処理・監査呼び出しの流儀

- `language plpgsql security definer set search_path = public`を全RPCに付与
- 権限確認は関数本体の**最初**に行い、`raise exception 'not authorized';`(理由を詳細化しない)
- 対象レコードが存在しない場合は`raise exception '<entity> not found';`(例: `'application not found'`)
- 入力値バリデーションは`raise exception 'invalid <field>';`
- 読み取り専用RPCには`stable`を付与
- `log_sensitive_access(p_screen text, p_target_employee_id uuid, p_target_data text)`の呼び方: 対象が職員でない場合(今回は児童)は**`p_target_employee_id`にnullを渡し、`p_target_data`に文脈を文字列で記述する**(`fetch_payroll_transfer_recipients`と同じパターン)。例: `perform log_sensitive_access('園内記録閲覧(fetch_child_internal_notes)', null, format('child_id=%s', p_child_id));`
