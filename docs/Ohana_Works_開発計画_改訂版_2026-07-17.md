## 2. GPT文書からの主な修正点（実態との差分）

1. **保護者アプリは全機能実装済み**。GPT文書は「これから公開順に作る」前提だったが、実際は6機能（お知らせ閲覧・申請・家庭連絡帳・園連絡帳・クラス写真・登降園QR）すべて実装・実機E2E確認済み。残タスクは「作る」ことではなく「施設・クラス・機能単位の段階公開フラグを実装する」こと。
2. **保育業務のWeb移行は最終形として維持しつつ、当面はFlutter版（Ohana Kids）を育てる**。すでにAPP_MODE=childcareが実機確認済みのため、Web版（childcare.ohanaworks.jp）への移行は後段フェーズに配置。Flutter版への新規機能追加は「Web移行時に移植コストになる」ことを認識した上で許容する。
3. **サブドメイン構成（admin/childcare.ohanaworks.jp）は後回し**。独自ドメイン取得は当面スコープ外。現行のVercelドメインで運用継続。
4. **フェーズ体系は新しいPhase 0〜5に統一**。ただし実装済み内容を反映して中身を再定義（旧Phase 0/1/Aの成果はすでに大部分が完了済みとして扱う）。
5. **試験施設の目安を明記**。保護者アプリはBABY MAHALOまたはMahalo Stationから。職員アプリは全職員同時スタート。

3. 試験施設：保護者アプリはBABY MAHALOまたはMahalo Stationから開始見込み（正式決定は後日・ハードコード禁止）。職員アプリは全職員同時スタート。
4. グループ連絡：「管理職以上」「各クラスの担当」「プロジェクトチーム」など、特定のグループにだけ職員連絡ができる機能として作る。
5. 独自ドメイン取得：後回し。

## 4. 改訂版フェーズ計画

「開発完了」と「本運用」は別の状態として管理する（GPT文書の原則を踏襲）。

### Phase 0：権限境界・基盤整理（最優先・進行中の作業と並行）

目的：既存コードを壊さず、アプリ境界と権限を確定する。

- Ohana Staffから管理者専用機能（給与集計・全職員情報など）を整理（非表示または管理者Webへ移管）
- 一般職員は自己情報のみ、管理権限者にのみ承認・送信系を表示するロール分岐
- 機能フラグ基盤の拡張：施設単位に加え「クラス単位」「機能単位」の段階公開に対応（Ohana Family公開制御の前提）
- RLS・重要情報アクセスログの再検証（3ドメイン分離：職員業務／保育業務／保護者）
- 受入基準：一般職員が他職員の給与・個人情報へ到達できない。施設範囲外のURL/API直接指定が拒否される。

### Phase 1：Ohana Staff（職員アプリ）の正式運用 — 全職員同時スタート

- 職員セルフビュー：自分の月間勤怠（施設別）・給与明細（12か月表示・退職後6か月制御）
- 欠勤・遅刻・早退・有給申請、有給残数・履歴
- シフト確認・変更通知
- 90秒single-use QR（ポリシー固定・テスト）※現行仕様の8時間から要変更確認
- お知らせ・個別連絡・**グループ連絡（新規：管理職以上／クラス担当／プロジェクトチーム等のグループ単位配信）**
- イベント駆動のプッシュ通知（申請結果・シフト変更・明細公開・未退勤アラート等）と失敗・再送管理
- iPad代理打刻の監査ログ確認、Web代理打刻（現在時刻・過去修正）の統合
- 運用順：内部テスト → 全職員一斉試験運用 → 既存勤怠との照合 → 正式切替

### Phase 2：AI連絡帳の実運用開始（Ohana Kids上で）

- Edge Function（generate-contact-note）のモックを実AI呼び出しへ差し替え（ANTHROPIC_API_KEY登録）
- Claude／OpenAIのProvider抽象化と施設別の手動切替（APIキーはサーバー側管理）
- AI出力の自動公開禁止：職員修正 → 提出 → 承認 → 差戻しのフロー維持
- コドモンと並行運用（生成・承認後の文章をコピーして利用。転記完了ボタンは作らない）
- 施設・クラス限定で試験開始
- ※この段階ではWeb版への移行は行わず、Flutter版Ohana Kidsで運用する

### Phase 3：給与・労務の並行検証と正式切替

- 既存給与計算との2〜3か月並行照合（代表的な常勤・パート・兼務者でゴールデンテスト）
- 照合結果と差異理由の記録・承認後に本番切替
- 全銀協CSVは横浜銀行の試験アップロード完了まで本番無効（機能フラグでボタン無効化）。当面はExcel振込一覧を正式出力とする（実装・デプロイ済み）
- 賃金台帳・労働者名簿・施設別タイムカード・有給台帳の正式レイアウト実装
- 実打刻原本／修正実績／給与算定時刻／給与確定スナップショットの分離徹底
- 時間外アラートは給与算定上の時間外支給対象があるときのみ表示

### Phase 4：Ohana Family（保護者アプリ）の段階公開

- 施設・クラス・機能単位の公開フラグを実装（Phase 0の基盤を利用）
- 公開順（フラグONの順序）：①園からのお知らせ → ②欠席・遅刻・早退・お迎え変更 → ③家庭連絡帳 → ④園からの連絡帳 → ⑤クラス写真 → ⑥登降園QR
- 試験施設：BABY MAHALOまたはMahalo Station（正式決定後に設定値で指定。ハードコード禁止）
- 実機E2E・同意/プライバシー確認の完了が全面公開の条件
- 現在進行中のUI改善（メニュー並び替え・グリッド表示・申請種類の見直し・履歴一覧・未読バッジ等）はこのPhaseの準備作業として位置づけ

### Phase 5：保育業務Web版への移行・統合高度化

- 独自ドメイン取得・サブドメイン構成（admin/childcare.ohanaworks.jp）※このタイミングで再検討
- Ohana Kids（Flutter版）の機能をNext.js Webへ移植（AI連絡帳から順に）。Web安定後にFlutter版を廃止
- デイリーボード・当日出欠・在園状況のWeb統合
- PIMS正式CSV対応（フォーマット入手後）
- AI異常検知・監査支援
- 将来の音声・ビデオ通話（別プロジェクトとして承認後。通信Providerは疎結合設計で留保）

## 5. 優先順位（P0〜P3）

### P0：運用開始・個人情報保護を阻害する項目
1. Ohana Staffの権限境界整理（管理機能の分離）
2. 職員セルフビュー：自分の勤怠・給与明細
3. イベント駆動通知の自動化
4. QRの90秒single-use確定（現行8時間仕様からの変更判断を含む）
5. Web代理打刻と監査ログ
6. 月間勤怠・施設別表示・Excel出力（3施設勤務なら3シート、全体シートなし）
7. RLS・重要情報アクセス制御の再検証

### P1：最初の業務価値を生む項目
1. 有給管理・申請承認フロー
2. グループ連絡（管理職以上／クラス担当／プロジェクトチーム等）
3. AI連絡帳の実AI接続（Ohana Kids上）
4. AI Provider切替（Claude/OpenAI）
5. 園児登録・異動・退園の管理画面（現状SQLに依存 → admin_webにUI追加）
6. 施設・クラス・機能単位の公開フラグ基盤

### P2：十分な試験後に本番化する項目
1. 給与計算の本番切替（2〜3か月照合後）
2. 台帳出力（賃金台帳・労働者名簿等）
3. Ohana Familyの段階公開
4. デイリーボードの本格運用
5. PIMS CSV

### P3：保留
- 全銀協CSVの本番利用（横浜銀行確認待ち）
- PIMS API連携
- グループ音声・ビデオ通話
- 年末調整・賞与等（別途承認が必要な拡張）
- 独自ドメイン取得・サブドメイン移行

4. グループ連絡機能の要件詰め（グループの種類・作成権限・通知方式・既読管理・終了時の扱い）
5. 【未対応】園児マスタ（`/childcare/children`）のクラス列表示の基準日統一：`fetch_children_for_office_master`は`effective_end_date is null`の行を無条件表示するため、進級一括登録（`bulk_promote_children`）で未来日付（例：翌年度4/1）を事前登録すると、その瞬間から園児マスタ上はクラスが切り替わって見える。一方デイリーボード（`fetch_daily_board_for_office`）・欠席選択（`fetch_class_children`）・連絡帳必須判定（`is_family_daily_report_required`）・キオスク登園判定（`resolve-guardian-qr`）はいずれも`p_business_date`（実際の当日）基準で在籍クラスを解決するため、事前登録してから実際の開始日を迎えるまでの期間、同じ園児が画面によって違うクラスに見える状態になる。対処案：園児マスタのクラス列も`p_business_date`（今日）基準の解決に変え、あわせて「予約中の進級：○○組（開始日）」を別途表示する。2026-07-28時点で本番の`child_class_enrollments`はまだ実運用前（3行のみ）のため、直すコストが低いうちに対応するのが望ましい。
6. 【未対応】キオスクの必須判定連動確認（実機QRスキャン）：`resolve-guardian-qr`の家庭連絡帳必須判定（`is_family_daily_report_required`/`has_family_daily_report_submitted`）は保護者アプリ側での確認（2026-07-28実施）で実証済みだが、キオスク端末での実際のQRスキャン→登園拒否のE2E確認はまだ未実施。カメラ(`mobile_scanner`)がiPhoneシミュレータ表示のQRを物理的に読み取れないため、実機（`parent_app`用iPhone実機、または大和オハナ保育園のIPAD-O-01相当の実機）が用意でき次第対応する。代替として`issue-guardian-qr-token`/`resolve-guardian-qr`をcurlで直接呼ぶ経路も特定済み（カメラ・キオスクUI以外は実物コードで検証可能）だが、保護者の実認証トークン入手方法が未確定。
7. 【未対応・軽微】`/childcare/children`一覧で、退園済みの園児の行にも「期間設定」ボタンが表示されてしまう：`children/page.tsx`の表示条件が`!classDefaultRequired`のみで`!isWithdrawn`を見ていないため、退園済み園児（クラス在籍が無くなり`classDefaultRequired`がfalse扱いになる)でもボタンが出る。退園済みの行では非表示または無効化するのが自然。
8. 【対応済み・2026-07-28】保護者アプリのホーム画面で、園児カードが保護者の人数分重複する不具合を修正した：マイグレーション98（`20260714000098_guardian_visibility_fixes.sql`）で`guardian_child_links`のSELECTポリシーが`guardian_id = my_guardian_id()`から`guardian_has_child_access(child_id)`に変更され、同じ園児に紐づく他の保護者（共同親権者等）の紐付け行も見えるようになったが（意図的な変更）、`fetchLinkedChildren()`側がこれに追従せず`child_id`単位の重複排除をしていなかったため、園児に保護者が2人以上いる家庭ではカードが重複表示されていた。`fetchLinkedChildren()`に`guardianId`必須引数を追加し明示的に自分の紐付け行のみ取得するよう修正、実機確認済み。
9. 【未対応・TODO】個別目標シートのAI下書き（`generate_employee_goal_section_draft` RPC、`20260714000138`）は**現在モック実装**。Anthropic Console（API従量課金契約）が未契約のため、`ai_runs.provider = 'mock'`で仮の文章（プレフィックス「【AI生成(モック)】」）を返しているだけで、実際にAnthropic APIを呼び出していない。契約完了後、同RPC内のモック応答生成部分をEdge Function経由の実API呼び出しに差し替えること（`generate-contact-note`の`callAI()`と同様の差し替えパターン）。Phase 2の動作確認では「モック応答が返ること」の確認までとし、「AI下書き機能が完成した」とは報告しない（実API接続は別タスクとして残す。指示書§6.2にも記載済み）。

## 8. 進捗管理ステータス（GPT文書の定義を踏襲）

各機能を次の状態で管理する：企画 → 仕様確定 → 開発中 → 内部テスト → 園内試験 → 部分運用 → 本運用（その他：保留・廃止予定）

「開発完了」と「本運用」は別状態。完成率の数値ではなく、受入基準の通過を機能ごとに判定する。
