## 0. 本要望の性質(冒頭で明記)

**これは既存機能の改修ではなく、「保護者向け一斉配信(お知らせ)」の新規構築である。**

- 既存の `notices` / `create_notice`(admin_web「お知らせ」)は **職員宛て専用**(会社一斉/園単位/役職別/個別/グループ=すべて `employee` が対象)。**保護者向けには一切流用しない。**
- **保護者向けの一斉配信は現在存在しない。** 保護者アプリで現在「お知らせ」と表示されているものは、**連絡帳(daily contact)に紐づく園児別の個別連絡**であり、一斉配信ではない。
- したがって本設計は、新規テーブル + 新規RPC + 新規UI(admin_web作成/承認・parent_app閲覧)として構築する。既存の**規約・前例は最大限踏襲**し、新しい発明はしない(§7 参照)。

## 1. 名称の確定(要望反映)

| 名称 | 指すもの | 由来 |
|---|---|---|
| **連絡帳** | 園児別の日々のやり取り(家庭↔保育園)。既存の家庭連絡帳・園連絡帳・**連絡帳に付随する個別お知らせ**を含む | 既存機能(`child_daily_contacts` / `communication_book_*`) |
| **お知らせ** | 保育園から保護者への**一斉配信**(全施設/施設/クラス/園児単位)。今回新設 | 新規 `guardian_notices`(仮) |

- **既存の communication_book_notice(園児別お知らせ)は「連絡帳」側の機能**として扱う。テーブル名・カラム名は変更しない(表示文言のみ調整、§4.3)。
- **新設する保護者向け一斉配信を「お知らせ」**とする。
- 保護者アプリ・admin_web の両方で、この2つを**名称・画面配置の両面で明確に分離**する(§4.1・§4.2)。

## 2. 調査結果

### 調査1: 現在のお知らせ機能の配信対象単位

- **職員向け `notices`**(`20260710160006_rls.sql:116`、`create_notice` は `20260714000121`)。カテゴリ enum(`20260710160001…:70`)= `会社一斉/園単位/個別/役職別/勤務交代関連/災害モード`。宛先列 `target_office_id`・`target_position_id`・`target_group_id`・`notice_recipients`(個別/グループはスナップショット展開)。**すべて職員が対象。保護者を宛先にする経路は無い。**
- **保護者が現在見る「お知らせ」**(`parent_app/.../communication_book_notice_list_screen.dart`)は `fetchCommunicationBookNoticeHistory(childId)` が返す**連絡帳の個別お知らせ**(`individual_notice_masters` のチェック)。園児単位の連絡帳付随情報であり、独立配信ではない。→ **一斉配信は未実装。**

### 調査2: notifications(outbox)は child_id を持つか / 保護者への到達経路

- `notifications`(`20260710160005:46`)の元定義は職員専用: `target_employee_id`・`target_role_code`。**child_id 列は無い。**
- `20260714000101_push_device_tokens.sql:40` で **`target_guardian_id` を追加**。保護者pushは **guardian_id 単位**で outbox に積み、`dispatch-pending-notifications` が `push_device_tokens`(guardian_id 紐付け)と突合しFCM送信。
- **child_id は outbox にも push にも無い**=保護者配信は完全に guardian_id 単位。これが「兄弟のどちら宛か分からない」の技術的根源。
- `dispatch-pending-notifications` 冒頭コメント: 現状 outbox は職員通知のみ、保護者宛(target_guardian_id)行は未生成。保護者向けイベントの一部(登園拒否等)は Edge Function から直接送信(outbox未経由)。→ お知らせpushをoutbox経由に載せるのは自然な拡張。

### 調査3: 保護者アプリのお知らせ一覧/詳細の表示内容

- `communication_book_notice_list_screen.dart`: AppBar に `ChildContextAppBarTitle(title:'〇〇の保育園からのお知らせ', officeName: child.officeName)` → **園児名 + 施設名**。各行=連絡帳の日付 + お知らせラベル。**「園児を選んでから、その子の連絡帳お知らせを見る」構造**で、園児名は画面コンテキストで既出。
- **新しい一斉配信お知らせは園児コンテキストの外(横断一覧)で表示**するため、各行に「対象園児名(+クラス名)」または「園全体」バッジを明示的に付ける必要がある。

### 調査4: 既存の園児固有プッシュ(「たろうくん 登園しました」等)の仕組みと再利用性

- `resolve-guardian-qr/index.ts` 等が送信直前に `children`(`display_name, honorific_suffix`)を取得し**文字列補間**で本文生成(例 `` `${child.display_name}さんの登園には…` ``、`:164`)。`_shared/push.ts::sendFcmPush({title,body,data})` は title/body をそのままFCMへ渡す薄いラッパー。
- **再利用可否: 高い。** お知らせpush dispatch 時に対象園児の `display_name`(+敬称)を引いてタイトル冒頭に付与すればよい。既存と同一方式。

### 調査5: 現在のお知らせ作成の権限チェック

- admin_web `notices/page.tsx` は `is_labor_manager_plus`(`:72`)で会社一斉可否、作成は `create_notice` RPC(`:169`)。**認可の実体は RPC 内**(`20260714000121:29-58`、カテゴリ別に `is_labor_manager_plus`/`manages_office` 等)。**クライアント表示に依存せずサーバRPCで担保**する流儀。→ 新お知らせRPCも同流儀。

### 調査6: 兄弟児がいる保護者アカウントの存在(本番/ステージング)

- **ステージング**: `guardian_child_links` 集計 → **兄弟(1保護者↔複数園児)0件、複数保護者↔1園児 0件**(seedは園児ごとに1保護者)。→ **検証データ無し。作成必須**(§5)。
- **本番**: 本環境の supabase CLI にリンクされているのは**ステージングのみ**(prod ref `wdsziqxvmhwbdyfeiame` 未リンク)。**本番へ接続できていない**ため未確認。付録Aの読み取りクエリを本番で実行して確認いただきたい。

### 調査7: 既読管理の仕組みは存在するか

- 職員お知らせには `notice_recipients.read_at`(職員向け)。
- **保護者向けには連絡帳既読テーブルが既存**: `communication_book_reads(child_daily_contact_id, guardian_id) unique`(`20260714000088`)。RLSは**保護者は自分の行のみINSERT**(`guardian_id = my_guardian_id()`)、職員は `staff_has_guardian_data_access` で閲覧。**本要望の既読テーブルの理想的な前例**。
- 「詳細画面到達で既読」は、詳細遷移時に既読INSERTを呼ぶ実装で満たせる(連絡帳で同型実績)。一覧表示のみでは既読としない、プッシュから詳細到達も既読、を満たせる。

### 調査8: 1園児に複数保護者(guardian_child_links)の現状

- 構造上は複数可(`guardian_child_links(guardian_id, child_id, role)`)。ステージング実測は**0件**(調査6)。本番未確認(付録A)。
- 含意: 園児単位の既読集計で「複数保護者のうち何人が既読か」の定義が必要(判断#3)。

### 調査9: 役職階層と各施設の園長以上の実在

役職マスタ(`20260710160002:60`): `system_admin > labor_manager > director(園長) > chief(主任) > office_manager(園管理者) > viewer > staff`。**「施設長」役職コードは存在しない**(施設長=オーナーは `system_admin`、または複数施設 `office_manager` で表現。`20260714000138:10`)。

ステージング実測(施設×役職):
| 施設 | 実在役職 | 園長以上の有無 |
|---|---|---|
| 大和オハナ保育園 | director×1, chief×1, staff×2 | **あり(園長)** |
| BABY MAHALO | office_manager×1, staff×1 | **なし** |
| Mahalo Station | office_manager×1, staff×1 | **なし** |

### 調査10: Phase3(支援保育)承認フローの再利用性

支援保育申請(`support_childcare_applications`, `20260714000140:127`)の状態:
`draft → ai_draft → in_review → returned / approved → finalized → released → superseded → archived`(`:128`)。差戻し=`returned`(`:1240,1322`)、承認=`approved`+`approver_id`+`approved_at`(`:1325`)。
→ **お知らせ承認フローに同じ語彙・規約を再利用**。簡略化して `draft → in_review → returned / approved(=送信)` で足りる。

### FCMタイトル長(要望の「文字数」根拠)

- FCM HTTP v1 の上限はメッセージ全体で **4096バイト**(data+notification 合算)。`notification.title` 単体の明示的文字数上限は無い。実表示はOSが切り詰め(iOSロック画面タイトルは実質全角12〜20字、Android折りたたみ1行)。
- **推奨**: 園児特定可能時はタイトル冒頭に園児名。書式 `【〇〇ちゃん】<タイトル>`。**タイトル全体を全角20字以内**、超過は「…」。詳細は body。複数園児で複数通届く場合は各pushに各園児名を付与。

## 3. データモデル(新規)

```
guardian_notices                      -- お知らせ本体(一斉配信)
  id, scope('all'|'office'), title, body,
  status('draft'|'in_review'|'returned'|'approved'),
  created_by(employee), approved_by(employee), approved_at, returned_reason,
  created_at, sent_at

guardian_notice_targets               -- 宛先指定(作成時の意図。複数行=複数選択・階層併用可)
  id, notice_id, target_type('all'|'office'|'class'|'child'),
  office_id?, class_id?, child_id?

guardian_notice_recipients            -- 配信時に解決した宛先スナップショット(確定)
  id, notice_id, guardian_id, child_id?,   -- child_id=どの園児文脈で届いたか(兄弟判別の要)
  resolved_class_id?, unique(notice_id, guardian_id, child_id)

guardian_notice_reads                 -- 既読(保護者単位)
  id, notice_id, guardian_id, read_at, unique(notice_id, guardian_id)
```

要点:
- **targets(意図)と recipients(確定スナップショット)を分離**。前者は「クラスA+クラスB+園児X」の指定、後者は配信時に保護者×園児へ展開した結果。→「クラス2つ+園児1名」の**階層併用が自然に表現**できる。
- **recipients.child_id を保持**が兄弟判別の肝。all/office は `child_id=null`(園全体)、class/child は該当 child_id。1保護者に複数園児ヒット時は保護者×園児で複数行になり得る(判断#1・#2)。
- 既読 `guardian_notice_reads(notice_id, guardian_id)`。**child_id は既読キーに含めない**(既読=保護者がそのお知らせを読んだか、保護者単位で1回)。園児単位集計は recipients.child_id と突合。

## 6. 設計提案(要件別)

### 6.1 宛先選択(全施設/施設/クラス/園児・複数・階層併用)
作成画面で `target_type` を選び各階層で**複数選択**→ `guardian_notice_targets` に複数行。**階層併用可**(office+class+child 混在)。「全施設(all)」は他と併用しない(UIで排他)。

### 6.2 配信対象の確定タイミング — **スナップショット固定を推奨**
送信(承認確定)時点で対象保護者を解決し `guardian_notice_recipients` に固定。
- 理由: (1) 既読母数 N/M が安定(都度解決だと入退園で母数が動く)、(2) 「送った時点で誰宛だったか」が督促・監査の基準、(3) 既存 `notice_recipients` と同方式で一貫。
- 代替(都度解決=recipients を持たず閲覧時にRLS/RPCで動的判定): テーブルは軽いが**既読母数が確定できない**・毎回在籍判定の負荷・過去在籍の扱いが曖昧 → 既読可視化と相性が悪い。
- **転園・退園時**: 配信後に転園/退園しても recipients は変えない(送った事実を保持、保護者は過去お知らせとして閲覧可)。新規お知らせは配信ごとに解決し直すため、退園後は自然に対象外(解決は在籍中 enrollment を条件)。

### 6.3 保護者側の表示
- `child_id=null`(all/office)→ **「園全体」バッジ・園児名なし・保護者につき1件**。
- `child_id` あり(class/child)→ **対象園児名(+クラス名)バッジ**。
- 詳細画面**到達時**に既読INSERT(プッシュ経由の到達も既読)。一覧表示のみでは既読にしない。**保護者は自分の既読のみ**参照。

### 6.4 プッシュ通知
承認=送信時に recipients から `notifications`(target_guardian_id)を生成→ `dispatch-pending-notifications` でFCM。**園児特定行はタイトル冒頭に `【〇〇ちゃん】`**(§調査4方式)。all/office は園児名なし。タイトル全角20字目安・超過は「…」。

### 6.5 権限(RPCで担保)【2026-07-31 判断#5反映】
`create_guardian_notice` 内で宛先種別ごとに認可(**保育業務ドメインの `manages_childcare` を使う**=labor_manager を含めない。統括管理者の付与も `manages_childcare` 経由で自動波及):
- **全施設(all)**: **`is_system_admin()` または統括園長 `executive_director`**(=`is_executive_or_system_admin()`)。※判断#5: 大原統括園長は全施設の保育の最終責任者であり「承認はできるが作成はできない」非対称は運用不可のため、作成者にも含める。
- **施設/クラス/園児**: 対象施設に対する `manages_childcare(office_id)`(主任以上)。クラス/園児は所属施設を解決して同判定。
- **他施設保護者へ配信不可**を担保: 指定 office/class/child すべてを検証、1つでも権限外なら例外。
- 統括管理者は `manages_childcare` の付与OR句で自動的に付与施設の作成が可能(147の機構)。

### 6.5b 送信前の確認ダイアログ ＋ 誤送信の取り消し(誤送信対策)【2026-07-31 追加要件】
**全施設に限らず、施設/クラス/園児のすべての配信で、送信(approve)実行前に確認ダイアログを出す。**
- 表示: **配信対象の施設名**(全施設なら4施設すべて列挙)、**対象の保護者アカウント数**、**対象の園児数**、**「この操作は取り消せません(既送信のプッシュは取り消せません)」**の明示。
- 数字は送信せずに算出する `preview_guardian_notice(notice_id)` RPC(施設名配列・guardian数・child数を返す)で取得。
- **確認ダイアログを出す位置は「approve(承認+送信)ボタンの直前」(Phase C 実装要件)。** 不可逆の瞬間は approve のため、作成時だけでなく**承認する園長が承認ボタンを押す直前にも preview を表示**する。承認する園長は宛先を自分で選んでいないため、そこで初めて配信規模(施設・保護者数・園児数)を知る。統括園長の全施設お知らせは承認不要の即時送信=第三者の目が入らないため、この確認が最後の砦。

**送信後の取り消し(`revoke_guardian_notice`・Phase B)**: 承認=即送信のため誤りは必ず送信後に気づく。プッシュ自体は取り消せないが、アプリ内一覧に誤ったお知らせが残り続けるのを防ぐため取り消しを設ける。
- `guardian_notices` に `revoked_at / revoked_by / revoke_reason` を追加。**保護者側SELECTは `revoked_at is null` を条件に**(取り消し済みは保護者から見えない)。
- `revoke_guardian_notice(notice_id, reason)` RPC: 対象は `approved`(送信済み)のみ・二重取消不可・**理由必須**・実行権限は**承認者と同じ**(director自施設/executive_director全施設/system_admin=`is_guardian_notice_approver`)・監査(guardian_notices の update トリガ)。
- 取り消し実行時の確認ダイアログに**「既に配信済みのプッシュ通知は取り消せません」を明示**(Phase C)。

### 6.6 作成権限と承認フロー(Phase3語彙を踏襲)
状態: `draft → in_review → returned / approved(=送信)`。
- **作成**: 主任(chief)以上のみ。一般職員は作成画面/RPCに到達不可。
- **即時送信**: 作成者が**園長以上**(director / **統括園長 executive_director** / system_admin)なら `draft → approved` を1操作(承認不要)。
- **承認必要**: 作成者が主任・管理者(chief/office_manager)なら `draft → in_review`。承認者(**園長以上 = director / 統括園長 executive_director / system_admin**)が `approved`(=送信)または `returned`(差戻し・理由必須)。
  - **2026-07-30 更新**: 役職「統括園長(`executive_director`)」の追加が確定(`docs/権限・セッション管理_設計案_2026-07-30.md`)。統括園長は**全施設で園長権限を包含**するため、承認判定に含めれば**園長不在の3施設(BABY MAHALO/Mahalo Station/Halelea)の管理者お知らせも統括園長が承認**でき、判断#4は「統括園長が承認」で実質解決する。
- **承認と送信(推奨)**: **承認と同時に配信キュー投入(承認=送信)**。二段化は「承認済み未送信」の事故を生むため。送信前調整は下書き/差戻しで行う。
- **承認者を同一施設に限るか**: 統括園長は全施設スコープのため施設横断で承認可。それ以外の承認者(director)は自施設に限る設計を基本とする(判断#4は統括園長導入で解決)。
- **監査**: 作成者・承認者・承認日時・差戻し理由を `guardian_notices` 列 + `event_logs`(`log_event_change`)で記録。

### 6.7 既読の職員側集計とパフォーマンス【2026-07-31 判断#3反映】
- 一覧に「既読 N/M名」(M=recipients の distinct guardian、N=reads 数)。
- **未読者一覧は「世帯(園児)単位」で出す**(判断#3): 既読判定は **any(その園児に紐づく保護者が1人でも読めば、その世帯=園児は既読)**。**未読 = その園児に紐づくどの保護者も読んでいない園児**。→ 父だけ読んだ世帯は督促対象に残さない。保護者アカウント単位の未読一覧にはしない。
- 全施設/施設単位(recipients.child_id=null)は保護者アカウント単位で「未読の保護者」を出す(園児文脈がないため)。クラス/園児単位(child_id あり)は上記の園児単位。
- 行数見積り: 全施設お知らせ1本 ≒ 保護者数分(全園児数百・保護者×1〜2)→ 1配信最大 ~1,000行。年数万〜十数万行規模、B-treeで十分。
- インデックス: `recipients(notice_id)` / `(guardian_id)` / `(notice_id, child_id)`、`reads(notice_id)` + unique `(notice_id, guardian_id)`。未読集計は `recipients left join reads on (notice_id, guardian_id)` を notice_id で絞る。

### 6.8 既読RLS
- `guardian_notice_reads` INSERT: `guardian_id = my_guardian_id() and <当該noticeのrecipient>`。他保護者の既読は作成不可。
- SELECT: 保護者は自分の行のみ。職員は当該お知らせ施設の `manages_office` で集計閲覧。→ `communication_book_reads` のRLSを踏襲。

## 9. 判断待ち事項(俊さんが決定)

1. **兄弟2人が同じクラス → クラス単位お知らせを2件(園児ごと)表示 or 1件集約(園児名併記)**
   - 2件: 各園児にバッジ・既読も園児ごと。冗長・push2回。
   - 1件集約: 重複なし・push1回。園児ごとの文脈/既読が弱まる。
   - 目安: クラス単位=1件集約、園児単位=園児ごと(実務的)。
2. **兄弟が別施設 → 「全施設」お知らせを1件(園全体バッジ) or 園児ごとに分割**
   - 目安: 全施設/施設単位は1件・園児名なし(表示方針どおり)。園児ごとは表示方針と矛盾。
3. **園児単位の職員側既読集計 → 「1人でも読めば既読(any)」 or 「全員読んで既読(all)」**
   - any: 連絡帳の既存規約(1名閲覧=家庭確認済み)に整合。別居共同親権では一方だけでも既読に。
   - all: 全保護者到達を厳密把握。未読が残りやすく督促過多。
   - 目安: 既存規約に合わせ any。別居配慮重視なら all。
4. **園長不在の3施設(BABY MAHALO/Mahalo Station/Halelea)の管理者お知らせを誰が承認するか**
   - 案1: 施設長(または大和の園長)が必ず承認 — 単純だが承認負荷集中・滞留リスク。
   - 案2: 将来の「統括管理者」を承認者に加える — 負荷分散だが**統括管理者が未実装**(先行実装が必要)。
   - 案3: 施設の責任者(その施設の園長 or 責任 office_manager)を承認者 — 迅速だが「管理職以下は園長以上の承認」原則を緩め、実質自己承認に近づく。
   - 暫定推奨: 統括実装までは案1、実装後に案2へ移行。
