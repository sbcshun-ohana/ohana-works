# クラス活動 →(スナップショット)→ 連絡帳 連動 設計案

作成: 2026-08-05 / 俊確定: 方式=(b)スナップショット本文取込 / 対象=当日登園した児童のみ(欠席児に連絡帳は公開しない) / 公開後のクラス活動側からの自動反映なし・必要時は主任以上が連絡帳を個別修正(183の公開済みガードと同じ線)。
DB変更は **189以降**、本番反映は第2弾(184〜)にまとめて。

## 1. 調査報告(現行スキーマ)

### 1.1 クラス活動 `class_daily_activities`(migration 62)
- 列: `id, class_id, business_date, assignee_employee_id, today_theme, activity_content, class_overview, class_announcement, other_notes, status('draft'|'submitted'|'approved'|'rejected'), submitted_at, approved_by, approved_at, rejected_reason, created_at, updated_at`。`unique(class_id, business_date)`。
- **「クラス全体へのお知らせ」= `class_announcement` 列**(連絡帳へ取り込む本文の出所)。
- 保存/更新: **直接テーブルUPDATE**(専用の本文保存RPCは無し)。RLS: insert=`has_childcare_class_access`、担当者は `status in('draft','rejected')` で更新可、管理者ポリシーで `manages_childcare` は制限緩め。状態遷移RPCは claim/reassign/submit/approve/reject(62)。
- タイミング: `updated_at`トリガ、`submitted_at`(submit時)、`approved_at`(approve時)。

### 1.2 連絡帳 `child_daily_contacts`(migration 65 + 87 + 166)
- 本文列: `guardian_message, child_today_notes, free_notes, ai_generated_text, current_text`(=公開本文の主体)。構造化(87): `nap_periods, toileting_records, meal_completion_pct, meal_free_note, temperature, temperature_measured_at, bath_taken`。
- 公開制御(166): `status`、`published_at`(NULL=不可視)、`scheduled_publish_at`。保護者SELECTは `status='approved' and published_at is not null and published_at<=now()`。
- `unique(child_id, business_date)`。行生成は `ensure_child_daily_contact(child, date)`。

### 1.3 公開済み連絡帳の本文は現状 誰が修正できるか
- **本文編集は直接UPDATE(RLS)**。ポリシー2種:
  - `child_daily_contacts_update_assignee_content`: `assignee_employee_id=my_employee_id() and status in('draft','rejected')` → 担当者は承認前のみ。
  - `child_daily_contacts_update_managers`(65:82〜):
    ```sql
    create policy child_daily_contacts_update_managers on child_daily_contacts
      for update using (
        exists (select 1 from children c
                where c.id = child_daily_contacts.child_id and manages_childcare(c.office_id))
      ) with check ( ... manages_childcare ... );
    ```
    → **status 無制限＝主任以上(`manages_childcare`)は公開済み(approved/published)でも本文UPDATE可**。
- 結論: **公開済み本文の修正は「主任以上」が既存RLSの直接UPDATEで可能**(183 の公開済みガード=主任以上 と同じ線)。新RPCは不要。

## 2. 設計案(論点ごとの立場と根拠)

前提(俊確定): 方式=スナップショット本文取込 / 対象=当日登園児のみ / 公開後の自動反映なし / 事後修正は主任以上。

### (a) 記載タイミング
- **立場: 「公開処理時」に取り込む**(即時公開 `publish_child_daily_contacts_now` と 17時cron `cron_publish_due_daily_contacts` の両経路にフックを1関数で共有)。
- 根拠: 「当日登園した児童のみ」の判定は**公開時点が最も確定的**(登園状況は公開直前に固まる方向)。承認時だと未登園児にも入りうる、保存時だと早すぎる。
- 整合:
  - **保存後に登園した子**: 公開時点で登園していれば対象になる(公開時判定のため拾える)。
  - **お知らせ修正後に公開される子**: 公開時点の `class_announcement` を取り込む(最新反映)。
  - 対象判定 = 公開対象の連絡帳の児が**当日登園**(例: `daily_child_status.status in ('present','picked_up')` かつ `child_daily_attendance.is_absent` でない)。欠席児は取込対象外(かつ「欠席児に連絡帳は公開しない」方針と整合。※欠席児の公開抑止自体は別論点として下記(b)注記)。

### (b) 連絡帳行が無い登園児の扱い (v1確定: 自動生成しない)
- **確定(v1): 連絡帳行の自動生成はしない**。お知らせ取込は「承認済み連絡帳」にのみ追記。
- **役割分担**: 全保護者へ確実に届けたい内容は**一斉配信機能(guardian_notices)の守備範囲**とし、本連動(連絡帳追記)は「個別連絡帳がある登園児への補足」に限定する。
- 根拠: お知らせだけの行を生成して**可視化するには承認フローの外で公開**することになり、承認ゲート(65/166)を破る。166意味論(生成時 status='draft'・`published_at` NULL=不可視)を守ると「生成しても見えない」ため目的を果たせない。
- **決定点**: 「全登園児に必ず届けたい」場合は (B案) 公開時に登園児全員へ `ensure_child_daily_contact` で行生成し、お知らせのみの行を**自動承認+公開**する経路が要る(=承認バイパス)。バイパス可否は俊判断。v1は推奨A(承認済み連絡帳のみ追記)で提示。

### (c) 本文への入り方(スナップショット要件)
- **立場: `current_text` の末尾に見出し付きで追記**(例: `\n\n【クラスからのお知らせ】\n{class_announcement の取込時点コピー}`)。
- 根拠: 俊確定「本文取込」。**取込後は通常の連絡帳本文**として、担当者(承認前)・主任以上(公開後)が**個別に編集・削除可能**(=ライブ参照ではなくコピー=スナップショット要件を満たす)。
- 補足: 別列(rendered section)にせず本文へ融合するのは、俊要件「個別編集・削除できる通常本文」に合わせるため。

### (d) 公開済み本文修正を主任以上に許可する経路
- **立場: 既存で可能(新RPC不要)**。上記1.3の `child_daily_contacts_update_managers` RLS(主任以上・status無制限)で公開済み本文を直接UPDATEできる。取込機構自体は security definer RPC(公開処理内)で実行するためRLSを介さない。事後の手修正は既存の主任UPDATE経路。

### (e) 二重記載防止
- **立場: マーカー列で「(連絡帳, 取込元クラス活動)につき1回だけ追記」**。
  - 追加列案: `child_daily_contacts.class_announcement_applied_activity_id uuid`(+ `class_announcement_applied_at timestamptz`)。取込時に対象クラス活動の id を記録し、**既に同一 activity_id が適用済みなら再追記しない**。
  - 再公開/リトライ/複数回cron/お知らせ再保存でも、同一クラス活動の追記は1回に収束。
  - **お知らせ編集後の再反映はしない**(俊確定「公開後の自動反映なし」)。必要時は主任以上が本文を手修正(1.3の経路)。

## 2.5 189前に固める2点(俊指示)
- **① 取込対象の class_daily_activities.status 条件**:
  - 調査: Ohana Kids のクラス活動画面に **申請(submit)/承認(approve)/差し戻し(reject) が完全配線済み**(担当者=draft/rejectedで編集・申請、管理者=submittedを承認)。`class_announcement` も draft/rejected で編集。フロー自体はコード上 存在・利用可能(実利用頻度はデータ次第=下記SELECTで確認可)。
  - **提案(推奨): 取込条件 = `status='approved'`**。理由: 追記先が公開＝保護者可視のため、お知らせ本文も**クラス活動側の承認を通したもの**に限定する(連絡帳の承認とは別に、追記後内容は連絡帳承認者の目を経ないため)。運用でapproveが徹底されない場合は 'submitted' を含める緩和も1行で可能。
  - 利用状況の確認SELECT(俊が任意実行):
    ```sql
    select status, count(*) from class_daily_activities
    where business_date >= current_date - 30 group by status order by status;
    ```
- **② 空お知らせのスキップ**: `class_announcement` が NULL または空白のみ(`btrim=''`)なら**取込しない**(見出しだけの追記を防ぐ)。189に実装。

## 3. 想定DB変更(189・設計承認後に全文提示)
- `child_daily_contacts` に `class_announcement_applied_activity_id uuid`(+ `_applied_at timestamptz`) 追加。
- 取込関数 `apply_class_announcement_to_contact(contact_id)` (security definer): 対象児が当日登園 & 未適用 & クラスに `class_announcement` あり の時のみ、`current_text` へ見出し付き追記＋マーカー記録。
- `publish_child_daily_contacts_now` / `cron_publish_due_daily_contacts` の公開ループから上記関数を呼ぶ(両経路共有)。
- ※ (b)でB案(登園児全員へ生成)を採る場合のみ、追加で ensure＋自動承認経路の是非を再設計。
