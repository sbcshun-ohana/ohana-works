## 1. この機能が何であるか(1段落で)

職員同士が「誰から誰への連絡か」が明確に分かる形で申し送り・連絡を送り合える**園内連絡**を新設する。宛先は①職員個人(複数可)②時間帯区分(早番/中番/遅番)③施設全体④クラス単位の4通りで、**今後の区分追加に耐える構造**にする。受け取った職員は、アプリを開いた(ログインした)瞬間に自分宛ての連絡に**視覚的に気づけ**、「確認しました」ボタンで既読が**管理側に分かる**。時間帯区分は職員マスタに登録しない——その日のシフト(勤務予定)から動的に判定する。クラス宛ては**担任に確実に届き**(職員マスタに担任設定を新設)、担任以外にも一覧で見える。これに伴い、園内記録の区分「申し送り」は廃止し、申し送りの役割は園内連絡へ移す。

## 2. 設計原則(実装判断に迷ったらここに戻る)

1. **「誰が誰に・誰が確認したか」を常に表示できるデータ構造にする。**送信者・宛先・確認は全て記録し、管理側(主任以上)は「誰に届いて、誰が確認済みか」を一覧できる。
2. **時間帯区分の個人マスタを作らない。**早番/中番/遅番と職員の対応は保存せず、対象日のシフトから**読むたびに動的に解決**する。判定ロジックはDB関数1箇所にだけ置く。シフトが差し替われば宛先も自動で追従する。担任だけは例外で、俊さんの指示によりマスタ登録する(日々変わらないため)。
3. **一覧はオープン、確認義務は宛先に。**連絡の閲覧は自施設の全職員に開き(申し送りノートを皆が読める運用と同じ)、アラート・確認ボタン・未確認バッジは**宛先該当者のみ**に出す。
4. **書き込みは全てRPC経由・テーブルはRLS deny-all。**staff_pins・guardian_notices と同じ流儀。保護者ドメインからは一切到達不能。
5. **プッシュは既存の notifications outbox を使う**(職員宛て target_employee_id は既存機構)。プッシュは「気づきの補助」、アプリ内のアラート表示が「正」。

## 3. スコープ

**含む**: 園内連絡のDB・RPC・全アプリのUI(送信/一覧/アラート/確認)・時間帯マスタ・**職員マスタのクラス担任設定**・園内記録からの「申し送り」廃止・プッシュ連携・園内記録モーダルのUI改善・職員PIN管理の職員マスタへの移動。

**設計のみ(実装は将来)**: 返信コメント(§5.6。テーブル・拡張点として設計に含めるが、今回はUI・RPCを実装しない)。

**含まない**: 施設をまたぐ連絡(統括向け。将来検討)、添付ファイル、園児への構造化リンク。

## 5. データモデル(Phase 2)

### 5.1 `staff_time_bands` — 時間帯区分マスタ(施設別・人は登録しない)

早番は「シフト**開始**時刻」、遅番は「シフト**終了**時刻」で判定するため、開始窓と終了窓の両方を持てる構造にする(どちらか一方のみ設定)。

| 列 | 型 | 説明 |
|---|---|---|
| `id` / `office_id` / `name` / `sort_order` | | 施設別の帯定義。表示名は施設で変更可 |
| `start_from` / `start_until` | time null | シフト開始時刻がこの範囲なら該当(早番用) |
| `end_from` / `end_until` | time null | シフト終了時刻がこの範囲なら該当(遅番用) |

**シード(冪等。俊さんの回答した実運用値を初期値とする)**:

| 施設 | 早番(開始窓・仮幅30分) | 遅番(終了窓) |
|---|---|---|
| 大和オハナ保育園 | 07:00〜07:30 | 19:00〜 |
| BABY MAHALO | 07:00〜07:30 | 20:00〜 |
| Halelea | 08:00〜08:30 | 19:00〜 |
| Mahalo Station | 08:00〜08:30 | 19:00〜 |

- **中番はマスタに置かず導出する**: 対象日にシフトがあり、早番にも遅番にも該当しない職員。宛先UIには「中番」も並べる(判定はシステム定義)。
- 早番の窓幅30分は仮値。Phase 1 でシフト開始時刻の実分布を調査し、必要なら提案を添えて調整する(admin_web の設定画面で施設ごとに変更可能にする)。

### 5.2 `staff_messages` — 連絡本体

| 列 | 型 | 説明 |
|---|---|---|
| `id` / `office_id` / `author_employee_id` / `body` / `created_at` / `updated_at` | | 連絡は自施設内 |
| `target_date` | date | 対象日(時間帯宛て・クラス宛てで必須。「明日の早番へ」の"明日") |
| `deleted_at` | timestamptz null | 論理削除(送信者と主任以上のみ)。**物理削除は行わない**(俊さん指示: 削除しない形で閲覧できる状態を保つ) |

### 5.3 `staff_message_targets` — 宛先(1連絡に複数可・種別は併用可)

| 列 | 型 | 説明 |
|---|---|---|
| `message_id` | uuid FK | |
| `target_type` | text | `individual` / `band` / `facility` / `class` (CHECK)。**将来の区分追加はこのCHECKへの値追加で対応**する旨をコメントに明記 |
| `employee_id` | uuid null | individual のとき必須 |
| `band_id` | uuid null | band のとき必須 |
| `class_id` | uuid null | class のとき必須(childcare_classes 参照) |

### 5.4 `class_homeroom_assignments` — クラス担任(新設。職員マスタから設定)

| 列 | 型 | 説明 |
|---|---|---|
| `class_id` | uuid FK | childcare_classes |
| `employee_id` | uuid FK | 担任(1クラスに複数可・1職員が複数クラスも可) |
| `assigned_at` / `unassigned_at` | timestamptz | 履歴を残す(年度替わりで担任が変わるため) |

- 設定UIは**職員マスタ**(職員詳細に「担任クラス」欄)。クラス側からも見えると便利だが、編集は職員マスタに一本化する。
- 担任は日々変わらないためマスタ登録する(俊さんの指示。§2-2 の「人を帯に登録しない」原則の例外として明記)。

### 5.5 `staff_message_reads` — 確認(既読)

| 列 | 説明 |
|---|---|
| `message_id` + `employee_id` 複合ユニーク | |
| `opened_at` | 本文を開いた時点で自動記録 |
| `acknowledged_at` | **「確認しました」ボタン**を押した時点。管理側が見るのはこちら |

- 申し送り文化では「読んだ」と「承知した」は別。アラート(未確認バッジ)は `acknowledged_at` が入るまで消えない。
- 送信者と主任以上は、連絡ごとに「宛先該当者の一覧と確認状況(確認済み/未確認)」を見られる(`fetch_staff_message_ack_summary`)。

### 5.6 `staff_message_comments` — 返信コメント(**設計のみ・今回は実装しない**)

| 列 | `id` / `message_id` / `author_employee_id` / `body` / `created_at` |
|---|---|

- テーブルは本マイグレーションで**作成だけ**しておく(将来UIを足すだけで使えるように)。RPC・UI・アラート連動は実装しない。将来実装時の仕様メモ: コメントは連絡の閲覧者全員が読め、投稿すると送信者と既コメント投稿者にアラート。

## 6. 宛先解決(この設計の核)

### 6.1 判定関数はDB関数1箇所

`is_staff_message_addressed_to(p_message_id, p_employee_id)` を SECURITY DEFINER で実装し、**アラート件数・確認義務の判定・プッシュ宛先解決のすべてがこの関数(またはこれを使うビュー)を経由する**。フロントで判定を再実装しない。

| target_type | 「宛先該当」の判定 |
|---|---|
| `individual` | employee_id 一致 |
| `band` | 対象職員が `target_date` に当該施設でシフトを持ち、開始時刻が帯の開始窓に入る(早番)/終了時刻が帯の終了窓に入る(遅番)/どちらの帯にも該当しないシフトがある(中番) |
| `facility` | 当該施設の在籍職員全員 |
| `class` | `class_homeroom_assignments` で当該クラスの**担任**である(unassigned_at が null) |

### 6.2 閲覧と確認義務は別物

- **閲覧**: 自施設の全職員が全連絡を一覧で読める(クラス宛てを「その日クラスに入った担任以外」も読めるように、という俊さんの要望を全区分に一般化。申し送りノードの掲示板運用と同じ)。
- **確認義務(アラート・確認ボタン・未確認バッジ・確認状況の集計対象)**: §6.1 の宛先該当者のみ。
- この2層構造により「担任には確実に届き、その日入った職員も見られる」が実現する。

### 6.3 シフト差し替えへの追従

band 宛ての該当者は読むたびに動的解決するため、送信後にシフトが差し替われば新しい担当者に自動で表示される。プッシュ(§8)だけは送信時点の解決で飛ぶため、差し替え後の職員はプッシュを受け取れないが、ログイン時のアラート(§7)で必ず気づける。この非対称は仕様として画面ヘルプに明記する。

### 6.4 クラス宛てのUI表示条件

大和オハナ以外の3園は合同保育のためクラス連絡を使わない(俊さん指示)。機能フラグ `class_messaging_enabled` を施設別に持ち、**シードで大和オハナのみON**にする。宛先選択UIの「クラス」タブはこのフラグがONの施設でのみ表示する(施設名のハードコード禁止)。

### 6.5 Phase 1 調査で確定すること

シフトのテーブル構造(名称・日付・開始/終了時刻の持ち方・下書き/確定の状態があるか)と、直近シフトの開始・終了時刻の実分布(早番窓30分の妥当性、19:00/20:00終了の該当者数)。**確定済みシフトのみを判定対象にするか下書きも含めるか**は調査結果を添えて提案すること。

## 7. アラート(気づきの仕組み)

| アプリ | 挙動 |
|---|---|
| Ohana Kids(共有iPad) | **PINログイン直後**に自分宛て未確認の連絡が N 件あればバナー「あなた宛ての連絡が N 件あります」→ タップで一覧へ。ヘッダーの「園内連絡」アイコンに未確認バッジ常時表示 |
| Ohana Staff(個人スマホ) | 同上のバッジ + プッシュ受信 |
| admin_web | ヘッダーにベルアイコン + 未確認バッジ |

- 「未確認」= 宛先該当かつ `acknowledged_at` 無し。件数取得RPCは §6.1 の判定関数を使う。
- 共有iPadでは**ログイン中の本人の分だけ**表示する(前の利用者の連絡を出さない)。
- facility 宛ては全職員にアラートが出る(全員が確認対象)。

## 8. プッシュ連携(Phase 4)

- 送信RPCが、送信時点の宛先該当者(individual 全員 + band/クラス/施設を送信時点で解決した職員)を**既存 notifications outbox に `target_employee_id` 行として積む**。既存の `dispatch-pending-notifications` がFCM送信する。新系統は作らない。
- タイトル例: 「【園内連絡】◯◯さんから」。ロック画面に本文を出しすぎない(先頭20字程度)。

## 9. 園内記録からの「申し送り」廃止(Phase 2 に含める)

1. マイグレーションで `child_internal_notes.category` の CHECK から `'handover'` を除去。既存の handover 行(ステージングのテストデータのみ。本番は145未適用で0件)は `'other'` へ変換し、本文先頭に `【旧:申し送り】` を付す。
2. `fetch_child_internal_notes_for_ai` の許可区分を `('observation')` のみに変更。
3. フロント定数から「申し送り」を削除(区分は4種になる)。
4. 園内記録モーダルに案内文を1行: 「職員間の申し送り・連絡は『園内連絡』をご利用ください」+ 園内連絡への導線。

**本番未適用のいまが変更の好機**(本番に handover データが存在しないため移行が発生しない)。この旨をマイグレーションのコメントに記録すること。

## 10. 権限・RLS・フェーズ・E2E

- **送信**: 自施設の全職員(一般職員含む。遅番の一般職員が翌朝の早番へ送るのが主用途)。**削除(論理)**: 送信者本人と主任以上。**閲覧**: 自施設の全職員(§6.2)。施設をまたぐ閲覧は不可(統括は将来)。**確認状況の集計閲覧**: 送信者本人と主任以上。
- テーブルは RLS deny-all、読み書きは全て SECURITY DEFINER RPC(`create_staff_message` / `fetch_staff_messages`(自施設一覧・既定30日・アーカイブ切替で全期間) / `fetch_staff_message_detail`(開封記録を含むため volatile) / `acknowledge_staff_message` / `fetch_my_alert_count` / `fetch_staff_message_ack_summary` / 担任設定の `assign_homeroom` / `unassign_homeroom` / `fetch_homeroom_assignments`)。`log_sensitive_access` は呼ばない(園児機微を含まない前提)。
- 一覧の既定表示は直近30日。それ以前は「アーカイブを表示」で全期間閲覧可。**物理削除は一切行わない**。
- フェーズ: **P0** §4 の3点 → **P1** 調査(§6.5) → **P2** DB(§5・§6・§9 を1マイグレーション+担任テーブル。全文提示→承認→ステージング) → **P3** UI(admin_web/Kids/Staff の送信・一覧・アラート・確認 + 職員マスタの担任設定) → **P4** プッシュ。コメントUIは将来フェーズ。
- 拒否側E2E(実アカウント): ①他施設職員に一覧が見えない ②band 非該当(対象日シフト無し/窓外)の職員にアラートが出ない(一覧では読める) ③シフト差し替えで新該当者にアラートが移る ④クラス宛てが担任にアラート・非担任は閲覧のみ ⑤class_messaging_enabled がOFFの施設でクラス宛てUIが出ない ⑥保護者アカウントからテーブル・RPC共に到達不能 ⑦acknowledge を他人が代行できない ⑧削除(論理)は送信者と主任以上のみ・物理削除経路が存在しない ⑨確認状況の集計は送信者と主任以上のみ取得可。

## 12. 実装者への禁止事項

- 職員×時間帯の対応マスタ・登録画面を作らない(担任マスタ §5.4 だけが俊さん指示による例外)。
- band/クラス/施設の判定ロジックをフロント・Edge Function に複製しない(DB関数1箇所)。
- 新しいプッシュ送信系統を作らない(既存 outbox のみ)。
- `handover` 廃止で園内記録の他の区分・既存データに触れない(変換対象は handover 行のみ)。
- 物理 DELETE を実装しない(論理削除のみ)。
- マイグレーションの承認前適用・本番への書き込み・保護者ドメインへの一切の実装。
