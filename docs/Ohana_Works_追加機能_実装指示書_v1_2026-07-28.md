# 3. この環境で作業するための実装ルール(全Phase共通・違反厳禁)

過去の実事故から抽出したルール。原案 §10.4 の禁止事項に加えて守ること。

## 3.1 マイグレーション

- 置き場所は **`supabase/migrations/`**。`admin_web/supabase/migrations/` に作ってしまう誤りが過去に複数回あった。作成後に `ls` でパスを確認する
- 採番は既存の連番形式(最新は `20260714000136_...`)。作成前に必ず `supabase migration list --linked` で最新番号とlocal/remote差分0を確認する
- 破壊的マイグレーション禁止(原案 §10.4)。列削除・型変更は行わず、追加とビュー/RPC差し替えで対応
- 重い制約(EXCLUDE等)の作成は ACCESS EXCLUSIVE ロックを取るため、**登園・降園のピーク時間帯(平日朝夕)を避けて適用**する

## 3.2 RPC設計 — RETURNS TABLE の列名衝突(既知の頻出バグ)

`RETURNS TABLE` 関数で戻り値の列名と参照テーブルの列名が同名だと `column reference "..." is ambiguous` で**実行時に必ず失敗**する。このバグで bulk_promote_children(132番から)と fetch_employees_tax_withholding_status(16番から)が長期間稼働不能だった。新規RPCでは:

- 戻り値列名と同名の列を本体で参照する場合、必ずテーブル名/エイリアスで修飾する
- ローカル変数は `v_` 接頭辞で統一
- 作成後、次の観点で自己レビューする: 「戻り値列名の集合」と「本体が参照する全テーブルの列名の集合」の積集合に含まれる名前が、無修飾で本体に出現していないか(この機械的スキャンで過去の全件洗い出しを行った実績がある)

## 3.2b `log_sensitive_access()` を呼ぶ閲覧RPCは `stable` にしない(既知の頻出バグ)

`log_sensitive_access()` は `sensitive_access_logs` への INSERT を伴う。この関数を呼ぶRPCを `stable`(または `immutable`)として定義すると、PostgRESTがそのRPC呼び出しを読み取り専用トランザクションとして実行するため、`cannot execute INSERT in a read-only transaction` で**実行時に必ず失敗**する。

- 「見た目は読み取り専用の関数」に飛びついて `stable` を付けないこと。`log_sensitive_access()` を呼ぶ関数は例外なく `volatile`(既定、`language plpgsql security definer set search_path = public` のみでvolatile/stable指定を書かない)にする
- 既存の同種関数(`fetch_payroll_transfer_recipients`・`fetch_employees_tax_withholding_status`・`fetch_employee_facility_wages`)はいずれもこの理由でvolatile
- **型チェック・マイグレーションのドライラン(`begin;`〜`rollback;`)では検出できない。** ドライランはservice_role/postgres接続で実行され読み取り専用トランザクション化の対象にならないため、エラーが再現しない。**実際にPostgREST経由(実サインインセッションまたは相当のRPC呼び出し)で実行する拒否側/正常系E2Eでのみ発覚する**(園内記録機能Phase Bで実際に発生した不具合。マイグレーション145→146番で修正)
- 新規に閲覧系RPCを作る際は、作成後に `select proname, provolatile from pg_proc where proname = '...';` で `v`(volatile)になっていることを確認する

## 3.2c `stable`/`immutable` 全体の横断チェック(2026-07-30時点)

`log_sensitive_access()` を呼ぶ全関数(`fetch_child_internal_notes`・`fetch_child_internal_notes_for_ai`・`fetch_employee_facility_wages`・`fetch_employees_tax_withholding_status`・`fetch_payroll_transfer_recipients`)は、上記修正後すべて`volatile`であることを確認済み。他に同様の不具合を抱える既存関数は無い。

## 3.3 本番DBでの検証プロトコル(ステージング導入までの間)

- 書き込みを伴う検証は `begin; ... SELECTで確認 ...; rollback;`(確定するときのみ commit)を**1つのSQLファイルにまとめ、`supabase db query --linked --file` の1回のツール呼び出しで実行**する。分割実行すると begin が効かず即コミットされる
- `supabase db query --linked` は `auth.uid()` が null になるため、`manages_childcare()` 等の権限チェック付きRPCは必ず not authorized で落ちる。回避が必要な場合はトランザクション内で `set local request.jwt.claims` に検証用職員の auth_user_id を設定する方式のみ許可。**`my_employee_id()` 等の関数を `create or replace` で一時差し替えする方式は絶対禁止**(誤ってコミットされると全ユーザーが管理者化する)
- 認可まわり・UI操作が必要な確認は回避策を探さず、手順を明示してユーザー(人間)に依頼する
- 検証用データは終了後に必ず元の状態へ復旧する(園児・職員は物理削除できない。テストレコードを増やさない工夫をする。FK順序に注意: 例 daily_child_status.last_event_id → child_attendance_events)

## 3.4 動作確認の基準 —「呼び出さずに検証したつもり」を繰り返さない

2026-07-28に「実装完了・検証済み」と記録されていた機能3件が実は一度も動作していなかった(いずれも呼び出さずに検証済み扱いにしていた)。今回の3機能は行政提出物と人事文書であり、この失敗は許されない。

- 実装した経路を**実際に呼び出して**確認する。コードレビューだけで「検証済み」としない
- **成功パターンと失敗するはずのパターンの両方**を試し、判定・ゲートが本当に切り替わることを確認する(例: 権限外職員でAPIを叩いて拒否されること、必須未入力で承認がブロックされること、の「拒否側」も必ず実行する)
- 確認結果は「何をどう呼び、何が返ったか」まで記録する

## 3.5 コミットとデプロイ

- 本番適用した変更は**同日中にコミット・push**する(本番稼働済みなのに未コミットの作業が3件溜まっていた事故の再発防止)
- DBのみの変更はVercelデプロイ不要。admin_web変更は tsc / eslint / next build、Flutter変更は dart analyze を通してからコミット
- admin_webの本番反映はVercel(team: ohana-works)。反映後にブラウザでの実機確認まで行って完了とする

# 4. 設計判断(Fableの判断と理由)

原案が実装者の裁量に委ねている、または現行環境の実態を踏まえて決める必要がある論点。Phase 0 の調査結果がここでの前提と食い違った場合は、判断を機械的に適用せずユーザーへ報告すること。

## D1. 画面の載せ先

- **架け橋・支援保育の全画面(日常入力含む)= admin_web `/childcare/*` 配下。** 理由: 保育業務のWeb画面群は既に `/childcare/*` に集約され、施設選択の保持(useChildcareOffices、`?office=` クエリ)、ChildcareNav、`manages_childcare()` 権限、Suspenseラップまでパターンが確立している。別アプリを新設すると認証・権限・施設選択を二重に作ることになる。原案 §6.12 の「スマートフォンやiPadでも入力しやすい工程別フォーム」はレスポンシブ対応で満たす
- **個別目標シート = admin_web の職員管理系新ルート**(例 `/hr/goal-sheets`。既存の職員系ページの命名規則にPhase 0で合わせる)。`/childcare` 配下に置かない。理由: 利用権限が保育業務権限ではなく人事系権限であり、ナビゲーション・権限の系統を混ぜない
- **本人閲覧はOhana Staff(Flutter)に「自分の目標シート」画面を追加。** 既存の「自分の勤怠」と同じセルフビュー系統。parent_app・Ohana Kidsには何も追加しない
- Ohana Kids のWeb化(将来方針)とは独立に進める。本件をWeb化の口実にしない

## D2. 権限・RLSドメイン

現行の絶対要件「職員業務 / 保育業務職員側 / 保護者の3ドメイン完全分離」を維持したうえで:

- 3機能とも**保護者ドメインへは一切公開しない**(RLS・RPC・Storageすべて)。園児の発達・支援情報を扱うが、保護者向け開示は本スコープ外
- 個別目標シートは職員ドメイン内に新しい軸を持ち込む: 「対象職員本人は配布後の自分のシートのみ閲覧可、他人のシートは主任以上のみ」。本人閲覧用RPCは `my_employee_id()` 基準で自分の released 済みシートだけ返す専用のものを新設し、管理用RPCと分離する
- 機微情報(健康・配慮事項、発達・支援内容)は**専用テーブルに分離**し、園長・主任・法人管理者・個別指定職員のみ閲覧可。先行事例として、officesテーブルに機微列があるため保護者には fetch_my_children_office_names()(security definerで必要最小列のみ返す)を新設した判断がある — 同じ思想で「必要最小の列だけ返す専用RPC」を機微アクセスの唯一の経路にする
- 「主任」「園長」「法人管理者」「支援児童確認担当者」が既存の roles(employee_roles×roles)のどれに対応するかは **Phase 0 で実テーブルを確認**し、対応表を作ってからRLSを書く。原案 §11.4 のとおり、担当者指定は役職でなく「年度・施設・対象業務ごとの付与」テーブルで持つ
- **役職の実態(2026-07-28 ユーザー確認済み):** 「園長」がいるのは大和オハナ保育園のみ(大原利奈)。BABY MAHALO・Mahalo Station・Haleleaには園長の代わりに「管理者」という役職があり、その上の「施設長」は高木俊(事務長兼務、3園の施設長)。したがって承認ロジックを役職「園長」に固定すると3園で破綻する — 原案 §13 の「最終承認者を園長に固定するか施設ごとに指定するか」は**施設ごとの承認者指定テーブルで確定**。個別目標シートの最終承認者の初期データは 大和オハナ保育園=大原利奈、他3園=高木俊。「主任確認」ステップを実際に誰が担うか(3園では「管理者」か)は Phase 0 の対応表作成時に確認する
- 機微テーブルへのアクセスは既存の sensitive_access_logging 機構で記録する

## D3. 「共通文書・承認基盤」の粒度 — 汎用エンジンは作らない

原案 Phase 1 は「共通文書・承認基盤」を先行構築せよと読めるが、**汎用の文書管理エンジン(全文書型を1つの状態機械で処理する仕組み)は作らない**。共有するのは次の4点に限定する:

1. `document_templates` — テンプレート版管理(原案 §3.5 の項目そのまま。3機能共用)
2. `ai_runs` + `ai_run_evidence_links` — AI実行履歴と根拠記録リンク(3機能共用。§D5)
3. **スナップショット方式** — 各機能の文書テーブルに `snapshot jsonb` 列を持ち、確定(finalized)時に自動入力値の解決結果を「値+取得元+基準日」の形で凍結する。編集中はマスタをライブ参照し、確定後はスナップショットのみを表示・出力に使う
4. **状態語彙と列名の統一** — status値(draft/ai_draft/in_review/returned/approved/finalized/released/superseded/archived)、version/supersedes_id、author_id/reviewer_id/approver_id、finalized_at/released_at 等の列名を3機能で完全に揃える

承認フロー自体は**機能別テーブル(原案 §4.9/§5.11/§6.13 の *_reviews 等)+機能別RPCで個別に実装**する。

**Fableの判断(理由):** (1) 3機能の承認経路は似て非なるもので(個別目標=作成→主任確認→園長承認→配布+本人閲覧確認、架け橋=担任→主任→園長+改訂許可フロー、支援保育=複数名確認・提出後の行政イベント追跡付き)、汎用化すると条件分岐の塊になる。(2) 現行コードベースは「機能別RPC+機能別RLS」のパターンで一貫しており、Opus/Sonnetが既存コードを参照しながら差分実装するにはパターン踏襲が最も事故が少ない。(3) 原案 §7.2 も「共有してよい概念」と言うだけで共通実装を強制しておらず、§7 末尾の「1つの巨大テーブルへ統合してはならない」の精神はむしろ個別実装側にある。語彙と列名さえ揃えれば、将来の汎用化リファクタは可能。

## D4. スナップショットと改訂

- `finalized` 時に (a) snapshot jsonb 凍結 (b) PDF生成 (c) テンプレート版・データ版・生成日時・生成者・ファイルハッシュを *_exports/*_releases 系テーブルに記録
- 改訂は「新しい行を version+1・supersedes_id 付きで作る」方式。旧行は superseded にするだけで本文もPDFも残す。UPDATE で本文を書き換える経路を作らない(確定後はRLS/トリガで本文UPDATEを拒否する)
- 旧年度PDFを新テンプレートで再生成する機能は作らない(原案 §3.5)

## D5. AI基盤(新規構築)

- **実行はEdge Function経由のみ。** APIキーはVault管理(レガシーAPIキー移行でVault運用・Edge FunctionのSecrets切替の実績あり)。ブラウザ・アプリへキーを渡す経路を作らない

- **ステージング環境: 導入する。** 第2Supabaseプロジェクト+匿名化データで開発し、本番へは検証済み成果物のみ適用(§5 Phase 0.5)
- **支援保育の実運用: 2027年度(令和9年度)から。** 令和8年度前期様式は検証素材として登録(§5 Phase 3)
- **現状の運用実態**: 支援保育の様式1・2は市から届いたExcel専用様式で作成しており、**大和市への提出実績あり**。Phase 3 で過去提出物の匿名化コピーの提供を受け、(a) システム出力と実物の照合(印刷範囲・改ページ・チェック欄)、(b) 受理実績のある記入の粒度・文体をAI下書きの品質基準、に使う。**取り扱い注意**: 実物ファイルは氏名・生年月日等を伏せた匿名化コピーのみを使い、リポジトリにもステージングDBにも実名データを入れない
- **役職と最終承認者**: §4-D2 に反映済み(園長は大和オハナのみ=大原利奈、他3園は管理者+施設長(高木俊が事務長と兼務)。個別目標シートの最終承認者=大和オハナ:大原利奈、他3園:高木俊)。原案 §13 の「最終承認者の指定方式」は施設ごと指定で確定

# 7. 完了の定義

各Phaseの完了条件は次をすべて満たすこと。

1. 原案の該当受入基準(§4.10 / §5.12 / §6.14 / §12)を1項目ずつ**実際に操作・呼び出しで**確認し、結果(何を叩いて何が返ったか)を記録した
2. 成功系だけでなく、拒否・ブロックされるべき操作の失敗系を実行して確認した
3. 検証用データを復旧し、本番データが検証前の状態に戻っている
4. tsc / eslint / next build / dart analyze(該当分)がクリーン
5. コミット・push済みで working tree clean、`supabase migration list --linked` の差分0
6. ユーザーによる実機確認(ブラウザ/実機)まで完了した
