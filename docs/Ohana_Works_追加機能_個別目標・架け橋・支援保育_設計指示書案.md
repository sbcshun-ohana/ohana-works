# Ohana Works 追加機能設計指示書案
## 個別目標シート・架け橋カリキュラム・支援保育事業

- 文書種別：Claude Codeへ渡すための設計指示書案
- 作成日：2026-07-28
- 対象：Ohana Works 現行リポジトリ
- 前提：Claude Codeは本書をそのまま実装仕様とせず、現行コード、DBマイグレーション、RLS、画面、既存設計書を確認し、差分調査を行ったうえで最終設計指示書を作成すること
- 個人情報：本書には添付様式の構造だけを反映し、園児・職員の実データは記載しない

# 1. 本書の目的

Ohana Worksへ次の3機能を追加する。

1. 管理者Webの「個別目標シート」
2. 保育業務Web・管理者Webの「架け橋カリキュラム」
3. 保育業務Web・管理者Webの「支援保育事業」

既存の職員・施設・園児・クラス・権限・文書・AI・承認・監査ログを再利用し、同じ情報の二重登録を避ける。自治体様式や国の参考様式が変更されても、DBの全面改修をせずテンプレートを差し替えられる構造とする。

本機能は、行政要件の充足や補助金取得を保証するものではない。要件の確認、資料作成、承認、提出準備、履歴保存を支援するシステムとして実装する。

# 3. 共通設計原則

## 3.0 入力負担を最小化する方針

3機能に共通して、利用者へ同じ情報を繰り返し入力させない。

画面設計は次を優先する。

1. 既存マスタ・履歴から自動入力
2. 選択肢、チェックボックス、候補提案
3. 前年度・前期・直近記録からの引継ぎ
4. AIによる文章案作成
5. 利用者は内容確認と必要箇所の修正

長い文章を最初から手入力させる画面は原則として作らない。

### 自動入力する情報

既存の各マスタ・履歴に登録されている場合は、少なくとも次を自動取得する。

- 法人名
- 施設名・施設住所・連絡先
- 年度・対象期間・前期／後期
- 職員氏名・職員番号・役職・職種・所属施設・入社日
- 園長・主任・担当者等の氏名
- 園児氏名・園児管理番号・生年月日・年齢・月齢
- クラス・在籍施設・入所日・在籍期間
- 保護者情報
- 進学予定小学校
- 過去の承認済み保育記録、面談記録、支援記録、関係機関連携記録
- 過年度の確定文書

自動入力値には取得元と基準日を内部的に保持する。確定済み文書では、後日マスタが変更されても当時の値を再現できるスナップショットを保存する。

### 入力UIの原則

- 初期画面には、その工程で必要な項目だけを表示する。
- 詳細項目は「詳細を入力」等で展開する。
- 入力済み、要確認、未入力を色とアイコンだけに頼らず文字でも表示する。
- 同じ情報を複数様式へ転記する場合は、共通データを1回入力して各様式へ反映する。
- 自動入力した値を変更する場合は、文書上だけの修正か、元マスタの変更申請かを選べるようにする。
- 前回値の無条件コピーは禁止し、引継ぎ候補として提示して確認を求める。
- 必須項目を一度に大量表示せず、工程別のステップ形式を採用する。

### AI文章作成の効率化

AIは自由入力欄の横に単純な「AI生成」ボタンを置くだけでなく、次の流れで利用する。

```text
参照期間・参照記録をシステムが候補選択
→ 利用者が使用する記録を確認
→ 強み・支援・目標等を短い箇条書きで追加
→ AIが項目別の文章案を作成
→ 「採用」「一部修正」「再作成」「使用しない」を選択
→ 人が最終確認
```

- AIは文書全体を毎回作り直さず、選択した項目だけを生成・再生成できること。
- 「短くする」「やわらかくする」「具体的にする」「重複を減らす」等の補助操作を用意する。
- AIが作成した文章と人が追記した文章を内部履歴で区別する。
- AI生成後も、必須の事実確認項目は自動完了扱いにしない。

## 3.1 年度・期間

- 年度は4月1日から翌年3月31日とする。
- 年度、対象期間、提出回、様式版はコードへ固定せずマスタ化する。
- 「令和8年度」「前期」「6月30日」等は、該当年度の設定値として保存する。
- 過年度データは当時の職員所属、園児在籍、様式版、承認者、AI設定で再現できること。

## 3.2 文書の状態

共通状態の例：

```text
draft
ai_draft
in_review
returned
approved
finalized
released
superseded
archived
```

- `approved` とPDF確定を混同しない。
- `finalized` 後の本文を直接上書きしない。
- 修正時は改訂版を作成し、旧版と新旧関係を保持する。
- PDF確定時に、テンプレート版、データ版、生成日時、生成者、ファイルハッシュを保存する。

## 3.3 AI利用原則

- AIは下書き支援であり、承認や行政判断を代替しない。
- 使用した根拠レコードを保持し、画面から確認できること。
- 根拠のない事実、診断名、障害名、家庭事情、性格評価を補完しない。
- 根拠不足は「要確認」と表示する。
- AI生成文は人が編集・確認して初めて提出可能とする。
- APIキーはサーバー側で管理し、ブラウザやアプリへ返さない。
- 入力データ、使用Provider・モデル、プロンプト版、出力、実行者、日時、採否を記録する。
- Claude/OpenAIを管理者設定で切り替えられる既存方針に合わせる。
- 機微情報を外部AIへ送信する場合は、送信項目を最小化し、法人が承認した設定でのみ実行する。

## 3.4 セキュリティ

- 画面の非表示だけで権限制御を完了させない。
- API、Server Action、DB RLS、Storage署名URLの全層で確認する。
- 健康、発達、障害、家庭、支援、マイナンバー等の機微情報は一般職員から分離する。
- 機微文書の閲覧、編集、AI送信、PDF生成、ダウンロードを監査ログへ記録する。
- PDFや添付を公開URLにしない。
- 退職者、退園児、異動者についても保存義務に従い履歴を残し、現在権限では閲覧できない状態を作る。

## 3.5 テンプレート管理

行政文書は、本文データと出力レイアウトを分離する。

テンプレートに持たせる情報：

```text
template_key
document_type
jurisdiction
fiscal_year
term
version
effective_from
effective_to
source_file_name
source_file_hash
mapping_definition
required_field_definition
status
```

- 国参考様式、大和市様式、将来の他自治体様式を併存可能にする。
- 旧年度の確定PDFを新テンプレートで自動再生成しない。
- 様式変更時は差分を管理者へ表示し、移行が必要な項目を確認できるようにする。

# 4. 機能1：個別目標シート

## 4.1 目的

各職員について年1回、前年の勤務・関わりを振り返り、強みを言語化し、次年度の育成方向と四半期目標を共有する。

懲戒、人事査定、退職勧奨、批判の文書として使用しない。職員の成長支援、相互理解、園の価値観との接続を目的とする。

## 4.2 対象期間

- 原則：前年3月1日から当年2月末日までの最長1年間
- 入社後1年未満：入社日から当年2月末日まで
- 休職期間等を除外するかは管理者が対象期間と備考で明示する
- 3月に作成・承認し、4月に本人へ配布する
- 年度設定で作成開始日、承認期限、配布日を変更可能にする

## 4.3 権限

| 操作 | 権限 |
|---|---|
| 新規作成 | 主任以上 |
| AI文章案作成 | 主任以上 |
| 編集 | 作成者、対象施設の主任、園長、法人管理者 |
| 最終承認 | 園長または法人が指定する承認者 |
| 本人配布 | 承認者または配布権限者 |
| 本人閲覧 | 対象職員本人のみ |
| 全施設横断閲覧 | 法人管理権限者のみ |

対象職員本人は、他職員のシートを閲覧できない。

## 4.4 作成フロー

```text
年度・対象職員を選択
→ 評価対象期間を自動算出
→ 所属・役職・評価期間・前年度目標等を自動入力
→ システムが対象期間の関連記録を候補表示
→ 作成者が使用する記録を選び、事実・長所・注意事項を短い箇条書きで補足
→ AIが育成目的の文章案を作成
→ 作成者が修正
→ 主任確認
→ 園長等が最終承認
→ PDF確定
→ 4月に職員アプリへ配布
→ 本人の閲覧確認を記録
```

## 4.5 必須記載項目

1. 日々の関わりへの理解とねぎらい
2. その人らしさ、強みの言語化
3. 園の価値観と本人の特性がつながる点
4. 今後の成長につながる視点と方向性
5. 注意事項
6. 4月〜6月の育成目標と背景・意味
7. 7月〜9月の育成目標と背景・意味
8. 10月〜12月の育成目標と背景・意味
9. 1月〜3月の育成目標と背景・意味

## 4.6 追加を推奨する項目

- 前年度目標の振り返り
- 具体的な事実・エピソード
- 本人が発揮した専門性
- チーム・保護者・園児への良い影響
- 管理者が提供する支援
- 研修・経験機会の提案
- 目標達成の観察指標
- 四半期面談日、振り返り、次四半期への引継ぎ
- 本人コメント欄
- 本人の閲覧確認欄

「本人の課題」だけでなく、「管理者がどのように支援するか」を必ず記載できる構造を推奨する。

## 4.7 AI文章ルール

### 入力

- 箇条書きの事実
- 良かった行動
- 強み
- 園の価値観との接点
- 育成したい能力
- 注意事項
- 四半期目標案

### 出力

- 敬意があり、具体的で、本人が次の行動を理解できる文章
- 批判、断定的な人格評価、威圧、皮肉を含めない
- 注意事項は曖昧にせず、事実・期待する行動・支援方法を明示する
- 根拠のない評価を追加しない
- 「いつも」「絶対」「向いていない」等の過度な一般化を避ける
- 医療・障害・家庭状況等を推測しない

### 推奨する注意事項の構造

```text
確認された状況
期待する行動
園・管理者が行う支援
確認時期
```

- 対象期間の記録候補
- 箇条書き入力
- AI下書き
- AI根拠・生成履歴
- 本文編集
- 四半期目標
- 注意事項
- 管理者支援
- プレビュー
- 確認依頼、差戻し、承認、PDF確定

初期入力は次の簡易フォームを基本とする。


- 本人コメントは法人設定で有効化可能

## 4.10 受入基準

- 入社1年未満の対象期間が入社日から2月末までになる。
- 主任未満は作成できない。
- AI生成文を人が確認せず確定できない。
- 必須項目と4四半期目標が未入力なら承認できない。
- 確定後の上書きができず、改訂版として履歴が残る。
- 配布前は本人に見えず、配布後は本人だけが閲覧できる。
- PDFと画面の内容が一致する。
- AI生成、編集、承認、配布、閲覧の履歴を追跡できる。

# 5. 機能2：架け橋カリキュラム

## 5.1 目的と初期対象

5歳児から小学校1年生へつながる教育・保育を、園・小学校・家庭・関係者の協働記録として整理し、小学校接続加算に関する資料準備を支援する。

初期導入：

```text
施設：大和オハナ保育園
対象：5歳児クラス
```

施設IDや法人IDをコードへ固定せず、施設・年度・クラス単位の機能フラグで制御する。将来、他施設・他法人・他自治体へ展開できるマルチテナント構造とする。

## 5.2 管理対象

- 業務分掌
- 年間計画
- 幼保小の協議録
- 小学校・地域との交流記録
- 幼児期の終わりまでに育ってほしい姿等に基づく記録
- 園児ごとの幼児の姿
- 移行支援シート
- 保育所児童保育要録
- 健康・配慮事項
- 添付資料
- 要件充足状況
- 承認・確定・提出履歴

## 5.3 共通データと文書分離

園児の基本情報、在籍、保育記録、成長、支援、連携、小学校情報等は共通データとして管理する。

同じ共通データから、次を別々の文書として生成する。

1. 移行支援シートPDF
2. 保育所児童保育要録PDF

一方のPDFを他方へ流用したり、1つのPDFに統合したりしない。各文書は独立したテンプレート版、承認状態、確定PDFを持つ。

## 5.4 作成・承認フロー

```text
担任作成
→ 主任確認
→ 園長承認
→ PDF確定
```

確定後の変更：

```text
主任以上が改訂許可
→ 改訂理由を入力
→ 新版を作成
→ 主任確認
→ 園長再承認
→ 新PDF確定
```

旧PDFを削除せず、旧版には「改訂済み」を付与する。

## 5.5 AI支援

- 対象年度の基準日から過去1年間の承認済み記録を参照する。
- 参照対象を園児、施設、クラス、記録日で厳密に限定する。
- 出力文ごとに参照記録を確認できるようにする。
- 根拠が不足する項目は「要確認」とする。
- 根拠のない発達評価、診断、家庭状況を生成しない。
- 事実と保育者の見立てを区別する。
- 引用元が修正・取消済みの場合は再生成・再確認を促す。
- AI結果だけで文書を承認・確定しない。

入力負担を減らすため、園児ごとに過去1年間の記録を手作業で探させない。日付、記録種別、発達・活動領域、作成者、承認状態を用いて参照候補を自動抽出する。

作成者は次だけを行うことを基本とする。

1. 参照候補の採用・除外
2. 現在の姿や変化の短い補足
3. AI文章案の確認・修正
4. 「要確認」の解消

AIは、共通データから移行支援シート用と保育要録用の文章を別々に作成する。文書の目的に合わせて表現を変えるが、元となる事実は共通とし、内容が矛盾しないよう整合チェックを行う。

## 5.6 機微情報

健康・配慮事項は、次の者だけが閲覧可能とする。

- 園長
- 主任
- 法人管理者
- 個別に指定された職員

担任であっても指定されていない場合は、一般記録と機微情報を分離して表示する。PDFに含める場合も文書種別・提出先・権限を確認する。

## 5.7 出力

- 園児別PDF
- 文書種別ごとのPDF
- 小学校別の一括PDF
- 年度一括PDF
- 年度一括ZIP
- ZIP内の一覧表

ファイル名は安全な文字へ正規化し、同姓同名時は園児管理番号等で区別する。

例：

```text
2026年度_○○小学校_移行支援シート_園児管理番号.pdf
```

# 6. 機能3：支援保育事業

## 6.1 添付資料から確認した令和8年度前期の要件

確認した資料：

1. `【通知文】令和8年度支援保育事業（前期分）について.pdf`
2. `㈰令和８年度前期「支援保育事業」提出票.docx`
3. `㈪様式1 集団生活で支援を必要とする子どもの姿.xlsx`
4. `㈫様式2 個別支援計画及び発達経過記録.xlsx`
5. `【表書き】前期.docx`

令和8年度前期について確認できた内容：

- 対象は、集団生活の姿から保育士加配等の個別援助を検討している3歳児から5歳児クラスの児童。
- 前期対象は令和8年4月から9月の在籍児童。
- 提出期限は令和8年6月30日。
- 不備の補正完了日が提出日となり、期限後は受付不可。
- 提出は大和市こども部ほいく課保育指導係へ原本を直接持参する。
- 電子メール提出は不可。
- 受付時に交付される提出書類受領確認票を保管する。
- 提出書類は、提出票、様式1、様式2。
- 様式1・2を基に市保育士が現場訪問し、実際の支援を確認する。
- 施設は、保育方針・日常保育・個別支援を説明できる「支援児童確認担当者」を選出する。
- 様式1・2は園長等の代表者を含む複数名で確認する。
- 補助金の使途予定と、児童への支援効果の見込みを具体的に記載する。
- 市による確認後の「支援児童対象児数確認表」は施設長等の署名が必要で、請求時まで双方で保管する。
- 後期分は10月から3月在籍児童を対象とし、別途案内予定。

これらは「令和8年度前期・大和市」の設定値として保持し、翌年度や後期へ固定的に流用しない。

## 6.2 目的

対象園児の支援記録を日常業務の中で蓄積し、申請時に必要な様式1・様式2・提出票・表書きを正確に作成し、提出前確認、訪問確認、受領確認票、対象児数確認表、請求まで一元管理する。

システムは対象資格を断定せず、必須項目の充足状況と確認事項を提示する。

## 6.3 管理単位

```text
法人
→ 施設
→ 年度
→ 前期・後期
→ 申請回
→ 対象園児
→ 様式・支援計画・記録
```

同じ園児が前期・後期・複数年度の対象となる場合も、それぞれ独立した申請スナップショットを持つ。

## 6.4 対象候補と登録

- 園児マスタから候補を選択する。
- 年度、期、年齢クラス、在籍期間を自動確認する。
- 「対象候補」「園内検討中」「提出対象」「対象外」を管理する。
- 対象外理由も記録できる。
- AIが申請対象を自動決定してはならない。

候補一覧には、年齢クラス、在籍期間、既存の個別支援計画、面談記録、関係機関連携記録の有無を自動表示する。利用者は対象候補をチェックして追加できるようにし、園児情報を一人ずつ再入力させない。

## 6.5 様式1の項目

### 基本情報

- 記入日
- 園名
- 年齢クラス
- 園児氏名
- 年齢（月齢）
- 性別（様式上必要な場合）
- 入所年月日
- 3・4・5歳児クラスの人数
- 各クラスの加配児童数
- 職員数
- 備考

### 1. 保育園の今後の方針

- 加配保育士を配置して支援予定
- 加配配置は困難だが、相談や療育につなげる予定
- 相談や療育につながっているが加配配置できていない
- 配置はしているが加配申請していない
- 目途年月
- 配置困難理由
- 申請しない理由

### 補助金の使用方法

- 保育士・保育補助員増員
- 保育士を支える職員等の増員
- 必要物品購入・環境整備
- 研修・保護者面談・関係機関連携強化
- その他
- 対象児童が受ける支援効果の見込み

### 2. 保護者との連携

- 直近面談日
- 面談者
- 面談内容
- 現在の支援状況
- 今後に向けた連携
- 保護者の意向

送迎時の会話だけを正式面談として扱わないよう、面談記録の種別を区別する。

### 3. 関係機関との連携

- 巡回相談
- 発達相談
- 児童発達支援事業所
- 保育所等訪問支援
- 担当者
- 相談日・通所開始日
- 頻度
- 具体的な連携内容
- 連携を通した具体的支援

「1年後まで様子を見る」等の長期的な様子見だけを定期連携として充足扱いにしない。

### 4. 子どもの姿

添付様式の分類とチェック項目をテンプレートデータとして登録する。

- 人間関係
- 言葉・表現
- 環境
- その他

チェックだけで完了とせず、様式2の「具体的な子どもの姿」へ根拠記録を連結する。

## 6.6 様式2の項目

- 年度
- 園児氏名
- 生年月日
- クラス名・年齢
- 年間目標
- 第1期から第4期までの期目標
- 教育の領域（健康・人間関係・環境・言葉・表現）
- 各期の具体的な子どもの姿
- 考えられる要因
- 支援の手立て
- 評価
- 保護者の意向
- 関係機関との連携

様式1でチェックした項目と、様式2の具体的な姿・要因・手立ての対応関係を画面で確認できること。

## 6.7 提出票の項目

- 提出日
- 施設名
- 支援児童確認担当者
- 3歳児提出人数
- 4歳児提出人数
- 5歳児提出人数
- 合計人数
- 様式1・様式2の添付確認

- 支援用物品
- その他の内容・金額
- 合計額

補助単価は年度設定とし、コードへ固定しない。添付提出票には92,000円/月および条件により12,000円/月の記載があるが、令和8年度前期の表示・試算条件として保持する。

既存給付費・補助金との重複可否を確認するチェック項目を設ける。

## 6.10 AI支援

AIで支援できる範囲：

- 日常記録から具体的な子どもの姿の文章案
- 保育者が入力した事実から考えられる要因の候補
- 実施済み支援から支援の手立ての整理
- 期ごとの評価案
- 保護者面談記録、関係機関連携記録の要約
- 入力漏れ・曖昧表現の指摘

### 効率的な作成手順

```text
園児を選択
→ 園児・施設・クラス情報を自動入力
→ 面談・関係機関・日常記録を自動収集
→ 様式1の該当候補と根拠記録を表示
→ 職員が該当項目と使用記録を確認
→ AIが様式2の「子どもの姿・要因・支援の手立て・評価」の文章案を作成
→ 職員が確認・修正
→ 様式間整合チェック
```

様式1のチェック結果、様式2の各欄、日常記録の関係を保持し、同じ内容を複数回入力させない。

禁止・制限：

- 診断名や障害名を推測しない。
- 医療・発達上の判断を確定しない。
- 申請対象、補助対象、加配必要性をAIだけで決定しない。
- 実施していない支援、面談、連携を生成しない。
- チェック項目に合わせるため事実を誇張しない。
- 根拠記録がない文章は「要確認」とする。

| P1 | 架け橋の共通記録と2種類のPDF | 初期運用の中核であるため |
| P1 | AI根拠表示と「要確認」 | 誤生成を業務資料へ混入させないため |

| P2 | 四半期振り返り | 育成サイクルを継続するため |
| P3 | 他法人・他自治体への展開UI | 初期運用の検証後でよいため |

# 11. 移行時の注意

## 11.1 既存保育記録

- 架け橋・支援保育のために日常記録を複製しない。
- 元記録への参照リンクと、文書確定時のスナップショットを使い分ける。
- 元記録が後から修正された場合でも、確定文書の当時内容は再現できること。

## 11.2 既存個別支援データ

- 既に類似する個別支援計画テーブルがある場合は、項目対応表を作る。
- 自動移行できない項目は「未移行」「要確認」とする。
- 自由記述を無理に構造化して事実を変えない。

## 11.3 添付行政様式

- 原本ファイルをテンプレート原本として保管する。
- 出力結果を原本と見比べ、印刷範囲、改ページ、文字切れ、チェック欄、余白を検証する。
- LibreOfficeやブラウザだけの見た目で合格とせず、Excel・Word・PDFの実ファイルでも確認する。
- 大和市が新様式を配布した場合は旧様式を残したまま新版を追加する。

## 11.4 権限

- 園長、主任、法人管理者、指定職員の意味を既存ロールへ正しく対応させる。
- 施設横断権限と自施設権限を分離する。
- 担当者指定は職員の役職だけでなく、年度・施設・対象業務ごとの付与を可能にする。

## 11.5 AI

- 本番導入前に匿名化したケースでClaude/OpenAIの出力差を検証する。
- 良い文章であることより、根拠一致と不適切な推測がないことを優先する。
- Providerやモデル変更で文章品質が変わるため、プロンプト版とモデルを文書に紐付ける。

## 11.6 本番切替

```text
開発環境
→ 匿名化データで自動テスト
→ 検証環境で帳票比較
→ 指定施設・指定クラスで試験
→ 紙・既存Excelとの並行運用
→ 管理者受入
→ 本番
```

支援保育事業は、少なくとも1回分を既存様式と並行作成し、全ページ・全項目・人数・金額を照合してから正規運用する。

# 12. 横断受入基準

1. 権限外の職員がURLやAPIを直接指定してもデータを取得できない。
2. 施設・年度・期を変更しても過去データが書き換わらない。
3. AI生成文の根拠、生成条件、採否を追跡できる。
4. 確定後の変更は改訂として残る。
5. 出力ファイルと画面・DBの確定内容が一致する。
6. テンプレート版と生成ファイルの対応を確認できる。
7. 必須項目、不整合、未承認を検出できる。
8. 一括出力へ権限外・対象外の園児や機微情報が混入しない。
9. 操作・閲覧・AI送信・承認・ダウンロードの監査ログが残る。
10. 既存機能と既存データを壊さず、機能フラグで段階公開できる。
11. マスタに存在する氏名、施設、所属、クラス、在籍、年度等を再入力せず利用できる。
12. 同じ情報を1回入力すれば、必要な複数様式へ反映される。
13. AI文章案を項目単位で作成・修正・再生成できる。
14. 通常の利用者が長文をゼロから入力せず、候補選択と短い補足で下書きを作成できる。
15. 自動入力値の取得元と基準日を追跡でき、確定文書では当時値を再現できる。
