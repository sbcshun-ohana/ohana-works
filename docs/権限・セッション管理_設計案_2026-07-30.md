## 0. 全体像

3つの要件は「iPad共有時の“誰が操作しているか”の安全性」という同じ問題系のため、1設計にまとめる。
- **要件1**は権限モデル(誰が何をできるか)。**要件2/3/自動ログアウト**はセッション(今誰がログインしているか)。
- 依存: 要件2/3の**役職表示**は要件1で追加する役職コードを含む。要件3の**端末縛り**は既存のキオスク端末登録(`devices`)を流用。自動ログアウトと要件3(ピッカー復帰)は動線で連結。

## 1. 要件1: 統括園長・統括管理者

### 1.1 追加する2役職

| 役職 | ロールコード案 | スコープ | 権限 | 付与 |
|---|---|---|---|---|
| **統括園長** | `executive_director` | **全施設(定義上・付与テーブル不要)** | 全施設で 園長(director)以下＋管理者＋統括管理者を包含。**labor_manager/system_admin の職員業務系(給与・社保・マイナンバー)は含まない** | `employee_roles`(role=executive_director・**office_id=null**)。system_admin のみ |
| **統括管理者** | `area_manager`(代替 `oversight_manager`) | **付与テーブルで対象施設を明示** | 指定施設で office_manager(管理者)相当。自施設は従来の office_manager | `employee_roles`(role=area_manager)＋付与テーブル。system_admin のみ |

- sort_order は既存(1..7)を壊さず広い採番(例 25/45)で**追記のみ**。表示順は §2.2 の役職定数で制御。
- **職員業務系は拡張しない**: executive_director を `is_labor_manager_plus` / `is_system_admin` に**追加しない**。

### 1.2 多施設権限付与テーブル

```sql
create table multi_office_authority_grants (
  id uuid primary key default gen_random_uuid(),
  grantee_employee_id uuid not null references employees(id) on delete cascade,
  office_id uuid not null references offices(id),
  granted_level text not null check (granted_level in ('office_manager','director')),
  granted_by uuid not null references employees(id),
  granted_at timestamptz not null default now(),
  revoked_at timestamptz, revoked_by uuid references employees(id), note text
);
create unique index uq_moag_active on multi_office_authority_grants
  (grantee_employee_id, office_id, granted_level) where revoked_at is null;
```
- 有効付与=`revoked_at is null`。統括管理者は `granted_level='office_manager'` を対象施設ごとに持つ。統括園長は全施設roleのため行不要(将来 `director` レベル付与の余地は残す)。
- 監査: `log_event_change` トリガ。付与/剥奪RPC(`grant_multi_office_authority`/`revoke_multi_office_authority`)は **`is_system_admin()` のみ**(SECURITY DEFINER)。

### 1.3 施設スコープ判定5関数の変更(各に2点)

対象: `manages_office` / `manages_childcare` / `is_support_childcare_chief` / `has_goal_sheet_edit_access` / `childcare_office_manager_employee_ids`。
1. `executive_director` を**全施設スコープで許可**(system_admin と同じく office_id 無視で true)。
2. 付与テーブルの OR 句:
```sql
or exists (select 1 from multi_office_authority_grants g
  where g.grantee_employee_id = my_employee_id() and g.office_id = target_office_id
    and g.revoked_at is null and g.granted_level in ('office_manager','director'))
```
- RLSポリシーは関数を呼ぶだけなので**ポリシー改修0**。`has_childcare_office_access` は `manages_childcare` 経由で自動波及。

### 1.4 大和「director 空席」影響監査(確定事項1)

- **director を単独要求する箇所は無い**(5関数で director は chief/office_manager と並列)。大和は chief 在籍で元々穴なし。
- 支援保育**最終承認** `is_support_childcare_office_approver` と 目標シート承認 `is_goal_sheet_office_approver` は **role不使用**(承認者テーブル or system_admin)。→ ここに **`executive_director`(全施設)を追加**し、統括園長が全施設の最終承認者として通るようにする。
- お知らせ承認(園長以上)にも `executive_director` を含める(お知らせ設計書 §6.6/§9-4 更新)。
- **結論: 5スコープ関数＋2承認関数に executive_director を追加すれば、大和の director 空席で穴は生じない。**

### 1.5 既存役職別UIの非破壊確認(確定事項1-4)
- admin_web に役職コード網羅 switch で例外を投げる箇所は無く(サーバ判定 `is_labor_manager_plus` 等に委譲)、roles マスタ動的取得の画面は自動反映 → **破壊リスク低**。役職プルダウンがDB駆動かハードコードかは実装時に確認。役職表示名は §2.2 の定数へ集約し「(不明)」表示を防ぐ。

### 1.6 大原利奈への統括園長付与(確定事項1-5・**本番は承認後**)
1. 本番クエリ⑥で employee_id・現行役職・表記揺れ確認。
2. `insert into employee_roles(employee_id, role_id, office_id) select :ohara_id, id, null from roles where code='executive_director';`
3. 大和の既存 director 行は空席化するなら削除(統括園長が包含のため残置も無害)。admin_web に任意role割当UIがあればUI手順も併記。

## 2. 要件2: ログイン中アカウントの常時表示


## 3. Ohana Kids 自動ログアウト(確定事項2)

- **10分無操作で自動ログアウト**。操作(タップ/入力)のたびにタイマーリセット(アプリ全体を `Listener` で捕捉)。
- **タイムアウト設定可能・既定10分・最小5分ガード**(5分おき業務チェックの現場実態)。
  - **2段階**: まず**アプリ定数(既定10分・下限5分)でDB変更なし**に実装 → 施設別可変化は次段で `offices`/専用設定へ列追加(別マイグレーション・別承認)。
- **予告**: 残り1分で全画面予告オーバーレイ、**タップで延長**。0で `signOut()` → §4 のピッカー画面へ。
- **下書き保護(データ消失防止)**:
  - 入力中テキスト(園内記録の書きかけ等)を onChange デバウンスで**端末ローカル**(shared_preferences)に自動下書き保存。キー=`employee_id + child_id + category`、**ログイン中ユーザーのキーのみ復元対象**(他人の書きかけを見せない)。
  - 自動ログアウトでも下書きは残し、**再ログイン後に同一キーの書きかけがあれば復元プロンプト**。サーバ送信は保存RPC実行時のみ、保存成功でローカル下書きクリア。

## 4. 要件3: 職員ピッカー + PIN 簡易ログイン(Ohana Kids)

方式: 登録済み保育業務iPad限定。施設の職員一覧から自分をタップ → 個人PIN(4〜6桁) → ログイン。

### 4.1 端末縛り(確定事項3-1)
- PINログインは**登録済み保育業務端末のみ**。既存の**キオスク端末登録(`devices` テーブル: `device_code`/`status`/`office_id`、`pair-device` Edge Function、Flutter `device_pairing_service`)を流用**。端末は `office_id` に紐づく。
- **メール+パスワードは全端末で従来どおり併存**(admin_web・Ohana Staff・未登録端末はこちらのみ)。PINは登録端末での“追加の速い経路”であり、パスワード方式を置き換えない。

### 4.2 職員ピッカー(確定事項3-2)
- 端末が紐づく施設で**保育業務にアクセスできる在籍職員**を氏名＋役職で一覧。判定は既存 `has_childcare_office_access(device.office_id)`(所属 or 管理)を母集合とする専用RPCで**必要最小列(employee_id・氏名・役職名)だけ返す**。
- **統括園長・統括管理者の表示**: 両者は当該施設に `has_childcare_office_access` が真になる(executive_director=全施設、area_manager=付与施設)。→ その施設で作業するなら**ピッカーに表示**する。統括園長は全施設のピッカーに出る(1名のため実害小)。表示可否を絞りたい場合は「その施設に常勤所属(employee_office_assignments)がある者のみ既定表示＋“他施設権限者を表示”の展開」も可(判断ポイント)。

### 4.3 PINの保管と検証(確定事項3-3)
- テーブル `staff_pins(employee_id pk, pin_hash text, updated_at, failed_attempts int, locked_until timestamptz)`。**PINはハッシュのみ**(bcrypt/argon2)。**平文・ログ出力禁止**。
- RLS: クライアントから `pin_hash` は**一切読めない**(SELECTポリシーを付けない/deny)。設定・検証は下記の経路のみ。
- **検証とセッション発行は Edge Function(service role)がサーバ側**で `device_id(有効・office一致)＋employee(該当officeにアクセス可)＋PIN(ハッシュ照合)` を検証してから行う。**クライアントでPIN照合しない**。
  - セッション発行: Edge Function が検証後、対象職員の auth ユーザーに対する**サーバ発行セッション**(GoTrue admin API によるトークン発行)を返す。発行方式の具体(admin生成セッション/短命トークン交換)は実装時に確定するが、**「サーバ側検証後にのみ発行」**は設計の確定事項。

### 4.4 総当たり対策(確定事項3-4)
- **連続失敗でロック**。提案: **5回失敗で15分ロック**(`locked_until` による**時間経過で自動解除**)＋**admin_web 職員マスタからの管理者解除**の併用。ロック中の試行は即拒否。
- 試行(成功/失敗/ロック)は**ログ記録**(`sensitive_access_logs` 相当 or 専用 `pin_login_attempts`)。PIN値はログに残さない。

### 4.5 PINの設定・変更・リセット(確定事項3-5)
- **本人設定**: 初回は**メール+パスワードでログインした状態**で PIN を設定(ハッシュ化はサーバ側 RPC/Edge Function。平文はサーバに保存しない)。変更も同経路。
- **管理者リセット**: admin_web 職員マスタから対象職員の PIN を**リセット/クリア**(次回は本人再設定が必要)。RPCは `manages_office`(管理者以上)ゲート＋監査記録。

### 4.6 自動ログアウトとの連動(確定事項3-6)
- 自動ログアウト(§3)→ **ピッカー画面へ戻る** → 自分をタップ + PIN数桁 → **数秒で復帰**。パスワード再入力不要(登録端末のため)。§3 の下書き保護と組み合わせ、書きかけは復帰後に復元プロンプト。

### 4.7 承認系の重い操作の扱い(確定事項3-7・**両案併記/俊さん判断**)

対象: 支援保育の最終承認、お知らせの承認送信 等の重い/不可逆操作。

| 案 | 動線 | 利点 | 欠点/リスク |
|---|---|---|---|
| (a) **PINセッションのまま実行可** | 追加操作なし | 速い・現場の承認が滞らない | 4〜6桁PINは相対的に弱く、共有iPadの放置中に誤/不正承認の余地(自動ログアウト＋常時表示で緩和) |
| (b) **重い操作前にパスワード再入力(ステップアップ認証)** | 承認確定時のみ再認証 | 不可逆操作の保護が強い・監査上明確 | 管理者がiPadでパスワードを持ち歩かない運用だと承認が止まる・手間 |

推奨の目安(判断は俊さん): **通常操作はPINセッションで可、最終承認・お知らせ配信のみ (b) のステップアップ**(重い操作だけ再認証)。両案とも実装可能な構造(承認RPC呼び出し前に再認証フラグを要求できる)にしておく。

## 5. 拒否側E2E(実アカウント/実JWT・確定事項3-8＋要件1の権限境界)

| # | シナリオ | 期待 |
|---|---|---|
| 1 | 統括管理者が**付与外施設**の児童/文書へアクセス | 拒否 |
| 2 | 統括管理者が付与施設で管理者操作 | 成功 |
| 3 | 統括園長が**全施設**で管理者/承認操作 | 成功 |
| 4 | 統括園長が**労務系**(給与・マイナンバー・is_labor_manager_plus 相当) | **拒否**(職員業務系を持たない) |
| 5 | 剥奪後の統括管理者が旧付与施設へアクセス | 拒否 |
| 6 | **未登録端末**からのPINログイン試行 | 拒否 |
| 7 | **他施設職員のPIN**で当該端末からログイン | 拒否(端末officeにアクセス不可) |
| 8 | **ロック中**のPIN試行 | 拒否 |
| 9 | クライアントから `staff_pins.pin_hash` を直接SELECT | 拒否(0行/権限エラー) |
| 10 | 付与・剥奪RPCを **system_admin以外**が実行 | 拒否 |

正常系: PIN設定→ピッカー→PINログイン→自動ログアウト→ピッカー復帰、常時表示に氏名(役職)が出る、統括園長付与後に大和で承認が通る、監査ログに付与/剥奪/PIN試行が残る。実機確認は俊さん。

## 6. 影響範囲・実装順・判断待ち

### 6.2 実装順(案・main直コミット/1本ずつ)

### 6.3 判断待ち(俊さん)
1. ロールコード名: `executive_director` / `area_manager`(代替 `oversight_manager`)でよいか。
2. ピッカーに統括園長/統括管理者を「常時表示」か「他施設権限者は展開表示」か(§4.2)。
3. 重い承認操作: (a)PINのまま / (b)パスワード再入力(§4.7)。推奨は最終承認・配信のみ(b)。
4. PINロック: 5回/15分・自動解除＋管理者解除でよいか(§4.4)。
5. 自動ログアウトの可変タイムアウトを初期から施設設定(DB)にするか、まずアプリ定数(10分)で出すか(§3)。
